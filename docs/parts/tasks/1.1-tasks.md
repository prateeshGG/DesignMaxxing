# 1.1 Repository, Environments & Delivery: Task List

Source: [1.1 spec](../1.1-repository-environments-delivery.md) · decisions applied: F-20, F-24, F-35, F-45, F-53, F-55, F-58, F-61 · status: draft

**How to read this list.** F-45 and F-55 put the crawler and everything else on the founder's computer before launch: local Postgres, Redis, web app and worker, with the crawler started by hand for a crawl session (F-53). Groups G1 to G5 are that local-first path and are what V0 needs to start building. G6 is the online deployment (two-machine shape, registry, deploy and rollback) and is built only **when the library goes online**. Task ids are stable; new tasks take the next free number. Names marked (P) in the spec are used as written (OQ-1.1-1).

## Not in V0
- Kubernetes, Terraform, OpenSearch, vault, event bus, `apps/api`, `apps/worker-dashboard`, `notification-service`: never built; `layout-check` (T05) keeps them out (R1, R2, F-35).
- Staging environment: none in V0 (OQ-1.1-8); revisit at G4.
- Runtime-editable limits from `/admin` (OQ-1.1-23): limits are read-only in V0; the admin screen is 6.4's.
- Hosted-browser fallback configuration: not V0 (§1 Explicitly not built).
- Python toolchain in CI or images (OQ-1.1-25): no task until the first Python script exists.
- Slim `worker-app` image (OQ-1.1-24): one image in V0.
- `landing/` inside the workspace or CI (OQ-1.1-26): 8.1 decides.
- Second Crawler VM: only the hook is built (no fixed host names, no host-local state, checked by T27); adding a machine is a deployment action (doc 20 §5).
- Nightly `golden-canary` schedule: dropped before launch because the crawler never starts by itself (F-53); on-demand only (T37).
- Provider private network between two VMs (OQ-1.1-10): not applicable before launch (F-55); after launch only the encryption rule of T51, with 1.7 writing the firewall.
- `CRAWLER_STATE_KEY` behaviour (V2): only the scope-check hook exists (T13).
- Deploy, secret-rotation and restore runbooks (prose): 8.4.
