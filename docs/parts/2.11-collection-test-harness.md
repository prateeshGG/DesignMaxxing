## 1. Purpose & Scope

**Purpose.** Every other collection spec makes promises: a unit reaches a terminal state within its deadline, a blank render is never published, a blocked site stays blocked, Redis can be wiped without losing work, a crop never cuts through a media element. Until something proves them, they are claims. 2.11 turns each promise into a repeatable test, says what a pass is, and says how the result is reported. It implements DC-12 (the torture suite, the golden-set canary and the chaos drills must pass before a capture-runtime change ships) and it is the place where DC-16 ("each hazard gets a fixture") is made true.

Three things make up the harness (doc 22 §13):

| Part of the harness | What it is | Runs |
|---|---|---|
| **Torture suite** | A local, deterministic **fixture site** that reproduces each hazard and failure, plus synthetic inputs for the pure checks, plus fault injection against a scratch stack. Each fixture has an expected outcome and ends in a terminal state within its deadline | Locally and in CI; offline (F-45) |
| **Golden-set canary** | 20–30 founder-approved real sites captured through the normal pipeline on a scratch stack and compared with stored baselines and a control run, so a drift in Chromium, Playwright or our own code is seen before it ships | On the founder's computer (F-45), nightly when it is free and on every runtime change |
| **Chaos drills** | Deliberate failures of the processes and services around the capture (kill -9, Redis wipe, Postgres restart, disk full, object storage down, network drop, machine sleep) and the recovery that must follow | Automatable ones in the harness stack; the real sleep drill by hand before alpha |

The harness does **not** re-specify the behaviour it tests. Every fixture cites the owning Part and its rule or edge-case ID; the expected outcome follows from that rule. If a behaviour changes, the owner's spec changes first (maintenance rule of the template), then the fixture.

**Design goal (DC-17).** The harness must cost the founder no time on a green day (one line in the daily summary) and, on a red day, point at the owning Part and rule so that the fix goes into the capture runtime, not into founder time.

**Phase:** `[V0]`. Later-phase hooks are marked **[hook]** and are compatibility only (F-40): tablet and laptop fixtures (2.8, V1), interaction-state fixtures (2.7, V1), scroll-pass-video fixtures (2.4, V1), authenticated and mobile fixtures (7.x, V2). None is built in V0.

## 3. Data Model

### 3.1 No tables, no events

**2.11 owns no database table, no event, no queue and no BullMQ job in V0 (P).** Everything it keeps is files: the repository module (fixtures, catalogue, golden-set list, drill definitions), and a data directory outside the repository (reports, baselines, evidence). Reasons: the harness is test tooling, not product data; a table would need migrations in every environment (1.2) and would tempt the product to read test results; the numbers the canary compares already exist in the owners' tables and read contracts (`gate_result`, `capture_unit`, `capture_attempt`, `raw_artifact`), which the harness reads from its **scratch** database only. Whether results should also be mirrored into Postgres for dashboards is OQ-2.11-24. The harness reads with the owners' read contracts where they exist and with read-only SQL in test code otherwise; it never writes except through the owners' functions (as the product would).

| Owned by 2.11 (files) | Read-only from the scratch database (owner) |
|---|---|
| Fixture definitions, expected outcomes, fixture pages and data; the catalogue index; the golden-set list; drill definitions; doubles; run reports, result records, history; baselines (numbers and hashes); evidence of failed fixtures and of golden runs | `crawl_run`, `capture_job`, `capture_session`, `capture_unit`, `capture_attempt`, `intake_hold`, `event_delivery` (1.4); `source`, `site_recipe`, `takedown_request` (1.5); `discovery_run`, `discovered_url` (2.1); `raw_artifact` (1.3); `gate_result`, `gate_check_result`, `gate_section_result`, `bad_page_fingerprint`, `publish_batch` (2.10); `global_breaker` (2.9); `screen`, `section` where 3.2 has created them (1.2) |

### 3.4 Expected-outcome record and notation (P)

`expected` has three parts: `required` (assertions that must hold), `target` (assertions reported but not blocking, used where an owner says "candidate technique, not a guarantee": H7) and `invariants` (named checks of H9 and H10 beyond the global ones). The catalogue's "Expected outcome" column uses this shorthand:

| Notation | Meaning |
|---|---|
| `child:` | Result of one attempt from the standalone child (2.2 `AttemptResult`): `captured`, `failed(CODE)`, `blocked(CODE)`, `skipped(CODE)`; `+flag` / `−flag` = attempt flag present / absent |
| `gate:` | 2.10 verdict `ACCEPTED`, `NEEDS_REVIEW`, `REJECTED`, `BLOCKED`, `SKIPPED` with the reason code; `Gnn` = a check outcome (`pass`, `fail`, `not_evaluable`, `not_run`) or a section verdict |
| `state:` | Final unit state with its reason, `STATE(reason)`; `job:` final job state |
| `section map:` | The expected `SectionMap` stored with the fixture, compared exactly (2.3 R30) |
| `inv:` | An extra invariant checked from the request log, the database or the host |
| "never published" | No `screen` or `section` produced by the fixture's units reaches `eligible` or `published` (DC-06) |
| "inside the fixture deadline" | The run reached the stated terminal state before `deadline_s` (H8) |

Assertions read these sources: the child's `result.json` and files (2.2), the page-capture report and `modifications[]` (2.3), `media-manifest.json` (2.4), `gate run` output or `getGateResult` (2.10), the unit and attempt tables through the owners' read contracts (1.4), the fixture site's request log (§3.5), Docker object state (leaks, labels) and the harness volumes.

### 3.5 Fixture-site request log record (P)

One JSON line per request, appended to a file on the harness volume (no HTTP endpoint exposes it: F-24 spirit):

| Field | Notes |
|---|---|
| `t_ms` | Monotonic milliseconds since the run started |
| `host`, `method`, `path` (query hashed), `status`, `bytes_sent`, `aborted_by_client` | |
| `ua` | The `User-Agent` seen (H10 compares it with `CRAWLER_USER_AGENT`) |
| `referrer_present` | Boolean (for the hotlink fixture) |
| `headers_seen` | Names only, from an allowlist plus any header outside the normal browser set (a spoofing or stealth header would show here) |
| `kind` | `navigation`, `subresource`, `robots`, `sitemap`, `beacon` (page-side event spy), `other` |
| `fixture_id` | From the host name |

Page-side event spies (a few lines in each fixture page) report input events, viewport size at shot time and page-visible state as `beacon` requests, so the log is the single oracle. A beacon is page traffic and is not counted in the pacing assertion.

### 3.6 Profiles: time scaling (P, values are [Estimate] suggestions, OQ-2.11-4)

All limits are configuration (doc 22 §11, 1.1 R9), so the `fast` profile overrides **numbers only**, keeping the ratios the owners require (H21). Unchanged under every profile: the F-10 rate and concurrency floors and ceilings (so `Crawl-delay` fixtures run in real time) and F-11's readiness definition.

| `LIMIT_BREAKER_OPEN_BASE_H` / `LIMIT_BREAKER_OPEN_MAX_D` (2.9) | 6 h / 7 d | about 15 s and about 60 s, expressed in the key's unit (OQ-2.11-4) |

| `STORAGE_GC_GRACE_HOURS` (1.3) | 48 | 0 |

The `full` profile uses the decided values; it is the only profile in which `full`-tagged fixtures run, and the one required before alpha (H22). ### 3.8 Golden-set definition, baseline and comparison records (P)

**`golden/golden-set.yaml`:** a list of entries `{ domain, category, added_by, approved_at, status, note }` with `status` ∈ `active`, `paused`, `removed`; the file holds **no captured content**. The set is 20–30 sites (doc 22 §13). Membership rules: §5.5. Each domain is also a `source` in the **scratch** database (created with `createSource` and approved with `setSeedStatus`), never in the real one.

**`baseline.json` (per site):** `{ domain, accepted_at, accepted_by, reason, image_digest, host_os, fonts_image_version, gate_version, config_version, units: [{ canonical_url, profile, state, rung, quality_score, verdict, failed_checks[], phash_motion, phash_static, hash_algo, section_count, method_counts, coverage_ratio, hazards_unresolved[], straddle_count, crop_through_media_count, segmentation_weak, readiness {elapsed_ms, capped}, flags[], media {items_by_layer, partial}, bytes, duration_ms }] }`. Numbers, ids and hashes only: no page text, no images (H15). Stored outside git (OQ-2.11-9).

**Comparison record** (inside the report): per unit pair (same `canonical_url` and profile in baseline and candidate; pages found in only one run are listed, not compared) and per metric: `baseline`, `candidate`, `control` (when a control run was made), `tolerance`, `class`.

### 3.9 Drill definition record (P)

`{ id, injection (from the toolbox of §5.6), target (labelled harness object), arm_condition (for example "after N units are RUNNING"), window_s, restore, verify (assertions), safety (limits), mode: auto | manual }`; `auto` rows are run by the runner locally and in CI where Docker is available. A drill has the phases `arm → inject → observe → verify → restore → post-conditions (H9)`.

### 3.10 State machines (not stored)

```
run:     planned ──► running ──► passed | failed | error | not_run      (not_run = offline, active crawl session, prerequisite missing)
fixture: pending ──► running ──► passed | failed | error | deferred | info_failed ;  failed ──(re-run passes)──► unstable
canary difference:  compared ──► unchanged | improvement | site_drift | access_lost | runtime_regression | unclassified    (§5.5)
manual drill: due ──► recorded(passed | failed)
```

### 3.11 Migration notes

None: no table. The scratch database is built from empty by 1.2's migrations on every stack start (or kept between canary nights, §5.5). The harness data directory is created on first run; its layout is versioned by a `harness_version` field in every record.

## 4. API Surface

**No HTTP endpoint is added** (F-24: no `/internal/*`). The fixture site is a separate test-only container on the harness network; it is never part of the production Compose files or images, and it has no control endpoint (it is configured by files and read through its log file). **No event, queue or BullMQ job is added.** 2.11 exposes (a) root scripts and CLI commands, (b) the result record, (c) module contracts, (d) the fixture-site contract, (e) configuration keys, and (f) seams it asks other Parts for.

Common rules for every interface below:

| Rule | Detail |
|---|---|
| Auth | None beyond local access: the commands run as the founder on the founder's computer or as the CI job. The harness stack uses throwaway credentials generated per run; calls into the owners' functions carry `actor = harness:<run_id>`; no production secret is read |
| Errors | The exit codes of §4.2. The harness distinguishes a product `failed` from its own `error` and never turns one into the other |
| Idempotency | A fixture run is independent: each run creates its own Compose project and scratch database and removes them. Re-running a fixture gives the same result on the same image digest (H3). `harness canary baseline accept` is idempotent per run id; `harness drill record` per drill id and commit |

### 4.2 Exit codes and the commit-bound result record

| Exit code | Meaning |
|---|---|
| 0 | `passed` |
| 1 | `failed` (a required fixture or a canary check failed) |
| 2 | `error` (the harness could not judge: guard tripped, image missing, stack would not start, too many sites unreachable) |
| 3 | `not_run` (offline for a golden run, a crawl session is active, prerequisite missing) |

`failed`, `error` and `not_run` all block (DC-12: "must pass"; what could not be run is not a pass). ## 5. Business Rules & Edge Cases

### 5.1 Rules

| # | Rule | Basis |
|---|---|---|
| H1 | **Isolation.** The harness runs only against stacks it created: its own Compose project, its own Postgres database (name prefix `harness_`), its own Redis, its own object-storage emulator, its own spool and temp volumes, its own network `harness-net`; every container carries the label `dm.owner = harness:<run_id>`. At start it refuses to run if the database, Redis or storage configuration does not point at instances carrying the harness marker (a marker row or key written at creation). `FLUSHALL`, `kill`, `docker pause`, volume fill and network cuts act **only** on harness-labelled objects. The harness stack also uses its own container-runtime scope, so that neither a real supervisor's reaper or start-up sweep nor a harness supervisor's can see the other's children (2.9 §5.8, R28 assume one supervisor per host; OQ-2.11-26). The founder's real database, queue, spool, storage and files are never touched, and the host disk and clock are never altered | F-45, F-35, DC-14, 2.9 R29 |
| H2 | **Hermetic fixture runs.** `harness-net` has no route out. Every fixture host is a `.test` name served by the fixture site; a request to any other host fails and is logged as a violation of the run. The torture suite and the unit layer must pass with the network disconnected | F-45, 1.1 R14 |
| H3 | **Deterministic fixture site.** The same request returns the same bytes. Content is derived from the fixture id and a fixed seed; nothing depends on the wall clock; time-dependent behaviour is relative to the request or page load ("the counter stops 3 s after load"). `harness selftest` serves every page twice and compares bytes | DC-02, 2.2 R3 |
| H4 | **Original content only.** Fixtures are written for this project. Field-observation fixtures reproduce a behaviour, never a third-party page: no copied markup, text, images, fonts or scripts | F-18, F-41, F-44 |
| H5 | **The catalogue is the contract of the harness, not of the behaviour.** A row's expected outcome must follow from the cited owner rule or edge case. A change of behaviour changes the owner's spec first, then the fixture. `harness check` verifies that every cited ID exists in the owner's spec file (a table row beginning with that ID) and that every request listed in §5.8 maps to a row | DC-12; template maintenance rule |
| H6 | **Expectations are structural**: states, reason codes, flags, check outcomes, counts, section maps, request-log facts. Pixel-golden images are not used, because expected pixels depend on the image digest and its fonts (OQ-2.2-12). Exceptions: `det_static_twice` (same digest, same page, twice) and the perceptual-hash comparisons the gate itself defines (G03, `can_hashes`) | OQ-2.2-12, F-25 |
| H7 | **Safety invariant first, technique second.** Where an owner calls a technique a candidate and not a guarantee (DC-16, doc 23), the required expectation is the safe failure (the problem is flagged, the unit is never ACCEPTED on that account, nothing is published automatically); technique success is a `target`, reported and not blocking until the spike makes it required | DC-16, 2.3 §5.2, doc 23 DC-16 |
| H8 | **Terminal within the deadline.** Every pipeline and chaos fixture ends in the stated terminal unit state (or job state) before its fixture deadline (§3.6 formula). The runner stops a run that overshoots 1.5 × the deadline and records the stuck state as the failure; a fixture is never left hanging. A run selected with `--fixture` or `--part` is `partial` and never counts as a pass | DC-01, DC-04 |
| H9 | **Post-conditions after every pipeline and chaos fixture.** (a) no unit left in `LEASED`, `RUNNING`, `CAPTURED` or `VALIDATING`; (b) no duplicate rows: one row per `unit_key`; per `(capture_unit_id, retry_round, seq)`; per `(capture_attempt_id, type, sha256)`; one open `capture_session` per live child; one `gate_result` per attempt; (c) no leaked child container, process, temp directory or intake hold that the fixture did not expect; (d) a second reconciler run and a second janitor tick change nothing; (e) after a GC run with grace 0 no blob is unreferenced; (f) every artifact row with `stored_at` set has a readable blob | 1.4 §7, 1.3 R13, E5, 2.9 R21, 2.5 R22 |
| H10 | **Honest, polite and safe behaviour is asserted from the request log on every fixture-site run.** The `User-Agent` equals `CRAWLER_USER_AGENT` and is identical on every request; only the fixture's hosts are contacted; `robots.txt` is fetched before any page of the host and no disallowed path is requested; navigation pacing follows the OQ-2.2-1 default (top-level navigations and discovery/S3 fetches to a host: at most 1 per second and 2 concurrent; subresources are recorded, not asserted, OQ-2.11-16); the page-side event spy shows no input event other than the dismiss clicks the owner allows (2.3 R4, 2.2 R15); no `POST` reaches the site; after a takedown no navigation starts later than one attempt. For every `child` run, each entry of 2.3's `modifications[]` is marked restored and `viewport_unchanged` is true for every shot (2.3 R5, R14) | F-10, DC-08, SC-03, 2.2 R7–R10, R15; 2.3 R4, R5, R14 |
| H11 | **Blocks are measured and never evaded.** Block fixtures assert exactly one polite retry (1.4 R10) and identical identity (UA, headers, address) across attempts. The harness contains no code path that rotates an address, changes a user-agent, solves a challenge, slows down to look human or retries a block more often than the product does. `BLOCKED` is a result to report, not a failure of the suite | DC-08, DC-18, SC-03, SC-05 |
| H12 | **No benchmark contamination.** The labelled benchmark and dev set (F-29, 4.6) are never read by the harness. The golden set is a regression set, not an evaluation set: nothing is tuned on it by the harness, and a stored baseline is not a label | F-29, doc 23 gap 13 |
| H13 | **Real sites only through the production path.** The canary reaches a real site only through the code the crawl uses (2.1 discovery with robots, 1.4 pacing, 2.2 child with the honest user-agent, 2.10 gate), on a harness stack. It never uses standalone shortcuts that skip robots or pacing. Per domain: 1 request per second, 2 concurrent | F-10, F-11, R14 of 1.1 |
| H14 | **The golden set is chosen and approved by a person.** Members are founder-approved sources (DC-19, F-46). The harness never adds, discovers or replaces a site; the founder may pause or remove a site at any time; a source under takedown leaves the set at once and its stored data is purged | F-46, DC-19, 1.5 R-7, E-3 |
| H15 | **Golden captures are private evidence.** They live only under `HARNESS_DATA_DIR/evidence` and in the harness stack's private storage on the founder's computer; never committed, never in CI logs or artifacts, never displayed outside local admin tools. Reports and baselines from golden runs hold numbers, ids, hashes and counts, never page text | F-18, F-41, F-42, 1.3 R17, 2.10 R23 |
| H16 | **The canary and a crawl session do not run at the same time** on the same computer by default: they share the founder's address and CPU, and pacing state lives in separate Redis instances, so F-10 could be exceeded for a domain that is both a golden site and a crawl target. The canary refuses to start while `supervisorStatus` reports an active session (exit 3; the founder may override, logged). The hermetic suite and the chaos rows may run during a session, at low priority, only when the container runtime is isolated by a separate daemon (OQ-2.11-26); otherwise they refuse to start (exit 3) | F-10, F-45, 2.9 R34, R28 |
| H17 | **A baseline changes only by a founder action** (`harness canary baseline accept`, with a reason), never automatically: drift must not approve itself | DC-12, doc 22 §2 #17 |
| H18 | **Classify before blocking.** Each canary difference gets exactly one class (§5.5): `unchanged`, `improvement`, `site_drift`, `access_lost`, `runtime_regression` or `unclassified`. Only `runtime_regression` and `unclassified` block | DC-12, DC-18 |
| H19 | **No automatic retry of required fixtures.** A failed fixture may be re-run once, only to label the failure `unstable`; an `unstable` fixture still blocks until it is fixed (a harness defect) or removed by a catalogue change the founder approves | DC-12 |
| H20 | **No waivers in V0**: a failing required fixture is fixed in the runtime, or the owner's rule is changed in its spec first (H5); there is no "ship anyway" switch (OQ-2.11-17) | DC-12, DC-17 |
| H21 | **Time scaling changes numbers, never logic.** The `fast` profile overrides only existing `LIMIT_*`/policy keys and keeps the ratios the owners require (heartbeat timeout several times the interval; attempt deadline above the child total). A limit that cannot be scaled because it is a code literal is reported to its owner as a defect (1.1 R9) | 1.1 R9, DC-01 |

**Schedule.** Nightly at a fixed local time, only when the computer is on and no crawl session is active (H16); on demand for a runtime change (`harness canary run --sha`); and in the `full` profile before alpha. A run that overlaps another is refused (lock file, EH15).

**Run procedure.**

| Step | Action |
|---|---|
| 1 | Preflight: H1 guards, free space, network reachable, no crawl session, image digest of the commit under test, control image available (the previous release image kept by 1.1) |
| 2 | Start the harness stack (the scratch database may be kept between nights so the discovery tie-break of OQ-2.1-4 keeps the page set stable) |
| 3 | For each active site: `startCrawl` (purpose `crawl`) on the scratch stack with a per-source policy `max_pages = HARNESS_GOLDEN_MAX_PAGES` (stricter than F-10, allowed by 1.5 R-3). Discovery, pacing, robots, leases, the child, the gate all run as in production. Pages come from 2.1's plan; the canonical URLs of the plan are stored with the run |
| 4 | Wait for the run to finish (2.5 roll-up) within the run's time limit; collect metrics through the owners' read contracts (`getGateResult`, `gateStats`, `jobUnitSummary`, `getDiscoveryRun`, `listRawArtifacts`) and the page-capture report, media manifest and readiness report artifacts |
| 5 | Compare each unit pair (same canonical URL and profile) with the baseline (§3.8) |
| 6 | **Control runs, adaptive:** for sites with a difference beyond tolerance, run the same pages again with the control image (the previous release) now, and classify |
| 7 | Second golden run after `HARNESS_GOLDEN_RECRAWL_GAP_MIN` minutes for the false-"changed" measurement (`can_false_changed`, deferred until 3.4) |
| 8 | Build the report and the result record; delete evidence beyond retention (H30) |

**Comparison and classification.** Differences are classified once per unit and metric (H18):

| Class | When | Blocks? |
|---|---|---|
| `unchanged` | Within tolerance of the baseline | no |
| `improvement` | Better than the baseline beyond tolerance | no (reported; baseline refresh offered) |
| `site_drift` | The control run (old image, same time) differs from the baseline beyond tolerance and the candidate matches the control: the site changed, not our runtime | no (reported; baseline refresh offered) |
| `access_lost` | The unit is `BLOCKED`, `SKIPPED` for robots, or unreachable in the control run as well: the site's access changed | no; reported with `BLOCKED %` per category (DC-18); the founder may pause or remove the site; never worked around |
| `runtime_regression` | The candidate is worse than the control (or than the baseline when the control equals it) beyond tolerance | **yes** |
| `unclassified` | A difference whose control run could not be made (control image missing, site unreachable in the control run only) | **yes** until the founder decides (cannot prove site drift) |

**Metrics and suggested tolerances ([Estimate]; calibrate on the first five nightly runs, OQ-2.11-10).**

| Metric (owner) | Regression when |
|---|---|
| Verdict (2.10) | Any unit moves to a worse verdict (ACCEPTED → NEEDS_REVIEW, REJECTED or BLOCKED; NEEDS_REVIEW → REJECTED) |
| `quality_score` (2.10) | A unit drops by more than 5 points, or the mean over comparable units drops by more than 2 |
| Above-the-fold hash similarity (2.10, F-25) | Baseline and control ≥ 0.95 but the candidate < 0.95 |
| Readiness-cap rate, dismisser failure rate (2.2) | Up by more than 5 percentage points or by 2 or more units |
| `hazard_unresolved`, `segmentation_weak`, crop-through-media counts (2.3) | Up by 2 or more units, or from zero to any |
| Section count, method counts, coverage (2.3) | Changed without a change of `algorithm_version` |
| Media layer yield, `media` partial rate (2.4) | Yield down, or partial rate up, by more than 5 percentage points |
| Ladder: units needing S1 or later, final unit state (1.4, 2.2) | More units need S1 or later, or any unit ends in a worse state |
| Budget-cut units, units beyond deadline (2.2, 2.3) | Any unit beyond its deadline; any budget-cut unit not in the baseline |
| Duration p95, bytes per unit (informational) | Reported when up by more than 25%; not blocking |

**Block rate (DC-18).** The report lists `BLOCKED %` per seed category from unit outcomes (robots skips excluded, 1.5 R-4). A blocked golden site is a result, not a failure of the suite and not a reason to change identity.

**False-"changed" rate (DC-15).** After two golden runs the harness applies 3.4's normalization and hash to each comparable pair; units reported as changed over the short gap count as false by construction. Target ≤ 10% [Estimate]; above it the normalization is widened before re-crawls scale (DC-15). Deferred until 3.4 exists (H26).

**E2 scorecard (reported, informational as an absolute until the 20-site spike fixes the floors, OQ-2.11-12).** Pages with `quality_score ≥ 80` (E2: ≥ 90%); inbox share = `NEEDS_REVIEW` + `QUARANTINED` + `BLOCKED` ÷ units (DC-17: ≤ 5%); false-"changed" rate (≤ 10%); `BLOCKED %` per category; browser time per page (the E2 cost line counts AI too, which the canary does not use); founder-minutes per accepted site, taken from 4.4's recorded decision times when they exist and `not_measured` otherwise (OQ-2.10-30).

### 5.6 Chaos drills

**Injection toolbox** (all act on harness-labelled objects only, H1):

| Injection | How |
|---|---|
| Kill a process or container | `SIGKILL` of the child container, supervisor, gate handler or `worker-app`; `docker kill` of Postgres, Redis or the storage emulator |
| Freeze | `docker pause` of children, `SIGSTOP` of the supervisor (simulates a suspend: processes stop, the database clock keeps going) |
| Outage and restart | Stop and start the Redis, Postgres or storage-emulator container; `FLUSHALL` on the harness Redis |
| Network cut | Disconnect the crawler containers from `harness-net` services and back (never the host's network) |
| Volume fill | Fill a **dedicated size-limited volume** that holds the spool and temp directories (never the host disk) |
| Runtime double | A `ChildRuntime` double whose `healthy()` is false or whose `spawn` fails |
| Fake child | `harness-fake-child` speaks 2.2's protocol and misbehaves on script (malformed, oversize, path traversal, double or late result, never ready, ignores `abort`) |
| Provider double | Simulated `reportGlobalCall(ai_provider, …)` failures (4.1 is not built) |
| Process clock shim | A shifted wall clock for one process only (never the host clock); informational row |
| Manual | Real sleep or lid-close of the computer running the harness stack, with the founder present |

**Drill phases (every `chaos` row follows them):** arm (wait for the arm condition, for example "N units are `RUNNING`") → inject → observe for `window_s` (from the active profile) → verify (the row's expected outcome) → restore → post-conditions (H9).

**Safety rules (H1):** a drill never fills the host disk, never changes the host clock, never cuts the host network, never sleeps the computer except `chaos_suspend_real` by the founder's own action, and refuses to run if the target is not labelled `harness:<run_id>`.

### Reliability

- The harness is itself tested: `harness selftest` (H23), `harness check` (H5), fixture-site determinism (H3), and contract tests that keep the fake child equal to 2.2's schemas (EH11).
- A run that overshoots stops and says which unit was stuck (H8); `error` is distinct from `failed` so infrastructure trouble is never read as a product defect, and never read as a pass.
- Every injected fault is undone in `restore`; post-conditions (H9) prove the stack is clean before the next row. A crashed run leaves only labelled objects, which `harness run` removes at the next start (H1).
- The same suite can be run by a person with one command and by CI with the same result (same image, same configuration, H27).

### Security and privacy

| Area | Rule |
|---|---|
| The founder's data | Never touched: separate stack, database, Redis, storage, volumes, network and container-runtime scope (H1, OQ-2.11-26); the host disk, clock and network are never altered by a drill |
| Untrusted content | Fixture pages are written by us but behave hostilely on purpose (hangs, bombs, loops); the fixture site caps its own duration and bytes (EH18); the capture container keeps its sandbox profile (1.7); the metadata-address fixtures prove that nothing reaches the addresses |
| Test seams | The SSRF allowlist and CA trust exist only in `local` and `ci`; a `production` process refuses to start with them (§4.7) |
| Real sites | Robots, honest user-agent, F-10 pacing, no evasion (H11, H13); golden captures are private, never committed, never in CI artifacts, never displayed publicly (H15) |
| Secrets | The harness stack uses throwaway credentials generated per run; no production secret is needed or read; golden runs need no credentials (F-17) |
| Third-party content in the repo | None (H4); the golden-set file lists domains only |

### Assumptions

- [Assumption] A1: Docker Engine and Compose are available on the founder's computer and on the CI runner, and the supervisor's container-launch mechanism (OQ-1.1-12) works inside the harness stack in both places.
- [Assumption] A2: `.test` is reserved (RFC 6761), cannot collide with a real site, and each `<name>.test` is its own registrable domain for the Public Suffix library chosen by 1.1 (OQ-2.11-23).
- [Assumption] A3: Chromium in the capture container resolves fixture hosts through Docker network aliases with no browser flag.
- [Assumption] A4: The pinned Chromium can render WebGL on a software renderer inside the container (2.2 OQ-2.2-13); if not, the rows that need it are `error` of kind environment (EH14).
- [Assumption] A5: `capture-child --input --out` writes the same `result.json` and files as the production child (2.2 §4.8), and `gate run --input --out` is pure and offline (2.10 §4.8).
- [Assumption] A6: Every limit the fixtures scale is a configuration key (1.1 R9); a literal in code is a defect reported to its owner.
- [Assumption] A7: The scratch database may be kept between nightly canary runs, and 2.1's tie-break (OQ-2.1-4) then keeps each site's page set stable.
- [Assumption] A8: The previous release image stays available for control runs (1.1 deploy step 6 keeps it for rollback).
- [Assumption] A9: `[Field observation]` rows reproduce behaviours seen in 2026 on three real sites; those sites may change, which is why the `golden_field_*` rows are informational.
- [Assumption] A10: Fixture and golden counts and all durations in §7 are estimates; the first runs measure them.
