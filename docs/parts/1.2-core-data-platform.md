**How to read the Data Model.** Each column is tagged **D** (decided, with its source) or **S** (suggested default, waiting for the `OPEN QUESTION` named next to it). Suggested defaults are not decisions. When an OQ is answered, the S tag becomes D.

## 1. Purpose & Scope

**Purpose.** Give every other Part one PostgreSQL database that is the source of truth for metadata and relationships (doc 02 §3, DC-14). Give them one migration mechanism, one set of column conventions, and the base design-graph tables that normalization (3.2) fills and that search and the UI (5.x, 6.x) read.

**Phase:** V0. Later-phase tables are listed only as forward-compatible hooks and are marked as such (template rule 3, F-40).

| In scope (1.2 owns) | Out of scope (owner) |
|---|---|

**Circular references.** Base tables hold foreign keys to tables owned by 1.3, 1.4 and 1.5, and 1.4 holds a foreign key to `device_profile`. They are resolved by migration order (§3.6), not by merging ownership.

**External software:** PostgreSQL; the pgvector extension (F-31, D-34); a UUIDv7 generator (library or native function, OQ-1.2-3); a migration runner (OQ-1.2-2). No managed database service (F-35).

**Frozen decisions that constrain this Part**

| ID | Constraint |
|---|---|

| F-26 | Relational Postgres only; design graph = foreign keys + indexed relationship tables; no graph DB |
| F-21 | `ScreenState` not `UIState`; no `SourceVersion` in V0; design tokens = JSONB on `Section`/`Page`/`ProductVersion`; review items = `Classification` rows; per-domain policy on `Source` |

| DC-14 | Postgres is the single source of truth for unit state; Redis/BullMQ is rebuildable |
| DC-02, F-24 | Units are idempotent; delivery is at-least-once; consumers are idempotent |
| DC-06 | `capture_status` and `publish_status` are separate; `publish_status ∈ {unpublished, eligible, published, withdrawn}`; only `published` is user-visible |
| F-18 | Takedown within 48 h, propagating website → pages → screenshots → assets → embeddings → search index → cached thumbnails → collections |
| F-02, F-17 | V0 rows are public marketing websites, `logged_out` state only |
| F-07 | Sized for ≈ 500 sites / ≈ 10,000 pages, under the $200/month cap |

### 3.1 Platform

| Item | Value | Status |
|---|---|---|

| Extensions | `vector` (pgvector), enabled by migration 0001 | D (F-31) |

### 3.2 Shared conventions (apply to every table in the repo, all Parts)

| # | Convention | Rule | Status |
|---|---|---|---|
| C1 | Primary key | Every table has `id uuid PRIMARY KEY` holding a UUIDv7 | D (F-23) |
| C2 | ID generation | Generated in the application by `newId()` before insert, so a row's ID is known before it is written | S — OQ-1.2-3 |
| C3 | ID meaning | IDs are opaque. Code never uses ID order for correctness: UUIDv7 is generated on two VMs whose clocks can differ. Order by explicit timestamps | S — OQ-1.2-3 |
| C4 | Table and column names | `snake_case`, singular, matching the entity name (`product_version`). Foreign keys are `<referenced_table>_id`. F-23's `section_search` keeps its decided name | S — OQ-1.2-5 |
| C5 | Enums | `text` + `CHECK (col IN (...))`, not native Postgres enums, so values can be added in a plain migration. Values keep the spelling of the doc that decided them (e.g. `WEBSITE`, `PENDING`, `unpublished`, `needs_review`); new values are lowercase `snake_case` | S — OQ-1.2-5 |
| C6 | Row timestamps | `created_at timestamptz NOT NULL DEFAULT now()` on every table. Mutable tables add `updated_at timestamptz NOT NULL`, maintained by one shared trigger. Append-only tables (raw evidence registry, ledgers) have no `updated_at`. All times UTC | `created_at` D (doc 12 §5 Source, RawArtifact; F-23); type/trigger S — OQ-1.2-6 |
| C7 | Domain timestamps | Domain times are separate columns named `<event>_at` (`captured_at`, decided on ProductVersion, §28). They are never replaced by `created_at` | D (§28) for `captured_at`; naming S — OQ-1.2-6 |
| C8 | Deletion | No `deleted_at` soft-delete column. User-visible hiding is `publish_status = withdrawn` (DC-06). Physical removal is a hard delete done by the takedown purge, children first | S — OQ-1.2-7 |
| C9 | FK delete behaviour | `ON DELETE RESTRICT` on every FK. No cascades, so a mistaken delete cannot wipe a subtree | S — OQ-1.2-8 |
| C10 | Polymorphic references | `(entity_type text, entity_id uuid)`, as F-23 fixes for `Embedding` and `Classification`. `entity_type` must be a value from §3.4. Indexed on `(entity_type, entity_id)` | Shape D (F-23); value set S — OQ-1.2-5 |
| C11 | JSONB | Only where a decision names it: `design_tokens` (F-21), `Classification.evidence` and `section_search.filters` (F-23), per-domain policy on `Source` (F-21). Anything filtered or joined on is a real column | JSONB uses D; restriction S — OQ-1.2-5 |
| C12 | Heavy files | Never stored in Postgres (no image/video `bytea`); rows hold references to `raw_artifact`/`derived_artifact` (1.3) | D (doc 02 §3, §3 "do not put videos or screenshots in Postgres") |
| C13 | Provenance | Provenance is held by reference: every design-graph row reaches its capture through FKs (§3.5 map). Denormalized provenance columns are only added if 1.6 decides so | S — OQ-1.2-15 |
| C14 | Text | `text`, not `varchar(n)`. Length limits are CHECK constraints when needed | S — OQ-1.2-5 |

### 3.5 Relationships and provenance map

```
source (1.5) ─1:1(V0)─ product ─< product_version ─< screen >─ page >─ product
                                                       │  └── device_profile
                                                       │  └── capture_unit (1.4) ─> capture_job ─> crawl_run
                                                       ├─< screen_artifact ─> raw_artifact | derived_artifact (1.3)
                                                       ├─< section ─< section_artifact ─> raw/derived_artifact
                                                       │      ├─< asset (section_id, optional)
                                                       │      └─< animation (section_id, optional)
                                                       ├─< asset ─> raw_artifact
                                                       └─< animation ─< animation_artifact ;  animation ─> asset (optional)
```

### 3.6 Migrations

| Rule | Status |
|---|---|
| One global, ordered, forward-only migration sequence in the database package; every Part adds its tables and columns through it | S — OQ-1.2-2 |
| A migration may only reference tables created by earlier migrations | S — OQ-1.2-2 |
| An applied migration is never edited; fixes are new migrations | S — OQ-1.2-2 |

## 4. API Surface

**No HTTP endpoints, no BullMQ jobs, no events.** 1.2 has no runtime process of its own. F-24 forbids `/internal/*` endpoints. Events are emitted by the Parts that write rows, using 1.4's envelope.

### 4.1 Module contracts (database package; names S — OQ-1.2-2)

| Contract | Input | Output | Errors | Idempotency | Callers |
|---|---|---|---|---|---|
| `getDb()` | Connection config from 1.1 | Pooled client | Connection error (thrown) | — | all |
| `withTransaction(fn)` | Callback | Callback result; commit or full rollback | Re-throws callback error after rollback | — | all writers |
| `newId()` | — | UUIDv7 string | — | — | all inserts (C2) |
| Typed row definitions | — | Types for owned tables | — | — | all |
| `upsertProduct({sourceId, name})` | Source id | `product.id` | `ReferenceMissing` if source absent | On `source_id` (V0 unique) | 3.2 |
| `upsertPage({productId, canonicalUrl})` | Canonical URL from 2.1 | `page.id` | `ReferenceMissing` | On `(product_id, canonical_url)` | 3.2 |
| `insertProductVersion({productId, platform, capturedAt, captureJobId, version?, releaseIdentifier?})` | — | `product_version.id` | `ReferenceMissing` | On `(product_id, capture_job_id)` (OQ-1.2-27) | 3.4 |
| `recordScreenGraph({captureUnitId, pageId, productVersionId, deviceProfileId, capturedAt, title, artifacts[], sections[], assets[], animations[]})` | One unit's normalized output | IDs of all rows | `ReferenceMissing` (artifact/unit/page not yet registered) | On `capture_unit_id`; sections by `(screen_id, order_index)`; assets/animations by OQ-1.2-13/20 keys. Runs in the caller's transaction so 1.4's lease-conditional commit (doc 22 §5) and the graph write are atomic. (wave-3 review) 2.10's `applyGateToGraph(tx, …)` is called by 3.2 inside this same transaction, after the rows exist | 3.2 |
| `setPublishStatus({entityType: 'screen' or 'section', ids, expectedFrom, to})` | — | Count updated | `StaleStatus` when the current value differs from `expectedFrom` | Re-applying the same transition is a no-op | 2.10, 6.4 |
| `appendAnimationArtifacts({captureUnitId, links: [{animationItemKey, role, rawArtifactId?, derivedArtifactId?}]})` (wave-3 review) **(P)** | Links for posters and normalized videos finished after normalization | Count appended | `ReferenceMissing` (no `animation` with that `item_key` for the unit's screen, or the artifact is not registered) | Unique `(animation_id, role)`: an existing link is left unchanged and counted as existing | 3.2 (on 2.4's event `capture_unit.media_derived`, OQ-2.4-13) |
| `listSourceDependents(sourceId)` | Source id | IDs per table (product … animation, artifact links) plus `(entity_type, entity_id)` pairs for polymorphic consumers | — | Read-only | 6.4 / 1.5 takedown (F-18) |

## 5. Business Rules & Edge Cases

### 5.1 Rules

| # | Rule | Source |
|---|---|---|
| R1 | Every table's primary key is a UUIDv7 `id`. No other ID formats, including in other Parts' tables (see OQ-1.2-4 for `capture_unit`) | F-23 |
| R2 | Relationships are foreign keys or indexed link tables. Polymorphic `(entity_type, entity_id)` is used only by F-23's tables and by other Parts' cross-entity tables, always with §3.4 values | F-26, F-23 |
| R3 | No image, video or other heavy file is stored in Postgres | doc 02 §3 |
| R4 | Write order is blob → registry row (1.3) → design-graph row. FKs enforce it. A crash between steps leaves only an orphan blob, which 1.3's GC removes | doc 22 §4, §9 |
| R5 | Every write to an owned table is keyed by a natural key (§3.3, §4.1). Re-running normalization for the same unit gives the same rows and the same IDs | DC-02, F-24 |
| R6 | History is never overwritten. A new crawl creates new `screen` rows; an existing screen is never re-pointed to another unit, page or version | MB§40, doc 11 |
| R7 | `publish_status` defaults to `unpublished`. Only `published` rows may be returned by user-facing reads (5.1, 6.x). 1.2 never chooses a status | DC-06 |
| R8 | Decided `publish_status` transitions: `unpublished → eligible → published`; any → `withdrawn`. (wave-3 review) **(P)** also `eligible → unpublished` and `published → unpublished`, written only through `setPublishStatus` by 2.10 or 6.4 and logged (spot-check drop and demotion, OQ-2.10-26); `withdrawn` stays takedown-only. Other transitions are OQ-1.2-18 | doc 22 §4 / §8 |
| R9 | Takedown first sets `withdrawn` on every screen and section under the source (instant hide). The purge then removes rows children-first via `purgeEntities`, including polymorphic dependents in 3.1, 4.3, 4.5, 5.1 and 6.5 tables. Raw-evidence handling follows 8.2 (A-21). Deadline 48 h | F-18, doc 15 |
| R10 | Design-graph rows are derived and rebuildable from raw evidence by re-running 3.2. A rebuild keeps IDs stable through R5 so classifications, embeddings and (V1) collections stay attached | doc 04, §6 |
| R11 | V0 rows are web only: `product_version.platform = 'web'`, `screen.page_id` NOT NULL, `logged_out` state only | F-02, F-17 |
| R12 | Schema changes happen only through migrations (§3.6). No manual DDL on production | S — OQ-1.2-2 |
| R13 | No cascading deletes (C9). Deletes are explicit and ordered | S — OQ-1.2-8 |
| R14 | JSONB only where a decision names it (C11) | F-21, F-23 |
| R15 | Assets and animations have no public visibility in V0. Only screenshots are displayed | F-18 |

### 5.2 Edge cases

| Case | Detection | Automatic response | Human? |
|---|---|---|---|
| Normalization job delivered twice (at-least-once) | Unique natural key conflict | Upsert returns the existing row; no duplicate | No |
| Zombie worker writes after losing its lease (doc 22 row 4) | 1.4's `lease_id` condition in the same transaction | Transaction aborts; nothing from the zombie is committed | No |
| Worker or Chromium dies mid-write (doc 22 rows 3–4) | Uncommitted transaction | Postgres rolls back; 1.4 requeues the unit | No |
| Artifact not yet registered when graph row is written (doc 22 row 16, upload spooled) | FK violation → `ReferenceMissing` | Caller fails the job; retry per F-32 after the spool upload completes | No |
| Redis wiped (DC-14) | 1.4 reconciler | Postgres unaffected; queue rebuilt from unit rows | No |
| Migration fails | Runner exits non-zero; transaction rolled back | Deploy stops; previous code keeps running | Yes — fix the migration |
| Worker on the Crawler VM runs an older or newer build than the schema | Startup schema-version check (OQ-1.2-24) | Process refuses to start and reports to Sentry (1.8) | Yes, if it persists |
| Postgres unavailable (App VM restart or crash) | Connection errors in all callers | Jobs fail and retry per F-32; supervisor stops leasing because unit state cannot be written (2.9); web returns errors | Yes, if longer than RTO 1 day (F-35) |
| Data loss / corruption | 1.7 backup monitoring | Restore nightly `pg_dump` (RPO 24 h); run `db verify`; 1.3 GC removes blobs no longer referenced | Yes |
| pgvector missing or wrong version after a restore or image change | Migration 0001 / restore test fails | Fail fast; no partial schema | Yes |
| Database grows toward 50 GB | 1.8 size metric | Alert; F-35 §5 scale step (bigger VM, then separate Postgres) | Yes |
| Clock skew between App VM and Crawler VM | Not detected | Harmless by C3: nothing relies on ID order | No |
| Desktop and mobile units of the same URL insert the page at the same time | Unique `(product_id, canonical_url)` | `ON CONFLICT` → one page row | No |
| Canonical URL longer than the btree entry limit | Insert error | Avoided by indexing a hash of the URL (OQ-1.2-26) | No |
| Re-normalization yields a different number or order of sections | Natural-key mismatch on `(screen_id, order_index)` | OQ-1.2-20 (suggested: delete stale sections and their polymorphic dependents in the same transaction; 4.3/4.5 re-run) | No |
| Polymorphic rows left pointing at deleted entities | `db verify` | Report; purge them (R9) | Optional |
| S3 non-browser fallback unit (`no_visual`, doc 22 §7) | Unit flag (1.4) | Whether 3.2 creates a `screen` without images is 3.2's decision; schema permits a screen with no `full_page` artifact | No |

**Doc 22 failure-mode catalog:** rows 3, 4 and 16 are covered above. Rows 1–2 and 5–15 belong to 2.x/4.x. Rows 17–20 belong to 2.11/1.6/1.8. DC-16 capture hazards do not apply: this Part does no capture.

## 8. Open Questions & Assumptions

### Open questions

- **OPEN QUESTION OQ-1.2-1:** Which PostgreSQL major version and pgvector version? — Every migration and the backup format depend on it. PostgreSQL 18+ adds a native `uuidv7()`. — *Suggested default (not a decision):* the newest PostgreSQL major supported by the official pgvector Docker image at build time, pinned by exact image tag. Upgrades are tested with a restore first.
- **OPEN QUESTION OQ-1.2-2:** Which migration tool, and are the migration rules in §3.6 and the contract/CLI names in §4 adopted? — Every Part's schema work goes through it. — *Suggested default:* plain, numbered, forward-only SQL files applied by a small runner in the database package, which records applied versions in a migrations table. TypeScript row types are written next to them. Adopt §3.6 as written.
- **OPEN QUESTION OQ-1.2-3:** Where are UUIDv7s generated, and is "never order by ID" (C3) adopted? — Writers on two VMs need IDs before insert (R4, R5). — *Suggested default:* `newId()` in the application for every insert. A DB-side default is a fallback only if OQ-1.2-1 lands on a version with native `uuidv7()`.
- **OPEN QUESTION OQ-1.2-4:** Doc 22 §4 sets `unit_id = hash(canonical_url, viewport_profile, crawl_run_id)`, but F-23 says all IDs are UUIDv7. Which one wins for `capture_unit`? — `screen.capture_unit_id` and 1.4's idempotency depend on it. Owned by 1.4. — *Suggested default:* `id` is UUIDv7, and idempotency comes from a unique natural key `(crawl_run_id, canonical_url, device_profile_id)` on `capture_unit`.
- **OPEN QUESTION OQ-1.2-5:** Naming, enum representation, `entity_type` spelling and the JSONB restriction (C4, C5, C10, C11, C14). — Cross-Part consistency. — *Suggested default:* as written in §3.2 and §3.4.
- **OPEN QUESTION OQ-1.2-6:** Timestamp convention (C6, C7). — Every table. — *Suggested default:* `timestamptz` in UTC; `created_at DEFAULT now()`; `updated_at` only on mutable tables, maintained by one shared trigger; domain times as `<event>_at`.
- **OPEN QUESTION OQ-1.2-7:** Soft delete? — Affects takedown, rebuilds and every query. — *Suggested default:* no `deleted_at`. `publish_status = withdrawn` hides rows. Physical removal is a hard purge in dependency order, with retention of raw evidence and backups set by 8.2 (A-21).
- **OPEN QUESTION OQ-1.2-8:** FK `ON DELETE` behaviour. — Safety of purges. — *Suggested default:* `RESTRICT` everywhere; purges delete children first.
- **OPEN QUESTION OQ-1.2-9:** How do Page, Screen and Section map for web? — This is the core shape of the graph and is not decided in docs 05/12. — *Suggested default:* `page` = URL identity within a product, shared across versions. `screen` = page × device profile × capture unit, linked to its `product_version`, unique per `capture_unit_id`, carrying `title`. `section` belongs to a screen. Mobile screens (V2) have no page.
- **OPEN QUESTION OQ-1.2-10:** What is the cardinality between Product and Source, and what about multi-platform products later? — V2 products span web, iOS and Android sources (doc 05). — *Suggested default:* in V0, `product.source_id` is unique (1:1), and `product.name` is copied from `source.name` and editable. Revisit at G5.
- **OPEN QUESTION OQ-1.2-11:** Should `Platform` (§4 entity) be a table or an enum, and is `device_profile` a table with `code` values `desktop`/`mobile`/`tablet`? — 1.4's `capture_unit` and 2.2 reference profiles. — *Suggested default:* `platform` = text CHECK `('web','ios','android')`; `device_profile` = table seeded with the V0 rows.
- **OPEN QUESTION OQ-1.2-12:** How are design-graph rows linked to artifacts, and is a section crop a raw or a derived artifact? — Decides the link tables and what 1.3 registers. — *Suggested default:* per-entity link tables (`screen_artifact`, `section_artifact`, `animation_artifact`) with `role`, `capture_pass`, `seq`/`is_selected`, and exactly one of raw/derived. Whether a crop is raw or derived is for 1.3/2.3; the tables allow both.
- **OPEN QUESTION OQ-1.2-13:** Asset granularity and doc 12's `Asset.storage_key`. — Deduplication and the asset natural key for R5. — *Suggested default:* one `asset` row per occurrence per screen, physical dedupe via CAS (1.3), `raw_artifact_id` instead of a duplicated `storage_key`, natural key `(screen_id, coalesce(hash, source_url), section_id)`. (wave-3 review) Superseded for `asset` and `animation` by the (P) column `item_key`, unique with `screen_id` (OQ-2.4-10); the hash-based key above is kept only as a fallback if 2.4 gives no `media_item_id`.
- **OPEN QUESTION OQ-1.2-14:** What are the value sets for `asset.type`, `animation.type`, `animation.trigger`, and the time unit for durations? — The CHECK constraints need them. Owned by 2.4. — *Suggested default:* candidates from doc 08. `asset.type`: `image, svg, video, animated_image, lottie, canvas`. `animation.type`: `css_animation, css_transition, lottie, animated_svg, animated_image, video, webgl_animation, js_library`. `trigger`: `load, scroll, hover, interaction`. Durations in milliseconds. (wave-3 review) (P) additions from 2.4: `asset.type` `embed`, `other`; `animation.type` `unknown_motion` (OQ-2.4-11).
- **OPEN QUESTION OQ-1.2-15:** Is provenance held by reference (§3.5) or as denormalized columns per GAP§1, and where does the data class live? — Shared with 1.6. — *Suggested default:* by reference. Data class is implied by table plus `classification.status`. 1.6 adds columns only if a query needs them.
- **OPEN QUESTION OQ-1.2-16:** Should base tables carry denormalized current labels (`section_type`, `page_type`)? — Convenience vs. one source of truth (F-23). Note: F-10's page-type list (with `legal`) and F-27's (with `docs`, `login`, `signup`) differ; that belongs to 2.1/4.3. — *Suggested default:* no label columns. Labels are read from `classification` (4.3) or `section_search` (5.1).
- **OPEN QUESTION OQ-1.2-17:** Which entities carry `publish_status`? — Public visibility rules. A V1 animation viewer (6.6) may conflict with F-18's "no hosting of third-party source assets". — *Suggested default:* only `screen` and `section` in V0. A page or product is visible if it has at least one published screen. Assets and animations are never public in V0. Raise the 6.6 conflict with counsel (E5).
- **OPEN QUESTION OQ-1.2-18:** Which `publish_status` transitions exist beyond R8 (re-review demotion, reversing a withdrawal)? — Owned by 2.10/6.4. — *Suggested default:* `published → unpublished` allowed on re-review; `withdrawn` reversed only by an explicit, logged admin action. (wave-3 review) (P) In V0 2.10 also needs `eligible → unpublished` (a bad item dropped from a batch); both are in R8.
- **OPEN QUESTION OQ-1.2-19:** Where do gate results live before and after normalization (unit-level vs. screen-level `quality_score`; per-section outcomes before section rows exist)? — Shared by 1.4, 2.10 and 3.2. — *Suggested default:* the unit-level score and outcome live on `capture_unit` (1.4) and are copied to `screen.quality_score` at normalization. Section-level results are written onto `section` when 3.2 creates it. (wave-3 review) **Resolved by 2.10 §3.1 (adopted as (P)):** the gate's source of truth is 2.10's own tables (`gate_result`, `gate_check_result`, `gate_section_result`), not `capture_unit`; graph `quality_score` columns are write-once copies made at normalization by `applyGateToGraph`. The answer above (unit-level score on `capture_unit`) is withdrawn.
- **OPEN QUESTION OQ-1.2-20:** How does re-normalization handle changed section count or order (ID stability)? — Classifications and embeddings hang off section IDs. — *Suggested default:* match on `(screen_id, order_index)`. Sections that no longer exist are deleted, with their polymorphic dependents, in the same transaction, and 4.3/4.5 re-run for changed sections.
- **OPEN QUESTION OQ-1.2-21:** When and how are `screen_state`, `component`, `interaction` and `flow*` created? — Forward compatibility without pre-building (rule 3). — *Suggested default:* the first consuming Part's migration creates each table (2.7 / 4.9 in V1; 7.6 / 7.8 in V2) using §3.7's decided fields. `section` gains a nullable `screen_state_id` in V1.
- **OPEN QUESTION OQ-1.2-22:** Which database roles exist, and how does the Crawler VM connect? — Credential boundary (F-20, §52). — *Suggested default:* three roles: `migrator` (DDL, CI/deploy only), `web` (reads plus admin writes), `worker` (DML on the tables it writes). The Crawler VM reaches Postgres over a private network or TLS (details in 1.7).
- **OPEN QUESTION OQ-1.2-23:** What pool size per process, and is an external pooler needed? — Avoids exhausting connections. — *Suggested default [Estimate]:* ≤ 10 connections per process and no pooler until connection count becomes a measured problem.
- **OPEN QUESTION OQ-1.2-24:** Is a startup schema-version check adopted, and are migrations a deploy step? — Prevents a stale Crawler VM build writing to a newer schema. — *Suggested default:* migrations run before new code starts. A process refuses to start if the database is behind the latest migration its build expects.
- **OPEN QUESTION OQ-1.2-25:** How are bounds stored (units, coordinate origin, columns vs. JSONB), and what values does `section.detection_method` take? — Region features (GAP§20) and crops (DC-21). — *Suggested default:* four `numeric` columns in CSS px, relative to the full-page top-left. Device px = × `device_scale_factor`. `detection_method ∈ {dom, layout_block, visual}`.
- **OPEN QUESTION OQ-1.2-26:** How is uniqueness enforced on long canonical URLs? — Btree entries have a size limit. — *Suggested default:* unique index on `(product_id, sha256(canonical_url))`, with the full URL kept in `canonical_url`.
- **OPEN QUESTION OQ-1.2-27:** How is a web `ProductVersion` labelled, and is it tied to a crawl job? — Owned by 3.4. — *Suggested default:* `version` and `release_identifier` NULL for web (identified by `captured_at`); `capture_job_id` set; unique `(product_id, capture_job_id)`.
