## 1. Purpose & Scope

**Purpose.** Give the project one repository, three deployables, repeatable environments, one way of loading configuration and secrets, a CI pipeline that blocks unsafe changes, and the two-VM Docker Compose deployment. Every other Part builds on this one. It is meant to stay "boring" (IF§2, MB§71) and cheap enough for a solo founder to run (doc 20 §0).

**Phase:** `[V0]`. Later phases add nothing here except the forward-compatibility hooks marked **[hook]**.

## 4. API Surface

**HTTP:** none owned by this Part. No `/internal/*` endpoints (F-24). A container health check for `web` is OPEN QUESTION OQ-1.1-18 (suggested: an in-container command, or one public `GET` route owned by 6.1).

**Events / BullMQ jobs:** none emitted or consumed. 1.1 requires one property of 1.4's job catalog: **each job type declares its placement** (`app` or `crawler`), and each worker role consumes only queues of its placement (needed so the Crawler VM can be off without App VM workers picking up browser jobs, and so target-site traffic stays on the Crawler VM — OQ-1.1-11).

### 4.1 Module contract: `packages/config` (P)

```ts
// sketch only — names (P)
loadConfig(role: ProcessRole): Readonly<Config>
  // reads env vars for this role's schema; applies typed defaults for limits
  // throws ConfigError listing EVERY missing/invalid key by NAME (never by value)
redactedConfig(cfg): Record<string, string>   // secrets replaced by "***"; safe to log and to show in /admin
```

| Property | Rule |
|---|---|
| When | Called once at process start, before connecting to anything |
| Failure | Invalid config → log the key names to stdout → exit non-zero → Compose restart policy retries; the crash loop is visible to 1.8 |
| Immutability | Config is frozen after load; changing it means restarting the process |
| Scope | A role's schema includes only the variables that role needs; an unexpected secret for that role (per §3.5) is a startup error in `production` |
| Secrets | Never logged, never sent to Sentry, never returned by any API |

### 4.2 Process contract (all long-running roles)

| Signal / event | Required behaviour |
|---|---|
| Start | `loadConfig` → connect → become healthy; `worker-app`/`supervisor` startup triggers 1.4's reconciler run (DC-14) |
| `SIGTERM` | Stop taking new jobs/units; finish or release current work within the Compose `stop_grace_period`; exit 0. **For `supervisor`, the reconciled behaviour is 2.9 §5.9** (running attempts continue until the earlier of their attempt deadline and grace − 10 s, then the child is killed and the unit released with `releaseLease(shutdown)`, 1.4 T13; OQ-2.9-32) (wave-2 review) |
| Grace period | `supervisor`: ≥ unit deadline (90 s, doc 22 §5) plus margin [Estimate: 100 s]; others: [Estimate: 30 s] |
| Not finished in time | Killed by Docker; unfinished units are recovered by lease expiry and requeue (DC-03, DC-14) — no data loss by design |

| `build` | Build all workspace packages and apps | CI `build-images` |

### 4.4 Operator CLI

F-24 says operators use the admin UI or a CLI that enqueues jobs. 1.1 provides only the **entry mechanism**: the `cli` role of the `worker` image, run as a one-off container on either VM (e.g. `docker compose run --rm worker-app cli <command>` (P)). Each command (crawl a source, retry failed units, remove source, …) is defined by the Part that owns the behaviour. CLI commands enqueue jobs; they never call HTTP endpoints on the other VM.

### 4.5 Deploy procedure (contract)

```
deploy(vm, sha):                                  # script in infrastructure/scripts (P); trigger: OQ-1.1-7
  1. require: CI passed for sha on main; images web:sha / worker:sha exist in registry
  2. require (worker changes to capture runtime or Playwright/Chromium pin): torture-suite passed;
     golden-canary passed for this sha                                         # DC-12, doc 22 §13
  3. on App VM only: run 1.2's migration command once (one-off container from worker:sha)
     → on failure: STOP; running containers keep running the old sha
  4. pull images; `docker compose up -d` with the new sha
  5. wait for health checks (OQ-1.1-18); on failure → redeploy previous sha (rollback)
  6. prune old images, keeping the previous sha for rollback
rollback(vm) = deploy(vm, previous_sha)            # requires migrations compatible with previous release (OQ-1.1-22)
```

Auth: deploy credentials (SSH key, registry token) live only on the machine or CI that deploys (OQ-1.1-7); they are never placed in an App VM or Crawler VM service's environment.

## 7. Non-Functional Notes

### Performance and capacity

| Item | Value | Label / basis |

| VM sizes | Not decided | OQ-1.1-20 |
| Scale steps | Bigger App VM → separate Postgres → managed Postgres; second Crawler VM when crawl queue wait > 24 h; orchestration only at ≥ 3 always-on VMs | [Decision] doc 20 §5 |

### Reliability

- Deploys and restarts lose no capture work: Postgres holds unit state, leases expire and requeue (DC-03, DC-14).
- Redis persistence is optional for correctness (DC-14).
- Backups (nightly `pg_dump` + R2 versioning, RPO 24 h, RTO 1 day, restore test before launch) run in the `backup` slot; content owned by 1.7 (F-35).
- Rollback = redeploy the previous image SHA (§4.5).

### Security and privacy

- Two hosts = the §52 boundary: browsers and any site credentials only on the Crawler VM; the App VM holds the database and end-user auth (F-35).
- Network path between the VMs: OQ-1.1-10 (wave-2 review: before launch there is no second machine; after launch the crawler machine is the founder's computer reaching the online database over an authenticated, encrypted connection, 2.9 OQ-2.9-40; the capture container also shares a network and disk with the founder's own files, so restricted egress must block the home network and loopback, 2.9 R35, OQ-2.9-41). Capture containers run with 1.7's sandbox profile; F-20 requires restricted egress, which by default also blocks private ranges (so a capture container cannot reach the App VM).
- Secrets: host environment / secret store (F-20); exact form OQ-1.1-9; scoping per §3.5; leak checks in CI.
- Encryption at rest: provider defaults (F-20).

### Cost recording

1.1 creates no `CostEvent`s. Fixed costs it introduces (two VMs, registry, CI minutes) are inputs to 1.6's ledger and must fit F-07's $200/month cap with AI spend. The Crawler VM running only for batches (on-demand, F-35) was the main cost lever (wave-2 review: superseded by F-45; the crawler machine is the founder's own computer, so there is no crawler-VM bill and no on-demand lever).
