## 1. Purpose & Scope

**Purpose.** 1.4 is the part of the system that makes sure collection **never gets stuck**. It defines the unit of work, its state machine, how a unit is leased and kept alive, how lost work is found again, how domains share the browser slots fairly, what happens when an attempt fails, and how one stage tells the next stage that something happened. Postgres holds every unit's state. Redis/BullMQ is only a queue that can be rebuilt from Postgres (DC-14).

**Phase:** `[V0]`. Later-phase hooks are marked **[hook]**.

## 3. Data Model

**Conventions.** Table names are snake_case singular (P), subject to 1.2's naming convention. All ids are `uuid` UUIDv7 (F-23). All times are `timestamptz`. Enum representation (Postgres enum or `text` + `CHECK`) follows 1.2. **Every lease and deadline comparison uses the database clock**, never a worker's clock [Assumption]. 1.4 writes its own migrations with 1.2's tool.

### 3.1 Hierarchy

```
crawl_run (batch, e.g. "initial 500 sites")                         doc 22 §4
  └─ capture_job (one site; Blueprint §7 statuses; deadline 30 min) DC-13
       ├─ capture_session (one browser process run; ≤ 50 units / 30 min)  F-21, DC-07
       └─ capture_unit (canonical URL × viewport profile × crawl run)     DC-02
            └─ capture_attempt (one try with one strategy rung; ≤ 90 s)   doc 22 §4–§5
```

The `capture_unit` rows **are** the URL-level checkpoint (F-32, §51): pending, completed and failed URLs are unit states. Discovered-but-not-planned URLs are 2.1's.

### 3.8 Unit state machine

**Terminal states:** `ACCEPTED, NEEDS_REVIEW, QUARANTINED, BLOCKED, SKIPPED` (doc 22 §4 roll-up). `REJECTED` is transient: it is entered and left in the same transaction. Terminal states can be left only by the human-driven transitions T22–T24.

**Ladder.** Attempt *n* uses `next_strategy`; the default sequence is attempt 1 = `S0`, 2 = `S1`, 3 = `S2`, 4 = `S3` (doc 22 §7, DC-05). A manual retry may start at a chosen rung (doc 22 §10). After attempt 4 (or after `S3`, whichever comes first) the ladder is exhausted.

**Backoff** `backoff(n)` before attempt *n+1*: n=1 → **30 s**, n=2 → **5 min** (F-32); n=3 (before the `S3` fallback) → OQ-1.4-4 (suggested 5 min).

| # | From | To | Trigger (function, caller) | Guard | Side effects |
|---|---|---|---|---|---|
| T1 | — | `PENDING` | `createUnits` (2.1) | `unit_key` new | `dispatch_seq=1`, `pending_since=now`; dispatch entry added |
| T2 | — | `SKIPPED` | `createUnits` with `skip_reason` (2.1) | `unit_key` new | `reason_code` = robots/policy/budget; `capture_unit.finalized` |
| T3 | `PENDING` | `LEASED` | `leaseNextUnit` (scheduler, run by 2.9) | §5.3 eligibility; `lease_count < max` | new `lease_id`; `lease_owner`; `leased_at=last_leased_at=now`; `lease_expires_at=now+60 s`; `lease_count+1`; `pending_since=null` |
| T4 | `LEASED` | `RUNNING` | `startAttempt` (2.9) | lease matches and not expired; `attempt_no < 4` | `attempt_no+1`; insert `capture_attempt` (`strategy=next_strategy`); `attempt_deadline_at=now+90 s`; `heartbeat_at=now`; `lease_expires_at=now+60 s` |
| T5 | `LEASED` | `PENDING` | `expireLease` (2.9 sweeper / reconciler) or `releaseLease` (2.9) | lease expired, or holder releases | lease cleared; **no attempt used** (OQ-1.4-5); `dispatch_seq+1`; dispatch entry added |
| T5b | `LEASED` | `QUARANTINED` | as T5 | `lease_count ≥ max` (OQ-1.4-6) | `reason_code=LEASE_LIMIT`; `finalized` |
| T5c | `LEASED` | `PENDING` | `releaseLease(cause=host_unavailable)` (2.9) (P, wave-2 review) | lease matches (also after expiry while `lease_id` is still current) | as T5, plus `lease_count-1` (this lease is not counted); `reason_detail.cause = host_unavailable`; **no attempt used** |

| T6b | `LEASED` | `LEASED` | `heartbeat` (2.9 supervisor itself, no child step) (P, wave-2 review) | lease matches and not expired; `now < leased_at + LIMIT_LEASED_MAX_S` | `lease_expires_at=now+60 s`; `heartbeat_at` and `heartbeat_step` stay null (C2); the attempt clock has not started (OQ-2.9-9) |

| T15 | `VALIDATING` | `ACCEPTED` / `NEEDS_REVIEW` | `recordValidation` (2.10) | `attemptId` = `result_attempt_id` (applies to T15–T19) | attempt `verdict`; `finalized` |
| T16 | `VALIDATING` | `REJECTED` → `RETRY_WAIT` | `recordValidation(REJECTED)` | ladder not exhausted | as T8 (next rung, backoff) |
| T17 | `VALIDATING` | `REJECTED` → `QUARANTINED` | `recordValidation(REJECTED)` | ladder exhausted | `LADDER_EXHAUSTED`; evidence kept (S3 output is evidence only, doc 22 §7); `finalized` |

Every transition: increments `state_version`, sets `state_changed_at`, and runs in one Postgres transaction together with its event-log insert (§4.4). Any call whose guard fails returns `IllegalTransition` or `LeaseLost` and changes nothing.

**Worst-case time in `RUNNING` for one attempt:** 90 s deadline + 60 s lease timeout = 150 s, even if the supervisor's own kill fails, because `heartbeat` stops extending the lease once `attempt_deadline_at` has passed (rule R6).

## 4. API Surface

**No HTTP endpoints.** F-24 forbids `/internal/*` endpoints; operators use the admin UI (6.4) or the CLI (1.1 entry mechanism), which call the module functions below and enqueue jobs. All contracts are TypeScript module functions in a 1.4 module **(P name: `services/work-queue`)**; job names and payload schemas live in `packages/schemas` (F-24). 1.4 does **not** ask for `packages/events`.

**Common rules for every function:**

| Rule | Detail |
|---|---|
| Auth | In-process calls under the deployable's DB role (1.7). Calls that originate from a human carry `actor` and are recorded in `reason_detail` |
| Errors | `LeaseLost` (lease id no longer current or expired), `IllegalTransition{from,to}`, `NotFound`, `DeadlineExceeded` (heartbeat only), `JobNotOpen` (`createUnits` only; wave-2 review). Infrastructure errors (DB/Redis down) are thrown unchanged; the caller retries with backoff |
| Transactions | Each call is one Postgres transaction; event-log rows are written inside it; BullMQ enqueue happens **after** commit (§4.4) |
| Idempotency | Stated per function |

### 4.1 Lease and attempt contracts (callers: 2.9 supervisor)

```ts
type Lease = {
  unitId: UUID; leaseId: UUID; leaseOwner: string;
  crawlRunId: UUID; jobId: UUID; sourceId: UUID; domainKey: string;
  canonicalUrl: string;
  deviceProfile: { code: string; viewport_width: number; viewport_height: number; device_scale_factor: number };  // (P, wave-2 review) values of the unit's device_profile row (1.2); OQ-2.2-11
  attemptNo: number /* the attempt startAttempt will create */;
  strategy: 'S0'|'S1'|'S2'|'S3'; leaseExpiresAt: Date;
};

leaseNextUnit(input: { leaseOwner: string; captureJobId?: UUID }): Promise<Lease | null>
startAttempt(input: { unitId; leaseId; captureSessionId?: UUID }): Promise<{ attemptId: UUID; attemptNo; strategy; deadlineAt: Date }>
heartbeat(input: { unitId; leaseId; step?: CaptureStep }): Promise<{ leaseExpiresAt: Date }>   // throws LeaseLost | DeadlineExceeded; (wave-2 review) valid in LEASED (no step) and RUNNING (step)
withLease<T>(input: { unitId; leaseId }, fn: (tx) => Promise<T>): Promise<T>               // throws LeaseLost
completeAttempt(input: {
  unitId; leaseId;
  outcome: 'captured'|'failed'|'blocked'|'skipped';
  reasonCode?: string; reasonDetail?: object; flags?: string[]; fingerprint?: string;
}, tx?): Promise<{ state: UnitState }>
expireLease(input: { unitId; leaseId; cause: 'heartbeat_lost'|'deadline_exceeded'; reasonDetail?: object /* (P, wave-2 review) */ }): Promise<{ state; killChild: boolean }>
releaseLease(input: { unitId; leaseId; cause: 'shutdown'|'unused'|'host_unavailable' /* (P, wave-2 review) */ }): Promise<{ state }>
```

| Function | Behaviour | Idempotency / errors |
|---|---|---|
| `leaseNextUnit` | Runs the fair scheduler (§5.3) and performs T21+T3 or T3. (wave-2 review) The returned `Lease` carries the device profile's `code`, `viewport_width`, `viewport_height` and `device_scale_factor`, not just a code, so the child never needs a second lookup and never hard-codes DPR (DC-20); `createUnits` still takes the profile code (field name `viewportProfile`, unchanged to avoid touching 2.1's calls). `captureJobId` limits selection to one job (used when a session is scoped to a job, F-21). Returns `null` when nothing is eligible, with the reason logged (`intake_held`, `no_eligible_domain`, …) | Two concurrent callers never get the same unit (conditional `UPDATE … WHERE state='PENDING'`) |
| `startAttempt` | T4 | Repeating with the same lease after success returns the same attempt (no second row) |
| `heartbeat` | T6. Called by the supervisor every **10 s** with the child's current step (DC-03). After `attempt_deadline_at` it throws `DeadlineExceeded` and does **not** extend the lease. (wave-2 review) **(P)** Also allowed in `LEASED` (T6b), without a step, so the supervisor can pace (`paceDomain` wait) and spawn a child within the 60 s TTL; extension in `LEASED` is capped at `leased_at + LIMIT_LEASED_MAX_S` (DC-01; OQ-2.9-9) | Safe to repeat |
| `withLease` | Opens a transaction, locks the unit row `FOR UPDATE`, checks `lease_id` and `lease_expires_at > now()`, runs `fn(tx)`. Used to register artifacts (1.3) and complete the attempt in **one** commit, so a zombie that lost its lease cannot write anything (doc 22 §5) | Throws `LeaseLost` and rolls back |
| `completeAttempt` | T7–T12. Releases the lease explicitly (doc 22 §5). May be called inside `withLease` | Second call with the same (now cleared) lease → `LeaseLost`; caller treats it as done |
| `expireLease` | T5/T5b/T8/T9 by cause. Used by 2.9's lease sweeper (30 s, doc 22 §9), 2.9's deadline kill, 2.5's janitor (unit past hard deadline) and the reconciler. `killChild=true` tells 2.9 to kill the owning child | Conditional on the passed `leaseId`; a stale call is a no-op returning the current state. (wave-2 review) **(P)** The optional `reasonDetail` is stored as the attempt's `reason_detail` (and the unit's), e.g. the step at which a hung attempt was killed (OQ-2.9-12) |
| `releaseLease` | T5 (`unused`: leased but never started) or T13 (`shutdown`). (wave-2 review) **(P)** Cause `host_unavailable` (T5c from `LEASED`, T13b from `RUNNING`) is used for the disk hard stop, `SpoolFull`, a container-runtime outage and sleep or power loss. It does **not** increment `lease_count` (the lease just taken is given back) and does **not** count as an attempt (OQ-2.9-10, OQ-2.9-11, OQ-1.4-25). It is accepted while the `lease_id` is still current, even if `lease_expires_at` has passed but the sweeper has not yet expired it | Conditional on lease |

```ts
emit(tx, input: { eventType; schemaVersion; entityId; sourceId?; jobId?; payload; dedupKey: string }): Promise<{ eventId; duplicate: boolean }>
consume(consumer: ConsumerName, handlers: Record<EventType, (env: Envelope) => Promise<void>>): Worker
retryDelivery(input: { deliveryId: UUID; actor: string }): Promise<void>
```

| Function | Behaviour |
|---|---|
| `emit` | Must be called inside the caller's state-changing transaction. Inserts `event_log` (`ON CONFLICT (dedup_key) DO NOTHING` → `duplicate=true`) and one `event_delivery` row per consumer in the routing table (§4.5). After commit, the emitter adds a BullMQ job per delivery and marks it `enqueued`. If the process dies before that, the reconciler enqueues it (§5.4) |
| `consume` | BullMQ worker wrapper for one consumer queue: validates the envelope and payload against `packages/schemas`; upgrades older `schema_version`s (OQ-1.4-13); calls the handler; marks the delivery `completed`. Retries and DLQ per §5.6 |
| `retryDelivery` | Manual DLQ retry (§49, F-32): `dead → pending`, attempts reset, re-enqueued |

**Schema versioning (F-24):** additive-only changes within a `schema_version`; any breaking change bumps it. Consumers ignore unknown fields. Upgrade/compatibility mechanics beyond this: OQ-1.4-13.

**Ordering:** none guaranteed. Every handler re-reads the entity and drops stale events (e.g. `attempt_id` no longer current, `state_version` lower than seen) [Assumption; F-24 idempotent consumers].

## 5. Business Rules & Edge Cases

### 5.1 Core rules

| # | Rule | Basis |
|---|---|---|
| R1 | Postgres `capture_unit` is the only authority for unit state. A BullMQ entry is a hint; any consumer that finds an entry disagreeing with Postgres drops it | DC-14 |
| R2 | Every unit has a stable identity `unit_key`; creating it twice yields one row | DC-02 |
| R3 | Every state-changing write from a capture worker is conditional on the current `lease_id` (via `withLease`/`completeAttempt`). A zombie's write fails with `LeaseLost` and changes nothing | doc 22 §5 |
| R4 | A lease lasts until `heartbeat_at + 60 s`. Heartbeats arrive every 10 s | DC-03 |
| R5 | A lease holder that cannot write a heartbeat for 60 s must assume its lease is lost and stop the child (2.9 behaviour, required by this model) | DC-03 |
| R6 | `heartbeat` never extends a lease past `attempt_deadline_at`, so an attempt cannot outlive 90 s + 60 s even if the supervisor's kill fails | DC-01, DC-03 |
| R7 | Each new attempt uses the next strategy rung; the same rung is never repeated within a round | DC-05 |
| R8 | ≤ 3 browser attempts + 1 non-browser fallback per round; then `QUARANTINED`. For capture units, `QUARANTINED` is the DLQ of F-32 | DC-04, doc 22 §4, §7, F-32 |
| R9 | Backoff between attempts: 30 s, then 5 min | F-32 |
| R10 | A block gets exactly one polite retry, then `BLOCKED`. No rung evades (no CAPTCHA solving, no proxy/IP rotation, no fingerprint spoofing) | DC-08, doc 22 §7 |
| R11 | A unit failure never fails or blocks other units or other domains | DC-04, DC-09, IF§4 |
| R12 | `captured` ≠ publishable: `CAPTURED` only leads to `VALIDATING`; only the gate (2.10) or a human (4.4) moves a unit to `ACCEPTED` | DC-06 |
| R13 | Every wait in this Part is bounded: lease (60 s), attempt (90 s), retries (4 per round), leases per round, validation time and redeliveries, delivery attempts (3), backlog (500) | DC-01 |
| R14 | Every emitted event is written to `event_log` in the same transaction as the state change it describes | DC-14, F-24 |
| R15 | Consumers are idempotent; delivery is at-least-once | F-24 |
| R16 | Manual retry re-runs only failed units and resets their attempts; it never applies to `BLOCKED` units | F-32, doc 22 §10, DC-18 |
| R17 | Intake holds stop **new leases** only; units already running finish | doc 22 §6 |

### 5.2 Lease lifecycle (sequence)

```
supervisor (2.9)                 1.4 (Postgres)                         child (2.2)
leaseNextUnit ─────────────────► PENDING→LEASED (60 s TTL)
startAttempt ──────────────────► LEASED→RUNNING, deadline=now+90 s
     ◄──── step every 10 s ─────────────────────────────────────────── heartbeat(step)
heartbeat(step) ───────────────► extend lease to now+60 s (≤ deadline)
withLease(fn: register artifacts (1.3) + completeAttempt) ──► RUNNING→CAPTURED, lease cleared, emit captured
```

### 5.3 Fair scheduler (`leaseNextUnit`)

Pseudocode (contract-level):

```
if isIntakeHeld(): return null
eligible = domains D where
    exists unit u: u.domain_key = D and u.state in (PENDING, RETRY_WAIT with retry_at ≤ now)
                   and u.job.status = RUNNING
    and policy(D).crawl allowed                                  -- 1.5
    and effective_breaker(D) ≠ open                              -- stored by 1.5, set by 2.9; an expired `open` counts as half_open (wave-2 review, below)
    and (effective_breaker(D) ≠ half_open or count(non-terminal units of D, state ≠ PENDING, last_leased_at ≥ breaker_changed_at) = 0)   -- one probe unit (doc 22 §9; wave-2 review, below)
    and count(LEASED+RUNNING in D) < policy(D).max_concurrency   -- default 2 (F-10)
order eligible by max(last_leased_at in D) ascending, nulls first   -- round-robin, least recently served first
for D in eligible:
    pg_advisory_xact_lock(hash(D))                               -- no two supervisors overfill D
    re-check concurrency for D
    job = next entry from BullMQ queue capture.<D> (priority order)
    if job missing but Postgres has dispatchable units in D: re-add entries for D (self-heal), retry once
    if job's unit is not dispatchable or dispatch_seq differs: drop job, take next
    promote RETRY_WAIT→PENDING if due (T21); conditional UPDATE PENDING→LEASED (T3)
    complete the BullMQ job; return Lease
return null
```

(wave-2 review) **Breaker rules in the scheduler (P).** (a) `effective_breaker(D)` is the stored `breaker_state`, except that an `open` breaker whose `breaker_open_until` has passed is treated as `half_open` (one probe allowed) until 2.9's 30 s tick writes the state (OQ-2.9-17). 1.5's `evaluateCollection` applies the same rule, so the two callers always agree. (b) Half-open admission counts **every non-terminal unit of that domain that was leased since `breaker_changed_at`** and is not `PENDING` (so `LEASED`, `RUNNING`, `RETRY_WAIT`, `CAPTURED`, `VALIDATING`), not only `LEASED` and `RUNNING`: a probe waiting in `RETRY_WAIT` or `VALIDATING` still occupies the single probe slot (OQ-2.9-15). `PENDING` units are excluded so that a probe released unused can be leased again instead of blocking itself.

| Property | How it is met | Basis |
|---|---|---|
| One slow or hostile site cannot starve others | per-domain queues + round-robin by least-recently-served domain | DC-09, doc 22 §2 #7 |
| No head-of-line blocking | a saturated domain is skipped, not waited on | doc 22 §6 |
| Most valuable pages first within a site | BullMQ priority from page-type score | F-10, doc 22 §6 |
| Per-domain limit 2 concurrent | counted from Postgres `LEASED+RUNNING` under an advisory lock | F-10 |
| Global browser slots (2–3) | the supervisor calls `leaseNextUnit` only when it has a free slot (2.9); budget throttle halving slots is 2.9 reading 1.6 | doc 22 §6, §9 |
| Discovery is never blocked by capture | discovery runs from `ev.discovery`, a separate queue; it only shares `paceDomain` | doc 22 §6 |
| Which jobs are `RUNNING` (admission) | 2.5 | doc 22 §6 |

### 5.4 Reconciler (DC-14)

Runs at startup of `worker-app` and `supervisor` (1.1 process contract), every **5 min** in `worker-app`, after a Redis reconnect [Assumption], and on `work reconcile`. Only one instance runs at a time (Postgres advisory lock); a second caller returns immediately.

| Step | Action | Basis |
|---|---|---|
| 1 | `RETRY_WAIT` with `retry_at ≤ now` → T21 | F-32 |
| 2 | Each `PENDING` unit in a `RUNNING` job: ensure dispatch entry `"<unit_id>.<dispatch_seq>"` exists in `capture.<domain_key>`; add if missing (same id ⇒ no duplicate) | DC-14 |
| 3 | `LEASED`/`RUNNING` with `lease_expires_at < now` → `expireLease` (backstop for 2.9's 30 s sweeper) | DC-14, doc 22 §9 |
| 4 | Remove dispatch entries whose unit is terminal, not dispatchable, or has a different `dispatch_seq`; remove empty `capture.<domain>` queues of domains with no non-terminal units | DC-14 |
| 5 | `CAPTURED` with no `VALIDATING` after the validation deadline, and `VALIDATING` past `validation_deadline_at` → T20 | DC-01 |
| 6 | `event_delivery` `pending` (older than 1 min [Assumption]) or `enqueued` but absent from Redis → enqueue | DC-14 (extended to events, OQ-1.4-11) |
| 7 | Backlog check: if `count(ACCEPTED and normalized_at is null) + count(CAPTURED) + count(VALIDATING) > 500` → `holdIntake(backlog)`; if ≤ resume threshold → `releaseIntake(backlog)`. (wave-3 review) **(P)** `CAPTURED` and `VALIDATING` units count too, because a gate that falls behind is a backlog before anything is `ACCEPTED` (OQ-2.10-21); `PENDING` units are **not** counted (a hold stops new leases, so they could never drain) | doc 22 §6 |
| 8 | Log counts per state and the actions taken; expose to 1.8 | doc 22 §12 |

Every step is idempotent, so a reconciler crash midway is harmless. Steps 2 and 6 alone restore all lost work after Redis is wiped.

### 5.5 Retry and backoff — capture units

| Attempt ends with | Next |
|---|---|
| Failure (`failed`, `lease_expired`, `deadline_exceeded`), rejection by gate or human, and the ladder is not exhausted | `RETRY_WAIT`, next rung, `backoff(attempt_no)` |
| Same, ladder exhausted | `QUARANTINED` (`LADDER_EXHAUSTED`) |
| First block | `RETRY_WAIT` (polite retry), next rung |
| Second block, or block with ladder exhausted | `BLOCKED` |
| `released` (shutdown) or lease lost before start | `PENDING`, attempt not counted, bounded by `LIMIT_UNIT_MAX_LEASES` |
| `released` with cause `host_unavailable` (disk hard stop, `SpoolFull`, container-runtime outage, sleep or power loss) (wave-2 review) | `PENDING`, attempt not counted, `lease_count` not incremented |
| `skipped` with `HTTP_NOT_FOUND`, `NON_HTML_RESPONSE`, `OFF_DOMAIN_REDIRECT`, `POLICY_DENIED` or `ROBOTS_DISALLOWED` (wave-2 review) | `SKIPPED` at once (T12); ladder not climbed, no backoff |

### 5.6 Retry and DLQ — event deliveries (§49, F-32)

| Item | Rule |
|---|---|
| Attempts | 3 per delivery; BullMQ custom backoff 30 s, then 5 min |
| Timeout | per-consumer handler timeout (OQ-1.4-15) |
| After the 3rd failure | `event_delivery.status = dead` (Postgres DLQ); BullMQ failed job kept per retention; visible to 6.4 and 1.8 |
| Manual retry | `retryDelivery` resets attempts (F-32) |
| Schema invalid / unknown `schema_version` | not retried; straight to `dead` with reason `schema_invalid` |
| Downstream failure | never touches capture state; a failing classifier does not cause a re-crawl (§8, DC-10) |

## 7. Non-Functional Notes

### Capacity [Estimate]

| Quantity | Value | Basis |
|---|---|---|
| Units per full V0 run | ≈ 500 sites × 25 pages × 2 viewports ≈ 25,000 | F-07, F-10, F-12 |
| Units per site job | ≤ 50 | doc 22 DC-13 |
| Throughput | ≈ 270 units/h (≈ 0.08 leases/s) | doc 22 §14 |
| Heartbeat writes | 2–3 slots ÷ 10 s ≈ 0.3 writes/s | doc 22 §5–§6 |
| Events | ≈ 3 per unit × ≈ 3 consumers ≈ 10 delivery rows per unit ≈ 250,000 per full run | derived; trivial for Postgres |
| Reconciler scan | ≤ 25,000 non-terminal units every 5 min, index-backed | DC-14 |

No scaling work is needed; a second Crawler VM is a deployment action because leases coordinate through Postgres (doc 20 §5, 1.1 hook).

### Reliability

- Losing Redis loses no work (DC-14); losing a worker loses at most one attempt (DC-03); a unit's attempt lasts ≤ 150 s; a job ends within 30 min via 2.5 (DC-13).
- Redis must run with BullMQ's required settings (no key eviction); Redis persistence is optional (1.1, DC-14).
- Every 1.4 function is safe to retry.

### Security & privacy

- No HTTP surface (F-24). Crawler VM processes reach Postgres/Redis over the private path defined by 1.1/1.7.
- The capture child holds no DB or Redis credentials; the supervisor relays heartbeats and results [Assumption; 1.1 secret matrix shows no `DATABASE_URL`/`REDIS_URL` in the capture container].
- Payloads, `reason_detail` and `last_error` carry IDs and short messages only, never page text, cookies or secrets [Assumption; F-19].

### Cost recording

1.4 records no `CostEvent`. Attempt `started_at`/`ended_at` (including failed attempts) give browser seconds; the `CostEvent` itself is written by 2.9 using 1.6's contract (doc 13 "failures cost money").

### Testing requirements

| Test | Requirement |
|---|---|
| State-machine unit tests | every transition T1–T25 (plus T5c, T6b, T13b, wave-2 review) succeeds with its guard true; every other (from, to) pair is refused; constraints C1–C5 hold after each |
| Concurrency property test | random interleavings of `heartbeat`, `expireLease`, `completeAttempt`, `withLease`, `leaseNextUnit` from 2+ supervisors never yield two lease holders, a zombie write, or > `max_concurrency` units per domain |
| Fairness test | 1 domain with 50 units + 3 domains with 5 units: the small domains are each leased before the large domain's 3rd unit |
| Reconciler tests | after `FLUSHALL` mid-run every unit still reaches a terminal state; running the reconciler twice changes nothing |
| Outbox tests | crash between commit and enqueue → event delivered once by the reconciler |
| Delivery DLQ tests | 3 handler failures → `dead`; `retryDelivery` → delivered |
| **Torture/chaos fixtures required from 2.11** (doc 22 §13) | process-kill injection; lease-loss injection; supervisor kill; Redis kill/wipe; Postgres restart; disk-full injection (intake hold); hanging navigation (deadline path). Each must end in a terminal unit state within its deadline with no duplicate unit, attempt or artifact rows |

### Assumptions

- [Assumption] Table names are snake_case singular and enums follow 1.2's convention; names marked (P) may be renamed at the consistency review.
- [Assumption] All lease and deadline comparisons use the Postgres clock.
- [Assumption] The supervisor (2.9) relays heartbeats and results; the capture child never connects to Postgres or Redis (consistent with 1.1's secret matrix).
- [Assumption] One `capture_job` per site per crawl run (`UNIQUE (crawl_run_id, source_id)`).
- [Assumption] A `capture_session` belongs to one job (F-21); since a job has ≤ 50 units, the 50-unit recycle rule (DC-07) fits inside one job.
- [Assumption] `paceDomain` state lives in Redis; losing it only resets pacing and needs no reconciliation.
- [Assumption] The reconciler also runs after a Redis reconnect, in addition to startup and every 5 min (DC-14).
- [Assumption] Event payloads carry IDs and small metadata only (F-19 spirit).
- [Assumption] Downstream events of 3.x/4.x reuse this envelope and the `emit`/`consume` contracts but are catalogued by their own Parts.
- [Assumption] Event handlers re-read entity state and drop stale events; no ordering is guaranteed.
