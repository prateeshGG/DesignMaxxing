## 1. Purpose & Scope

**Purpose.** One place that answers, for any site: *may we collect from it, how fast, how much, with which per-site adjustments, and may what we collected be shown?* Every collection Part asks this registry before it acts. A takedown or a policy change here stops collection everywhere at the next check.

**Phase:** V0. Later phases get forward-compatible hooks only, each marked **[hook]** (F-40, template rule 3).

### 3.2 `crawl_policy` JSONB keys and the effective policy

`crawl_policy` holds **per-source overrides only**. Defaults come from config (1.1). The **effective policy** = defaults merged with overrides, each value clamped to its ceiling. Consumers always read the effective policy through `getEffectivePolicy`, never the raw JSONB. [Decision] doc 22 §11: "all limits are configuration, not code constants, and appear in the admin console".

| Key (P) | Type | V0 default (config) | Ceiling: an override may only be stricter | Basis | Enforced by |
|---|---|---|---|---|---|
| `min_request_interval_ms` | int | 1000 | ≥ 1000 (also ≥ robots crawl-delay if OQ-1.5-13 holds) | F-10 (1 req/s) | 1.4 scheduler |
| `max_concurrency` | int | 2 | ≤ 2, ≥ 1 | F-10 | 1.4 scheduler |
| `max_pages` | int | 25 | ≤ 25 | F-10, F-07 | 2.1 |
| `max_depth` | int | 3 | ≤ 3 | F-10 | 2.1 |
| `max_asset_bytes` | int | 26 214 400 (25 MB) | ≤ 25 MB | F-10 | 2.4 |
| `max_runtime_s` | int | 1800 | ≤ 1800 | DC-13 | 2.5 / 2.9 |
| `allowed_paths` | string[] (path globs) | `[]` (= all) | narrowing only | IF§6 ([03](../03-capture-and-crawling-workflow.md)) | 2.1 |
| `blocked_paths` | string[] (path globs) | `[]` | adding only | IF§6 | 2.1 |
| `max_query_variants` | int | **Not decided** (OQ-1.5-12) | — | IF§6 | 2.1 |

Not stored here in V0: the GAP§8 crawl budgets (`max_browser_minutes`, `max_video_minutes`, `max_storage`, `max_AI_cost`). Their values are not decided and budgets belong to 2.5 (OQ-1.5-12). The user-agent is global config (1.1) and is **never** per source (R-5).

The **robots override** is the only relaxation of F-10 that exists. It lifts robots disallow rules only and never raises any ceiling in this table.

### 3.5 `source_policy_change` (P) — owned, append-only

[Decision] F-10 requires a *logged* override; [Decision] GAP§29 / doc 16: overrides are stored as revisions, not overwrites.

| Column | Type | Note |
|---|---|---|
| `id` | uuid | PK |
| `source_id` | uuid → `source.id` | |
| `actor_type` | enum (P): `admin`, `system` | |
| `actor_id` | text | User id, or the Part id of a system actor (`2.1`, `2.9`) |
| `field` | text | Column name, `crawl_policy.<key>`, or `site_recipe` |
| `old_value`, `new_value` | jsonb | |
| `reason` | text | Required for robots override, takedown, takedown reversal, `drop`, `inaccessible` |
| `created_at` | timestamptz | |

The application role has no UPDATE or DELETE on this table. One row is written per changed field, in the **same transaction** as the change.

**Exception, to keep the log small:** routine system writes are not logged per call, namely robots refreshes that do not change `robots_status` and breaker transitions. Their history lives in the structured logs (1.8) [Assumption].

### 3.6 State machines

**`seed_status`** (DC-19)

```
candidate ──approve (admin / CSV keep)──► approved
candidate ──drop (admin / CSV drop)─────► dropped
approved  ──drop (admin, reason)────────► dropped
dropped   ──approve (admin, reason)─────► approved
```

**`takedown_status`** (F-18; reversal is OQ-1.5-4)

```
none ──requestTakedown──► requested ──markTakedownCompleted──► completed
requested | completed ──reverseTakedown (founder, reason; OQ-1.5-4)──► none
```

**`access_status`** (doc 22 §9–§10)

```
ok ──2.9 poison-quarantine mark──► needs_recipe_or_skip ──saveRecipe / admin clear──► ok
ok ──admin "mark inaccessible"──► inaccessible ──admin clear (reason)──► ok
ok ──admin "snooze 30 days"──► snoozed ──(now ≥ snoozed_until, evaluated lazily)──► treated as ok
```

Snooze expiry is evaluated at read time, so no cron job is needed. The stored value is reset to `ok` on the next write to the row.

**`breaker_state`**: `closed → open → half_open → closed | open`. The transitions and their timing are 2.9's. 1.5 stores them and enforces compare-and-set.

### 3.7 Migration notes

- One migration (tooling from 1.2) creates the four tables and their enums. The enum values marked (P) can change before the first deploy without cost. After that, changes are additive only.
- `USER_UPLOAD` (V1, F-22) and the V2 authorization values are additive enum migrations.
- Dropping the `authenticated_allowed = false` check is a V2 migration, gated by F-40.
- No `SourceVersion` table (F-21).

**`PolicyDecision` (P)**

```ts
type CollectionPurpose = 'seed_preview' | 'crawl' | 'recrawl' | 'media' | 'publish';
type DenyReason =
  | 'takedown' | 'competitor_domain' | 'seed_dropped' | 'not_approved'
  | 'authorization' | 'crawl_disallowed' | 'recrawl_disallowed'
  | 'media_disallowed' | 'screenshot_disallowed'
  | 'access_inaccessible' | 'access_snoozed' | 'needs_recipe_or_skip'
  | 'breaker_open' | 'robots_disallow_all' | 'robots_unavailable';
interface PolicyDecision {
  allowed: boolean;
  reason?: DenyReason;            // first failing rule in R-2 order
  scope?: 'homepage_only' | 'full'; // homepage_only for seed_preview (DC-19)
  retry_after?: string;           // ISO time: breaker_open_until or snoozed_until
  breaker_half_open?: boolean;    // allowed, but 2.9/1.4 admit exactly one probe unit (also set for an expired `open` breaker, R-2 step 9; wave-2 review)
  effective_policy: EffectivePolicy;
  recipe?: { recipe_id: string; version: number } | null;
}
```

### 4.2 Source Adapter interface

[Decision] D-46/GAP§30: acquisition goes through a Source Adapter per source kind (web URL, authorized web session, iOS authorized build, Android APK/AAB, internal test build). The interface itself is **Not decided** in the docs ([02](../02-system-architecture.md)); the sketch below is (P), OQ-1.5-31. Adapters normalize identity, give policy defaults and provenance values, and name the pipeline entry. They do **not** discover, capture or schedule; those stay with 2.1, 2.2 and 2.5.

```ts
type SourceAdapterKind = 'public_web'            // V0
  | 'authorized_web_session'                     // [hook] V2, 7.2
  | 'android_package' | 'ios_authorized_build'   // [hook] V2, 7.4 / 7.5
  | 'internal_test_build';                       // [hook] V2
interface SourceAdapter {
  readonly kind: SourceAdapterKind;
  readonly sourceTypes: readonly SourceType[];   // public_web: ['WEBSITE']
  readonly phase: 'V0' | 'V1' | 'V2';            // registry refuses adapters of an unopened gate (F-40)
  normalizeIdentity(input: { url: string }):
    { ok: true; canonical_url: string; domain: string; platform: string }
    | { ok: false; error: 'INVALID_URL' | 'UNSUPPORTED_SCHEME' };
  allowedAuthorization(): readonly AuthorizationStatus[]; // public_web: ['public', 'owner_permitted'] (P)
  defaultFlags(): Pick<Source, 'crawl_allowed' | 'media_allowed' | 'screenshot_allowed'
                               | 'recrawl_allowed' | 'authenticated_allowed'>;
  provenance(source: Source): { acquisition_method: string; access_authorization: string }; // values: OQ-1.5-31
  entryStage(): 'web_discovery';                 // 2.5 maps this to 2.1's discovery job; job name owned by 2.1
}
```

**V0 `public_web` adapter behaviour:**
- Accepts only `http`/`https`.
- Lowercases the host and strips the path, query, fragment and default port, keeping `canonical_url` as the scheme plus host, with no path. Full URL canonicalization is 2.1's.
- Computes `domain` as the registrable domain.
- Returns `platform = 'web'` (P).
- Sets `authenticated_allowed = false` (F-17).

## 5. Business Rules & Edge Cases

### 5.1 Rules

| # | Rule | Basis |
|---|---|---|
| R-1 | **No collection without permission.** No discovery job, crawl run or unit lease starts for a source unless `evaluateCollection` returns `allowed` for that purpose. Publication additionally requires `allowed` for `publish` (gate check 15) | [10](../10-authentication-and-permission-workflows.md) restriction 4; F-10; F-18; doc 22 §8 check 15 |
| R-2 | **Evaluation order.** The first failing rule wins and becomes `reason`: (1) `takedown_status ≠ none` → `takedown`; (2) domain on the competitor deny-list → `competitor_domain`; (3) `seed_status = dropped` → `seed_dropped`; (4) purpose ≠ `seed_preview` and `seed_status = candidate` → `not_approved`; (5) `authorization_status` not in the adapter's allowed set → `authorization`; (6) `crawl_allowed = false` (all purposes except `publish`) → `crawl_disallowed`; (7) purpose-specific flag: `recrawl_allowed`, `media_allowed`, `screenshot_allowed` (for `publish`); (8) `access_status` `inaccessible` / `needs_recipe_or_skip` / unexpired `snoozed` → matching reason with `retry_after` (`needs_recipe_or_skip` is checked at every lease, R-15, so it denies at the **next lease check**: units of that domain not yet leased are not leased, and attempts already running finish) (wave-2 review); (9) `breaker_state = open` and `now < breaker_open_until` → `breaker_open` with `retry_after`; an `open` breaker whose `breaker_open_until` has passed is treated as `half_open` (allowed, `breaker_half_open = true`, one probe) until 2.9's tick writes the state, the same rule as 1.4's scheduler (OQ-2.9-17) (wave-2 review); (10) `robots_status = disallow_all` without override → `robots_disallow_all`; `unreachable` → per OQ-1.5-14. Rules 8–10 do not apply to `publish`: already-captured, gate-accepted content of a source that is now blocked or snoozed stays publishable. Takedown, competitor, `dropped`, not-approved (OQ-1.5-20) and `screenshot_allowed` do apply to `publish` | Composition of F-10, F-18, F-41, DC-19, doc 22 §9–§10. The order is (P), OQ-1.5-1 |
| R-3 | **F-10 ceilings are absolute.** Per-source values may only be stricter than the §3.2 ceilings. Anything else fails with `POLICY_EXCEEDS_CEILING`, including for admins. The robots override is the only F-10 relaxation; it needs the founder and a reason, is logged, and never raises rate, concurrency, page, depth, size or runtime limits | F-10, DC-13, DC-01 |
| R-4 | **Robots is always honored.** Site-level `disallow_all` is a policy skip, and its units end `SKIPPED (policy: robots)`, **not** `BLOCKED`. So robots skips are not counted in `BLOCKED %`. Per-URL robots matching is 2.1's, using the rules stored via `robots_artifact_id`; with `robots_override = true`, 2.1 ignores disallow rules for that source | F-10; doc 22 §4 unit states; DC-18 |
| R-5 | **One honest identity.** The user-agent string with contact URL is global config: **1.1 owns the key `CRAWLER_USER_AGENT`** and its content follows F-10 (honest project name plus contact URL); 1.5 does not own it and only exposes the value through `getEffectivePolicy` (wave-2 review). No source, recipe or adapter may override it, add headers, or change TLS or browser fingerprints | F-10; DC-08; SC-03 |
| R-6 | **No evasion fields anywhere.** Recipes and `crawl_policy` reject proxy, stealth, CAPTCHA, credential and robots/rate keys (§3.3). A high block rate is answered by curation (drop, snooze, ask the owner), never by configuration | DC-08; SC-03; SC-05 |
| R-7 | **Takedown stops everything at once.** `requestTakedown` sets `takedown_status = requested`, records `deadline_at = received_at + 48 h`, and emits `source.takedown_requested`, all in one transaction (event after commit). From then on every purpose is denied, including `publish`, so the gate's check 15 rejects in-flight captures. The source row is kept, so the domain stays blocked | F-18; doc 22 §8 check 15 |
| R-8 | **Takedown wins every conflict.** Seed CSV `keep`, admin approval, robots override, `createSource` re-submission and recipes cannot re-enable a source under takedown. Only `reverseTakedown` can (OQ-1.5-4) | F-18 |
| R-9 | **No competitor libraries.** `createSource` refuses domains on the configured competitor deny-list, and `evaluateCollection` re-checks it (the list may grow after creation) | F-41 |
| R-10 | **Candidate and approve.** `candidate` sources allow only `seed_preview`, scope `homepage_only` (the spike captures each candidate's homepage). `approved` allows full crawling. `dropped` allows nothing. Re-importing the seed file never moves a source out of `dropped` or out of takedown unless the founder's CSV decision changed from `drop` to `keep` (`dropped → approved` is allowed; takedown is not). 2.1 reports conflicting rows | DC-19; `seeds/README.md` |
| R-11 | **V0 is public websites, logged out.** Only `type = WEBSITE` and the `public_web` adapter are accepted. `authenticated_allowed` must be `false`. Adapters whose gate has not opened are refused by the registry | F-02, F-17, F-40 |
| R-12 | **Field ownership.** Admin-only fields are written only by admin actions. 2.1 writes only the `robots_*` fetch fields (not the override) and seed fields during an admin-initiated import, through `setSeedStatus` and `updateSourceCuration` (wave-2 review). 2.9 writes only `breaker_*` and `access_status = needs_recipe_or_skip`. Each function updates only its own columns, so concurrent writers never overwrite each other. Every admin change writes a `source_policy_change` row in the same transaction | F-10 ("logged"); GAP§29; F-34 |
| R-13 | **Breaker storage, not behaviour.** 1.5 stores breaker fields with compare-and-set and turns them into `breaker_open` decisions. Thresholds, window, doubling and probe admission are 2.9's. The fields live in Postgres, so the state survives a Redis wipe | doc 22 §9; DC-14 (Postgres is the source of truth) |
| R-14 | **Recipes are versioned and bounded.** Default behaviour is generic, and a recipe is added only when a site misbehaves. Bodies are strict-schema validated. Rows are never edited in place. Saving activates the new version and clears `needs_recipe_or_skip`. 2.2 records the `recipe_id` and version it used, as provenance (field owned by 1.6) | doc 22 §7, §10; INT; D-50 provenance |
| R-15 | **Evaluate late, never cache.** Policy is evaluated at crawl-run creation (2.5), at each unit lease (1.4), and at the publish gate (2.10). No cache is kept beyond one call, so a takedown or flag change takes effect on the next check, at most one in-flight attempt later (≤ 90 s, doc 22 §5) | F-18; DC-03 |
| R-16 | **Snooze is 30 days and expires by itself.** "Snooze" sets `snoozed_until = now + 30 d`. After that, evaluation treats the source as `ok` | doc 22 §10 |
| R-17 | **Re-crawl permission.** `recrawl` is the purpose 2.5 uses when the source already has a completed crawl run; `recrawl_allowed = false` denies it. In V0, re-crawls are manual (F-10); the V1 monthly cron uses the same check [hook] | F-10; GAP§2 |
| R-18 | **SSRF early check.** `createSource` runs 1.7's SSRF check on the host. The fetch-time re-check after redirects stays in 1.7 | F-20 |
| R-19 | **No credentials on `Source`.** No secret, cookie, password or storage state is ever stored in these tables. V2 authorized sessions live inside the crawler boundary (7.1) and would be referenced by id only [hook] | F-15; §52; [10](../10-authentication-and-permission-workflows.md) |

### 5.2 Edge cases and relevant failure modes

Rows reference the doc 22 §2 failure-mode catalog (#n) where applicable. DC-16 capture hazards are 2.3's; V0 recipes carry no hazard-specific fields.

| # | Case | Detection | Automatic response | Human? |

| E-20 | Private, loopback or metadata host submitted | 1.7 SSRF check | `SSRF_BLOCKED` | No |

| Reliability | Postgres is the only store (DC-14), so nothing is lost when Redis is lost. Events are published after commit; consumers must be idempotent (F-24). A lost event must not leave a source collectable after a takedown: R-15 re-checks at every lease and at publish regardless of events |
| Fail-safe | A policy read error denies collection and publication (OQ-1.5-39) |
| Security | Writes only through §4.1. HTTP limited to the admin role (F-34). `source_policy_change` is append-only at the database-grant level. No credentials stored (R-19). The SSRF early check runs at creation (F-20). Recipe strings are data, never executed as script (OQ-1.5-28). Crawler-VM workers need read access to `source`/`site_recipe` and write access only through their system functions [Assumption: DB connectivity per 1.2/1.7] |
| Privacy | `takedown_request.requester_contact` is personal data: minimal, admin-only, retention per 8.2 (OQ-1.5-38) |
| Cost | This Part performs no expensive operation and emits no `CostEvent`. Robots fetch cost is 2.1's |
| Observability (data exposed to 1.8) | Counts by `seed_status`, `access_status`, `breaker_state`; open takedowns with age vs `deadline_at`; policy denials by `reason` (logged per call); `category` for `BLOCKED %` per seed category (DC-18). ## 8. Open Questions & Assumptions

### Open questions

Each entry: the question — why it matters — **Suggested default (a suggestion, not a decision).**

- **OPEN QUESTION OQ-1.5-1:** Confirm every (P) name in this spec: tables, columns, enum values, error codes, event names, the `DenyReason` order. — Downstream specs (1.4, 2.1, 2.5, 2.9, 2.10) will code against them. — **Suggested default:** accept as written; change only for consistency with 1.2/1.4 naming conventions found in the wave-1 review.
- **OPEN QUESTION OQ-1.5-2:** Should `source_type` contain the V2 values (`WEB_APP`, `IOS_APP`, `ANDROID_APP`, `AUTHORIZED_BUILD`) from day one, or only `WEBSITE`? — Enum churn vs. exposing unusable values. — **Suggested default:** include all §5 values now (they are decided names); the adapter registry refuses unopened gates (R-11).
- **OPEN QUESTION OQ-1.5-3:** Values of `authorization_status`. — The superseded AUTH list (`PUBLIC`, `USER_AUTHORIZED`, …) cannot be reused, and R-2 step 5 needs a set. — **Suggested default:** `public` (V0 default), `owner_permitted` (the site owner agreed; F-44 prefers such sites), `not_authorized`, plus [hook] `authorized_session`, `authorized_build` added in V2.
- **OPEN QUESTION OQ-1.5-4:** Lifecycle and reversibility of `takedown_status`. — A wrongly recorded takedown must be fixable, but a takedown must never lapse silently. — **Suggested default:** `none → requested → completed`. Reversal only via `reverseTakedown` by the founder with a reason; it returns the source to `seed_status = dropped`, so re-approval is a second explicit step.
- **OPEN QUESTION OQ-1.5-5:** Is an owner "opt-out" (do not crawl us) different from a takedown (remove what you have)? — It decides whether we need a second status. — **Suggested default:** one mechanism. Any owner request is a takedown: it removes existing data and permanently blocks collection.
- **OPEN QUESTION OQ-1.5-6:** Takedown scope: whole source only, or individual pages too? — Page-level removal needs per-page tombstones in 2.1 and in propagation. — **Suggested default:** whole source in V0 (matches F-18 "Remove-source propagation").
- **OPEN QUESTION OQ-1.5-7:** Does a takedown on `example.com` also block subdomains and other source types for the same registrable domain? — It prevents re-collection through a side door. — **Suggested default:** yes. Match on registrable domain across all source types.
- **OPEN QUESTION OQ-1.5-8:** Who orchestrates the 48 h propagation (website → pages → screenshots → assets → embeddings → search index → cached thumbnails → collections) and who marks a takedown `completed`? — No Part in [21](../21-parts-hierarchy.md) owns propagation end-to-end. — **Suggested default:** each data-owning Part ships an idempotent consumer of `source.takedown_requested`; 6.4 shows a per-store checklist; the founder calls `markTakedownCompleted` after it is green; the runbook lives in 8.4.
- **OPEN QUESTION OQ-1.5-9:** On takedown, is raw evidence (R2 blobs, including the robots.txt body) deleted or quarantined? — [15](../15-security-and-isolation.md) leaves it open; A-21 infers removal. — **Suggested default:** delete derived data and quarantine raw evidence until counsel (E5) advises. Owner: 1.3.
- **OPEN QUESTION OQ-1.5-10:** Are `source` rows ever hard-deleted? — Deleting loses the takedown block and the audit trail. — **Suggested default:** never. Removal = takedown plus tombstone. An unknown domain in a takedown creates a `dropped` tombstone row.
- **OPEN QUESTION OQ-1.5-11:** Are rate limit and concurrency keyed by registrable domain or by host? — Host keying lets subdomains multiply the load beyond F-10's per-domain intent. — **Suggested default:** registrable domain (`source.domain`).
- **OPEN QUESTION OQ-1.5-12:** Value of `max_query_variants`, and whether per-source overrides of the GAP§8 budgets (`max_browser_minutes`, `max_video_minutes`, `max_storage`, `max_AI_cost`) live in `crawl_policy`. — 2.1 needs a bound for URL traps (DC-01); 2.5 owns budgets. — **Suggested default:** `max_query_variants` = 3 per path [placeholder for the spike]. Budgets stay out of `crawl_policy` in V0 (2.5 decides).
- **OPEN QUESTION OQ-1.5-13:** Is robots `Crawl-delay` honored? — "Honor robots always" (F-10) arguably includes it, and it can only slow us down. — **Suggested default:** yes. Effective `min_request_interval_ms = max(1000, crawl-delay)`, capped so a site job stays feasible; if the delay makes 25 pages impossible within 30 min, the site gets fewer pages (2.1 prioritizes).
- **OPEN QUESTION OQ-1.5-14:** Policy when robots.txt is missing (4xx) or unreachable (5xx/timeout). — It decides whether outages make us crawl unpermitted paths. — **Suggested default:** follow RFC 9309. 4xx → no restrictions (`not_found`, allowed). 5xx or timeout → treat as disallow-all (`unreachable`, deny `robots_unavailable`) until the next successful fetch. Final call in 2.1.
- **OPEN QUESTION OQ-1.5-15:** Robots cache: is the body stored as a `RawArtifact`, and how fresh must it be? — Evidence of what robots said when we crawled is useful if challenged. — **Suggested default:** store each distinct body as a `RawArtifact` (content-addressed, 1.3); refresh at the start of every crawl run and at most every 24 h during a run.
- **OPEN QUESTION OQ-1.5-16:** Does the robots override expire, and does it require recorded owner permission? — Overrides are a legal-risk lever. — **Suggested default:** no automatic expiry, but shown prominently in 6.4. Recommended only when `authorization_status = owner_permitted`; not enforced.
- **OPEN QUESTION OQ-1.5-17:** Default values of the policy flags. — Defaults decide what a newly added site may do. — **Suggested default:** `crawl_allowed`, `media_allowed`, `screenshot_allowed`, `recrawl_allowed` = `true`; `authenticated_allowed` = `false`.
- **OPEN QUESTION OQ-1.5-18:** What does `media_allowed = false` mean in V0? — 2.4 needs a definite behaviour; F-18 already keeps source assets internal. — **Suggested default:** 2.4 skips storing asset binaries but still records the media inventory metadata.
- **OPEN QUESTION OQ-1.5-19:** Is `screenshot_allowed` also the display permission that gate check 15 names ("screenshots and display")? Does `false` also stop crawling? — Avoids a second flag. — **Suggested default:** yes, one flag. `false` denies `publish` and `crawl` (V0 value is visual).
- **OPEN QUESTION OQ-1.5-20:** Can captures of a source that is not `approved` (candidate previews, dropped sites) ever be published? — Seed previews exist only for the founder's contact sheet. — **Suggested default:** no. Only `approved` sources pass `publish`.
- **OPEN QUESTION OQ-1.5-21:** Does `needs_recipe_or_skip` stop new crawl runs, or only flag the site? — It decides whether a broken site keeps burning attempts. — **Suggested default:** (wave-2 review) it denies at the **next lease check** (R-15) and at the creation of any new `crawl` / `recrawl` run: units of that domain not yet leased are not leased (they stay `PENDING`; 2.5 closes them as `SKIPPED (JOB_DEADLINE)` at the job deadline, 2.9 OQ-2.9-25a), attempts already running finish, and the mark clears when a recipe is saved or the site is dropped.
- **OPEN QUESTION OQ-1.5-22:** After a snooze expires, is the site re-crawled automatically? — In V0, re-crawls are manual (F-10). — **Suggested default:** no automatic run. The site becomes eligible again and appears in 6.4's "ready to re-crawl" list.
- **OPEN QUESTION OQ-1.5-23:** Initial `seed_status` for a site the founder adds by hand. — DC-19 has the founder approve from a contact sheet, but a hand-added site is already chosen. — **Suggested default:** `candidate` by default, with an "approve now" option on `POST /sources`.
- **OPEN QUESTION OQ-1.5-24:** Handling of homepages that redirect to another registrable domain (e.g. a `.so` → `.com` move). — Gate check 1 rejects a changed registrable domain, so such sites fail every unit. — **Suggested default:** `domain` stays immutable. 2.1 flags the redirect; the founder creates a source for the target and drops the old one with `status_reason = "redirects to <domain>"`.
- **OPEN QUESTION OQ-1.5-25:** Recipe storage: versioned Postgres rows (proposed) or YAML files in the repo (INT)? — Recipes are created from the inbox at runtime (doc 22 §10), which suits rows; YAML suits review in git. — **Suggested default:** Postgres `site_recipe` rows; YAML as an optional export/import format with the same schema.
- **OPEN QUESTION OQ-1.5-26:** INT's recipe also carried `max_depth` and include paths, which overlap with IF§6 `crawl_policy`. Which wins? — Two places for one setting cause drift. — **Suggested default:** crawl scope only in `crawl_policy`; capture behaviour only in recipes.
- **OPEN QUESTION OQ-1.5-27:** Bounds for recipe values (`extra_wait_ms`, selector length, list sizes). — DC-01: everything bounded; a long wait eats the 90 s unit budget. — **Suggested default:** `extra_wait_ms` ≤ 10 000; ≤ 20 selectors per list; ≤ 500 characters per selector [placeholders, tune in the spike].
- **OPEN QUESTION OQ-1.5-28:** May a recipe contain arbitrary JavaScript to run on the page? — Power vs. safety and determinism. — **Suggested default:** no, not in V0. Selectors and waits only.
- **OPEN QUESTION OQ-1.5-29:** How are age gates and region selectors handled (doc 22 §15 item 7 points them to recipes)? Clicking them is an interaction, and the dangerous-action policy only arrives in V1. — **Suggested default:** V0 allows them only as `cookie_dismiss_selectors`-style dismiss clicks on non-submit elements; otherwise mark the site `inaccessible`.
- **OPEN QUESTION OQ-1.5-30:** Must a recipe change pass the torture suite and canary (DC-12 "capture-runtime change")? — Requiring it would kill the one-click inbox flow. — **Suggested default:** no. A recipe is data, not runtime code; the affected units are re-run and the gate judges them.
- **OPEN QUESTION OQ-1.5-31:** Confirm the Source Adapter method set (§4.2) and the provenance vocabulary for `acquisition_method` / `access_authorization`. — 1.6 and V2 adapters depend on it. — **Suggested default:** the §4.2 sketch; `acquisition_method = 'public_web_crawl'`, `access_authorization` = the source's `authorization_status` value.
- **OPEN QUESTION OQ-1.5-32:** What does `Source.owner` mean: the company that owns the site, or an internal user? — Attribution vs. ownership semantics. — **Suggested default:** nullable text naming the site's owner (company), used only for attribution; not a foreign key.
- **OPEN QUESTION OQ-1.5-33:** Is `category` a controlled vocabulary? — `BLOCKED %` per category (DC-18) needs stable groups. — **Suggested default:** free text taken from the seed file (24 values today), normalized to lowercase. Revisit if reports get messy.
- **OPEN QUESTION OQ-1.5-34:** Do breaker fields live on `source` (proposed) or in a separate table, and how is the doubling reset? How is a quality-driven "auto-pause site" (#19) represented? — 2.9 needs a home for its state. — **Suggested default:** on `source`. Doubling resets when a half-open probe succeeds and the breaker closes. #19 auto-pause is an open breaker with reason logged (2.9 to confirm).
- **OPEN QUESTION OQ-1.5-35:** Is the SC-04 adaptive throttle state (current delay) persisted? — It interacts with the static ceiling. — **Suggested default:** runtime state in 1.4's scheduler, not persisted. It may only be slower than `min_request_interval_ms`, never faster.
- **OPEN QUESTION OQ-1.5-36:** Roles: is "admin" the same as "founder" for robots override and takedown reversal once there is more than one admin? — F-10 names the founder explicitly. — **Suggested default:** V0 has one admin (the founder). If more are added, robots override and takedown reversal require an `owner` role.
- **OPEN QUESTION OQ-1.5-37:** Admin HTTP shape beyond §47 (`GET/POST /sources`): REST routes (proposed) or Next.js server actions? — 6.4 builds against it. — **Suggested default:** the §4.4 routes under the role-gated web app.
- **OPEN QUESTION OQ-1.5-38:** Retention of `takedown_request.requester_contact`. — Personal data. — **Suggested default:** keep for the length of the DMCA record-keeping period counsel advises (8.2); admin-only access.
- **OPEN QUESTION OQ-1.5-39:** Fail closed or fail open when policy cannot be read? — Failing open could crawl a taken-down or robots-disallowed site. — **Suggested default:** fail closed. Deny with a retryable error, so the unit is retried by 1.4's normal backoff.
- **OPEN QUESTION OQ-1.5-40:** Alert on a takedown approaching or past its 48 h deadline? — F-18 commits to 48 h; the daily summary may be too slow. — **Suggested default:** list open takedowns in the daily summary; send an immediate email at 24 h remaining and on breach (via 1.8).
- **OPEN QUESTION OQ-1.5-41:** Contents and location of the competitor deny-list (F-41). — `createSource` must check something concrete. — **Suggested default:** a config list (1.1) starting with `mobbin.com`, extended by the founder; matched on registrable domain.

### Assumptions

- [Assumption] One `WEBSITE` source = one registrable domain, because the seed file is keyed by domain and all 94 candidate rows are registrable domains.
- [Assumption] In V0 the founder is the only admin (F-34; solo founder).
- [Assumption] Crawler-VM workers can read the `source` and `site_recipe` tables in Postgres on the App VM, and write only through the system functions; the network path is 1.2/1.7's.
- [Assumption] 2.1 imports the seed file through `createSource` and `setSeedStatus` on behalf of the admin who runs the import.
- [Assumption] Routine system writes (unchanged robots refreshes, breaker transitions) are logged in structured logs rather than `source_policy_change`.
- [Assumption] A Public Suffix List–based library is acceptable for registrable-domain computation (choice per 1.1).
- [Assumption] Policy evaluation volume (about 270/h) needs no caching [Estimate, doc 22 §14].
