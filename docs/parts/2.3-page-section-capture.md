## 1. Purpose & Scope

**Purpose.** 2.3 is the part of the capture child that looks at the page. Inside 2.2's `pageCapture` slot it settles the page by scrolling, takes sharp raw screenshots in a motion pass and a static pass, measures the sections of the page from the DOM, applies the capture-hazard techniques, and records the DOM, accessibility tree, computed styles, performance timings and page metadata. It returns files and signals. It never decides whether a capture is publishable (2.10), never labels a section's type (4.3), never touches Postgres, Redis or object storage (2.2 R2), and never opens a page it was not given (F-46).

**What it hands on, in one line:** raw shots + a **section map** (DOM bounds, crop plan, hazard signals) + DOM-level documents; 3.2 turns them into `screen`, `screen_artifact`, `section`, `section_artifact` rows; 2.10 judges them.

**Phase:** `[V0]`. Later-phase hooks are marked **[hook]** and are compatibility only (F-40). The V1 scroll-pass video (F-13) belongs to 2.4; the interaction states (menus, tabs, accordions, toggles) belong to 2.7.

### 3.4 Contract documents (schemas in `packages/schemas`, additive-only within a `schema_version`, as F-24)

All documents are JSON, UTF-8, with `schema_version` and (where a detector or algorithm is involved) `algorithm_version`. All coordinates are **CSS pixels in page coordinates** (origin: top-left of the document at scroll 0) unless a field name ends in `_px` (device pixels). Names are (P).

## 4. API Surface

**No HTTP endpoints, no BullMQ jobs, no events** (F-24: no `/internal/*`; events are 1.4's; 2.2 §4 adds none). 2.3 exposes (a) the module slot function, (b) a pure library used by 3.2, 3.1 and 2.10, (c) files and documents, (d) configuration keys, (e) one optional developer command.

### 4.1 Module slot and phases

The slot is fixed by 2.2 (§4.4): `capturePage(ctx: AttemptContext, mode: 'full' | 'viewport_steps'): Promise<ModuleResult>` (slot `pageCapture`). It is called once per attempt, in S0, S1 and S2 (`full` for S0 and S1, `viewport_steps` for S2), never in S3. 2.2 lists 2.3's work under two steps (`capture` then `extract`) but defines one function; 2.3 resolves this by calling `ctx.heartbeat('extract')` itself at the boundary between its capture phases and its snapshot phase (OQ-2.3-5, owner 2.2).

**Call sequence in `full` mode, S0** (caps are 2.2/2.9's decided numbers; the split inside them is OQ-2.3-4):

| # | Phase | Step label | Work | Page state | Output | Bound |
|---|---|---|---|---|---|---|
| P0 | `PREPARE` | `capture` | Count nodes against `limits.dom_max_nodes`; read document facts; scroll to 0; resolve `ignore_selectors` to element handles | motion | facts in report | seconds, [Estimate] |
| P1 | `SETTLE` | `capture` | Scroll pass: steps of `CAPTURE_SCROLL_STEP_PX` with `CAPTURE_SCROLL_STEP_WAIT_MS` waits; track height growth, late overlays, scroll lock; return to top; wait `CAPTURE_SCROLL_FINAL_WAIT_MS`; `ctx.awaitReady({reason: 'after_scroll_pass'})` (substep, not a step change) | motion | `scroll` in report | `LIMIT_SCROLL_PASS_S` (20 s), ≤ `LIMIT_SCROLL_MAX_STEPS` (40) steps |
| P2 | `INSPECT` | `capture` | Read-only probes in the motion state: hazards (§5.2), motion facts, media boxes, candidate section roots with motion-state bounds; two reads ≥ 500 ms apart for moving things (counters, carousels, marquees) | motion | hazard evidence, `bounds_motion` | inside `LIMIT_SECTION_CAPTURE_S` (20 s) |
| P3 | `MOTION_SHOTS` | `capture` | `freezeTransitions()` just before each shot; above-the-fold viewport shot, stability frame, full-page shot (tiles if needed), region shots, pinned-state shots; frame selection where counters were detected (R18) | motion | `m-*` shots | same |
| P4 | `ENTER_STATIC` | `capture` | `ctx.passes.enterStatic()`; wait for quiet with `ctx.stability`; pause autoplay videos in place (R14); return to top | static | modification log | same |
| P5 | `MEASURE` | `capture` | Section detection (§5.3) in the static state; bounds; straddle check; shared-region confirmation; crop plan; pass hints | static | section map (in memory) | same |
| P6 | `STATIC_SHOTS` | `capture` | Same shot list as P3 in the static state | static | `s-*` shots | same |
| P7 | `EXIT_STATIC` | `extract` | `ctx.passes.exitStatic()`; verify the motion state is restored (reduced-motion media query false, no injected node); scroll to 0; `ctx.heartbeat('extract')` | motion | `motion_state_restored` in report | — |
| P8 | `SNAPSHOT` | `extract` | Rendered HTML, DOM snapshot, computed styles, page metadata, accessibility tree, performance timings, in this order of priority (R27) | motion | `rendered_html`, `dom_snapshot`, … | `extract` 20 s, **shared with 2.4** (OQ-2.3-4) |
| P9 | `FINISH` | `extract` | Write `section-map.json` and `page-capture-report.json`; register files with `ctx.output.add`; return `ModuleResult` | — | | small |

The page is left at scroll 0, in the motion state, with no remaining modification, for 2.4's `extractMedia` (2.2 §4.4 step 5).

**Behaviour by strategy and mode** (the rung is chosen by 1.4, never by 2.3: 2.2 R3):

| Aspect | S0 `full` | S1 `full` | S2 `viewport_steps` | S3 |
|---|---|---|---|---|

**`ModuleResult`** (2.2 §4.4): `{status: 'ok' | 'partial' | 'failed' | 'timeout' | 'skipped', flags?, detail?}`.

| Status | When |
|---|---|
| `ok` | Every phase of the rung finished and every planned output exists |
| `partial` | The budget or a bound cut some outputs, a non-essential output failed (for example accessibility), or a flag was raised. Finished files stay in the manifest (2.2 §4.4) |
| `timeout` | The `AbortSignal` fired; what exists is kept |
| `failed` | **No raw screenshot of any role could be produced** (page crash, every shot call failed), or `dom_max_nodes` exceeded. 2.2 ends the attempt `failed` with the module's reason |
| `skipped` | Never in V0 (S3 does not call the module) |

`ModuleResult.reason_code` (wave-3 review) (a field of 2.2's `ModuleResult` since this review; 2.2 §4.4) is set **only when `failed` or `timeout`**: `RESOURCE_LIMIT` (detail `limit: 'dom_max_nodes'`), `CRASHED` (detail `kind`), `TIMEOUT` (detail `phase`); 2.2 §5.4 copies it into the attempt. `detail` (P) carries, in addition to the report summary: `passes`, `shots {count, bytes, tiled}`, `sections {count, method_counts, coverage_ratio, weak}`, `hazards {detected[], resolved[], unresolved[]}`, `budget {used_ms, cut_at_phase}`.

### 4.2 Pure library (no browser, no I/O except the bytes passed in)

Used by 3.2 (crop execution), 3.1, 2.10 and the admin. Module `services/page-capture`, folder `lib/` (P, OQ-2.3-6). No function opens a page.

| Function | Input | Output | Errors | Idempotency |
|---|---|---|---|---|
| `parseSectionMap(json)` | The document | A typed `SectionMap`; unknown `schema_version` newer than supported is refused | `UnsupportedSchemaVersion`, `InvalidSectionMap` | Pure |
| `planSectionCrops(map, shots)` | Section map + index `shot_id → {width_px, height_px, dpr, tile?}` | `CropPlan[]`: `{order_index, capture_pass, source_shot_ids[], rect_px, expected_width_px, expected_height_px, status}` | `ShotMissing` (a planned source shot is not in the index → that crop is `not_captured`, not an exception) | Pure; same input, same plan |
| `cropInputHash(plan, sourceSha256s)` | A plan + the sha256 of each source blob | 64-hex string over sources + `rect_px` + `algorithm_version` (the 1.3 cache key input) | — | Pure |
| `renderSectionCrop(plan, bytes)` | A plan + the bytes of its source shot(s) | `{bytes, width_px, height_px}` — a cut with **no resampling**, tile join if the plan lists tiles in order | `CropOutOfBounds`, `ImageDecodeFailed`, `UpscaleRefused` (never produces an image larger than its source: DC-20, 1.3 E16) | Pure |
| `sectionOverlay(map, shotBytes)` | Map + one shot | An image with section boxes drawn (developer and admin aid, §4.5) | — | Pure |

**Rounding rule for crops (P, R12).** Each horizontal edge `y` (CSS px) becomes `round(y × dpr)` in device pixels, and the same value is used as the end of one section and the start of the next, so contiguous sections tile without gap or overlap. The left edge uses `floor` and the right edge `ceil` of `x × dpr`, clamped to the shot. Sections are never resized.

**Crop execution** (who runs `renderSectionCrop`, when, with which library, and for which units) is OQ-2.3-2.

## 5. Business Rules & Edge Cases

### 5.1 Rules

| # | Rule | Basis |
|---|---|---|
| R1 | 2.3 runs only inside the child through the `pageCapture` slot. It never connects to Postgres, Redis or R2, holds no secret, writes only under `output_dir/page/`, and registers files only through `ctx.output.add` | F-20, 2.2 R2 |
| R2 | **Everything is bounded:** every wait, scroll, `evaluate` and screenshot receives the `AbortSignal` and is capped by the phase budget and the remaining attempt budget (the smaller); no loop exists without a step counter; no single synchronous job in the child's event loop exceeds about 1 s [Estimate], so heartbeats keep flowing | DC-01, DC-03, 2.2 R4, R5 |
| R3 | **Evidence, not verdicts.** 2.3 records measurements, hints and flags. It never scores, never classifies, never decides publishability, never labels a section type, never decides which pass is better | DC-06, DC-10, 2.2 R17, F-27, 4.3 |
| R4 | **No interaction, no evasion.** The only things 2.3 does to a page are scrolling and the reversible style and playback changes in R14. No click, hover, key press, form input, dialog handling or navigation; carousel controls, menus and tabs are never touched (those states are 2.7's, V1). Any main-frame navigation caused by scrolling is aborted by 2.2 (R8, R15) | F-16, F-17, DC-08, SC-03, 2.2 R15 |
| R5 | **The viewport is never resized** after context creation: no `setViewportSize`, no device-metrics override for tall shots. Viewport, `screen` and DPR come from the profile. After each shot `innerHeight` and `innerWidth` are compared with the profile; a difference is recorded as `viewport_unchanged = false` and the shot is retried once by another method | DC-16 (`100vh`), DC-20, 2.2 §5.6 |
| R6 | **Sharp, never upscaled.** Raw shots are taken at the profile's `device_scale_factor` (desktop 2, mobile 3). Crops are cuts without resampling. Any size reduction (display WebP, thumbnails) is a derived artifact made by another Part | [Decision] DC-20, F-12; 1.3 R5 |
| R7 | **Two passes in S0, one in S1 and S2.** Motion first (the page as it naturally is), then static (reduced motion plus freeze, via `PassController`). Both are views of one navigation (2.2 R23); the motion state is restored before the DOM-level snapshot (2.2 R12) | DC-20, 2.2 R12, R23, OQ-2.2-14 |
| R8 | **Section bounds come from the DOM.** `getBoundingClientRect` plus the scroll offsets at scroll 0 gives page coordinates in CSS px; device px = × DPR. The canonical bounds are measured in the **static** state (doc 08); the same root elements are measured again in the motion state for the motion crops; a root that is not the same element in both runs gets `bounds_motion = null`. A DOM method always runs before any visual method | [Decision] DC-21; doc 08 |
| R9 | **Segmentation order:** semantic landmarks, then layout blocks (§5.3); `detection_method` records which produced each section. Slivers below the minimum height are merged into a neighbour, never given their own image, unless the root is a landmark header, nav or footer. Merging is recorded in `merged_from` | DC-21, doc 08, doc 06; doc 22 §8 check 12 |
| R10 | A section is the **outermost** qualifying element; nested qualifying elements are not separate sections. Fixed, sticky and absolute elements are sections only when they are landmark `header`, `nav`, `footer` or `[role=banner|navigation|contentinfo]` roots; they are marked `in_flow = false`. Floating widgets, chat bubbles, cookie remnants and bottom bars are never sections: they are hazard evidence | DC-16, F-25 (stable order index), doc 08 |
| R11 | **No type labels.** `landmark` is the element's tag or role as found in the DOM; the 25 types and `unknown` are assigned by 4.3 | F-27, 4.3 |
| R12 | **One source shot per section image.** The default source is the pass's full-page shot (or the ordered tiles of that one shot). Sections that share an animated region take their image from that region's single shot. A crop is never assembled from shots taken at different moments; where only that would be possible, the image is `seam_risk` or `not_captured` and the section is flagged | [Decision] DC-20; field: the Stripe ribbon seam |
| R13 | **Media straddles are detected, never hidden.** For every section edge, media elements whose box crosses the edge are listed in `media_edges`. What 2.3 does about a straddle is OQ-2.3-12. DOM bounds are never silently altered | [Decision] DC-21, MB§60 |
| R14 | **The DOM is not modified.** 2.3 adds no attribute, class, id or node. The only changes it may make are reversible and logged in `modifications[]`: the freeze style and reduced-motion emulation through `PassController`; pausing autoplay `<video>` in place during the static pass; and, if the spike adopts it (OQ-2.3-13), converting bottom-anchored fixed layers to absolute positions for one full-page shot. Each is restored in `finally`. Elements are tracked by handle, not by marker | §6 immutability, MB§60, 2.2 R12 |
| R15 | Everything 2.3 changed or hid is listed in the report, so a reviewer can tell evidence from our intervention | MB§60 spirit |
| R16 | **Settle pass:** steps of 400 px every 200 ms, return to the top, wait about 3 s, then `awaitReady` again. These values are [Field observation]; the pass is a fallback under the readiness detector, not a replacement (2.2 §5.2). It stops at `LIMIT_SCROLL_MAX_STEPS` or `LIMIT_SCROLL_PASS_S`, whichever first; it stops early if `scrollY` does not advance after the first step while the page is taller than the viewport (`scroll_locked`) | [Decision] doc 22 §5, §11; doc 08; F-11 |
| R17 | Every shot and the DOM snapshot are taken at **scroll 0** after the page is quiet; the page is left at scroll 0 for 2.4 | doc 08 |
| R18 | **Frame selection is bounded.** Where counters or number animation were detected in the viewport, up to `CAPTURE_FRAME_COUNT` candidate frames about `CAPTURE_FRAME_SPACING_MS` apart are taken; the first frame whose counter texts equal the previous frame's is kept; otherwise the last frame is kept and the section is flagged `counter_unsettled`. Only the selected frame is stored; the candidate log goes into the report | [Field observation] capture.md, doc 08 (Stripe "Global GDP"); OQ-2.3-15 |
| R19 | **Stability evidence for the gate:** one extra above-the-fold frame about 1 s after the viewport shot, per pass, stored as `stability_frame`. 2.3 does not compute the difference (2.10 does) | doc 22 §8 check 9, OQ-2.3-17 |
| R20 | **Every DC-16 hazard has detection, technique, fallback and fixture** (§5.2). What no technique fixes sets the flag `hazard_unresolved` and a report entry; what happens next (needs review, never auto-published) is 2.10's | [Decision] DC-16 |
| R21 | **DOM snapshot** is bounded by `dom_max_nodes`; covers the main frame and open shadow roots; records iframes as boxes with the `src` host (no content); stores text nodes with boxes so 4.2 can read text DOM-first; stores an attribute allow-list; **never stores the value of any form field**. Cross-origin iframe content, closed shadow roots and canvas pixels are out of V0 | F-19 spirit, MB§14, MB§60, OQ-2.3-18 |
| R22 | **Rendered HTML** is the serialization of the live DOM in the motion state after `exitStatic`, with no node of ours present. It is raw evidence; stripping scripts and styles for hashing is 3.4's (F-25, DC-15) | F-25, DC-15 |
| R23 | **Accessibility tree:** the browser's full tree, not the "interesting only" subset, through whatever API the pinned Playwright offers; if unavailable the document is skipped (`partial`), never a failure | doc 08, FL M, OQ-2.3-21 |
| R24 | **Performance:** raw entries only, no scoring (9.2's). `inp` is `null` in V0 because no interaction is performed (F-17, R4) | FL N, OQ-2.3-22 |
| R25 | **Page metadata** is read from the same DOM state and stored as found (truncated with a flag at its cap); canonicalization, normalization and interpretation belong to 2.1 and later Parts | FL B, 2.1 |
| R26 | **Partial results:** finished files stay in the manifest. `failed` only when no raw screenshot exists; a missing snapshot document, section map or report is `partial` | 2.2 §4.4, DC-10 |
| R27 | **Priority when the budget is short** (what is dropped first is listed last): (1) document facts and section bounds, (2) static above-the-fold shot, (3) static full-page shot, (4) page metadata, rendered HTML and DOM snapshot, (5) motion above-the-fold and full-page shots, (6) region and state shots, (7) accessibility tree, computed styles, performance, (8) stability frames. Each pass may use at most about half of the shot budget so one pass cannot starve the other (OQ-2.3-4). ### 5.3 Section segmentation (deterministic; V0 methods `dom` and `layout_block`)

Runs twice: in the motion state at P2 (roots and `bounds_motion`) and in the static state at P5 (canonical bounds). All thresholds are `CAPTURE_SEGMENT_*` placeholders ([Estimate], OQ-2.3-11). "Visible" = has a box, not `display: none`, not `visibility: hidden`, not zero-size. "Wide" = width ≥ `MIN_WIDTH_RATIO` × viewport width.

| Step | Rule | `detection_method` |
|---|---|---|
| 1 | **Landmark candidates:** visible `header`, `nav`, `main`'s direct block children that are `section` or `article`, `footer`, and elements with role `banner`, `navigation`, `region`, `contentinfo`. Candidates inside another candidate are dropped (R10). Doc 08's field selector `header, section, footer, main > div` is the starting heuristic: `main > div` joins only in step 2 | `dom` |
| 2 | **Choose the section level.** If step 1 gives at least two vertically stacked wide candidates covering at least `MIN_COVERAGE` of the page height, use them. Otherwise take `main` (or `body`), descend through wrappers that have one significant child (a wrapper with a single visible child of similar size), and use the first level that splits the content into at least two wide, vertically stacked blocks covering at least `MIN_COVERAGE`: the wide direct children of that level | `layout_block` |
| 3 | **Fill gaps.** A vertical gap of at least `GAP_PX` between selected blocks that contains visible content (a bare `div`) becomes a `layout_block` section; a smaller gap is ignored | `layout_block` |
| 4 | **Merge slivers.** A non-landmark block shorter than `MIN_HEIGHT_PX` is merged into the neighbour it shares the longer edge with; landmark `header`, `nav`, `footer` stay separate even if short (the gate exempts nav and announcement bars; deciding which is which is 4.3's) | keeps the neighbour's method |
| 5 | **Out-of-flow landmarks** (fixed or sticky header or nav) are listed with `in_flow = false`; they may overlap the first in-flow section; coverage is computed on in-flow sections only | `dom` |
| 6 | **Straddle detection** (DC-21): for each section top and bottom edge, media elements (`img`, `picture`, `video`, `canvas`, `svg`, `iframe`, `object`, `embed`, and elements with a non-`none` `background-image` that are not the section root) whose box crosses the edge by more than 1 px are listed in `media_edges`. Resolution policy: OQ-2.3-12 | — |
| 7 | **Shared regions** (hazard 7) are grouped; members get the same `shared_region_id` and a common region shot | — |
| 8 | **Weak result.** No section, coverage below `MIN_COVERAGE`, or one block for the whole page: emit one `layout_block` section covering the page and set `segmentation_weak` (2.10 sees it with gate check 12) | `layout_block` |
| 9 | **Visual (pixel) segmentation** is not run in V0; `visual` stays a reserved value of `section.detection_method` (OQ-2.3-10) | — |

`order_index` runs in page order (top to bottom, ties by document order). Overlay sections take their place by `y`. Because F-25 matches sections by (page, type, order index), floating non-landmark layers never enter the list (R10).

Because the step caps add up to more than the child's total, the total is the binding limit (2.2 OQ-2.2-5); R27 says what is dropped first.

### Reliability

- 2.3 can lose at most the current attempt (DC-03) and holds no durable state (R1).
- Every modification of the page is reversible and restored in `finally`; a failed restore ends in `motion_state_unverified` and a logged modification, never a silent change (R14, E28).
- Partial results are normal: the manifest keeps finished files; `failed` is reserved for "no screenshot at all" (R26).
- The section algorithm is pure given the measurements and is versioned, so a regression is visible as a version or output change in the canary (R30, DC-12).
- A change to 2.3 (algorithm, techniques, flags) needs the torture suite and the golden-set canary before it ships (DC-12, 1.1 R11).

### Security and privacy

- Crawled pages are untrusted code. 2.3 injects measurement functions into the page; they run in the page's world because layout reads need its objects, so a hostile page can distort measurements (E25) but cannot reach the host (container boundary, F-20, 2.2 R2).
- No form-field values, cookies, storage or request bodies enter any document (R21, R32). The DOM snapshot and rendered HTML may contain personal data that is public on the page (names in testimonials); text screening before indexing is 3.3's (F-19); raw evidence stays in the private bucket (1.3 R17); only screenshots are ever displayed publicly (F-18); the DOM, HTML and styles are never public.
- 2.3 makes no request, follows no link and performs no state-changing action (R4, R34, F-16, F-46).

### Cost recording

2.3 records no `CostEvent`. It reports per-phase timings, shot counts and bytes in the report so 2.9 can record browser time through 1.6 (2.2 §7).

### Observability (data for 1.8)

Per attempt (all from the report): phase timings and budget used; scroll steps and stop reason; css height; tile count; shots and bytes; sections, method counts, coverage; hazards detected, resolved, unresolved by id; frame-selection retries; node count and snapshot sizes; limits hit; flags `truncated`, `hazard_unresolved`, `segmentation_weak`. Metric names (P): `pagecapture_phase_ms`, `pagecapture_shots_total`, `pagecapture_bytes`, `pagecapture_sections`, `pagecapture_hazard{id,outcome}`, `pagecapture_truncated_total`, `pagecapture_segmentation_weak_total`, `pagecapture_crop_through_media_total`. Useful derived rates: `hazard_unresolved` rate per hazard, `segmentation_weak` rate, straddle rate, S0 → S1 rescue rate for 2.3's failures, share of units cut by the budget. Logs carry `run_id, job_id, unit_id, attempt, strategy, step, substep` (1.4 `logContext`) and never page text (R32).

## 8. Open Questions & Assumptions

### Open questions

Each entry: question — why it matters — **suggested default (a suggestion, not a decision).**

- **OPEN QUESTION OQ-2.3-1:** Is a section crop raw evidence or derived? (carried: OQ-1.2-12, review-wave-2 §4; OQ-1.3-5) — It decides what 1.3 registers, where the crop's file is created, and how much storage a page needs (crops tile the page, so raw crops would duplicate every shot's pixels). 1.2's `section_artifact` allows both; 1.3 lists `section_crop` as a derived kind "only if 2.3 crops rather than shoots". — **Suggested default:** a crop is **derived** (`derived_artifact`, kind `section_crop`, `raw_artifact_ids` = the source shot(s)): it contains no pixel that is not in a stored raw shot, it is a pure function of shot + rectangle + `algorithm_version` (so it is cacheable by `input_hash` and regenerable, §6), and it avoids doubling raw storage. What stays **raw** are the shots taken for the purpose of a section image that no crop of a full-page shot can give: `region` and `state` shots (captured pixels at a moment that cannot be recreated). Alternative if the founder prefers: 2.3 cuts crops in the child and registers them as raw `SCREENSHOT` (`role = section_crop`); this needs no later step but doubles screenshot storage and changes 2.2's manifest rules not at all.
- **OPEN QUESTION OQ-2.3-2:** Who runs `renderSectionCrop`, when, with which image library, and for which units? — The child has no credentials and 2.2's manifest carries only raw types, so derived crops cannot be produced in the child; `registerDerivedArtifact` needs the registered raw ids. The gate runs before normalization. — **Suggested default:** 3.2 (in `worker-app`) calls `planSectionCrops` and `renderSectionCrop` for each unit it normalizes (`ACCEPTED`, and `NEEDS_REVIEW` if 3.2 normalizes those), registers the result with `registerDerivedArtifact` (`producer = 'page-capture'`), and `recordScreenGraph` links it as `section_artifact` `crop`; the admin renders a crop on the fly from the raw shot (pure function) when it reviews a unit that is not normalized; the image library is chosen once with 3.1 (also needed for canonical screenshots). The gate does not need crops: it works from raw shots and the section map. (wave-3 review) Correction: the gate **does** need crops for G04, G09b and G12c (2.10 §5.2). It slices them in memory with the same pure `planSectionCrops` + `renderSectionCrop` (`lib/`), before any `section_crop` is registered, and registers nothing (2.10 OQ-2.10-31).
- **OPEN QUESTION OQ-2.3-3:** What does recipe `ignore_selectors` mean? (carried: OQ-2.2-18 b; 1.5 owns the field, doc 22 §7 says "selectors to ignore") — Without a definition, a recipe cannot fix a floating widget, and two Parts may read it differently. — **Suggested default:** matching elements are excluded from stability and frame-selection checks (2.2 R21), from hazard counting, from section-root candidacy and from "fixed element" coverage; they are **never hidden, removed or altered** (MB§60), stay in pixels and in the DOM snapshot with an `ignored` flag, and are listed in the section map (`ignored_nodes`). Hiding an element would need a different recipe field (not a V0 field, 1.5 R-12 limits recipes to five fields).
- **OPEN QUESTION OQ-2.3-4:** How are 2.2's step budgets spent inside 2.3, and who owns the numbers? (carried: OQ-2.2-5, OQ-2.2-6, OQ-2.9-7, OQ-2.9-8; review-wave-2 §4) — The step caps add up to more than 90 s; doc 22 §5 has lines for the scroll pass (20 s) and "section capture" (20 s) but none for the two passes' page shots; `extract` (20 s) is shared by 2.3's snapshot and 2.4's media extraction; the founder's machine may be slower. — **Suggested default:** the child's total is the attempt's remaining time minus the 30 s upload reserve (≈ 60 s, 2.2's suggestion); inside `capture` (40 s): the scroll pass 20 s, and `LIMIT_SECTION_CAPTURE_S` (20 s) covers **everything after the scroll pass** (inspect, both passes' shots, measurement, region and state shots); each pass may use at most about half of that, so a slow motion pass cannot starve the static pass; inside `extract` (20 s): 2.3's snapshot is limited to about 10 s of it and 2.4 keeps the rest [Estimate]; when budget is short, work is dropped in the order of R27 and the result is `partial` with `truncated` where pixels are missing. All keys come from one defaults table shared by 2.2, 2.3, 2.4 and 2.9; the real numbers come from the spike.
- **OPEN QUESTION OQ-2.3-5:** Interface gaps in 2.2's frozen slot. - **OPEN QUESTION OQ-2.3-7:** Single-shot size limit, tiling, and the meaning of `screen_artifact.seq`. (carried: OQ-2.2-25, OQ-1.3-10) — A mobile page of 12,000 CSS px is 36,000 device px; the gate's height maximum is 30,000 CSS px (90,000 device px at DPR 3), which cannot be one shot. 1.2 defines `seq` only as the order of S2 viewport shots. — **Suggested default:** measure the pinned Chromium's limit in the spike and publish it as `CAPTURE_SHOT_MAX_DEVICE_PX`; above it take ordered vertical tiles of one state (static pass: join freely; motion pass: a section crossing a seam under animated art is `seam_risk`); tiles carry `meta.tile {index, count, y_css, h_css}` and `seq` = tile index; 1.2 confirms that `seq` also orders tiles of a `full_page` row. Owner for `seq`: 1.2. (wave-3 review) Applied in 1.2 §3.3 (`screen_artifact.seq` orders the tiles of a tall `full_page` shot as well as S2 viewport shots).
- **OPEN QUESTION OQ-2.3-8:** Pass mechanics that depend on 2.2's choice (OQ-2.2-14). — (a) With the suggested in-place switch, `exitStatic` must restore the motion state before the snapshot and 2.3 must be able to verify it; (b) layout can differ between passes; (c) in S1 and S2 the freeze CSS was on from the start, so recorded animation and transition values are the frozen ones. — Computed-style values for motion tokens (V1, 4.8) would be wrong without knowing. — **Suggested default:** (a) 2.3 verifies (reduced-motion media query false, no injected node) and records `motion_state_unverified` otherwise; (b) bounds are measured per pass, static canonical and motion for motion crops, `css_height_*` recorded for both; (c) `computed_styles.motion_values_valid = false` in S1 and S2.
- **OPEN QUESTION OQ-2.3-9:** What 2.3 produces in S2 beyond viewport shots, and how many shots. (carried: OQ-2.2-26) — Gate check 12 needs to know what a `degraded` unit contains; 2.2's suggestion is "section bounds, no per-section images". — **Suggested default:** S2 records the section map with bounds and landmarks (cheap) and marks every image `not_captured`; viewport shots at consecutive positions, at most `CAPTURE_S2_MAX_SHOTS` (12 [Estimate]), then `truncated`; DOM snapshot, accessibility tree and page metadata are kept (2.2 §4.5); computed styles and performance are skipped. Alternative: cut crops from a single viewport shot when the whole section fits in it.
- **OPEN QUESTION OQ-2.3-10:** Does V0 include visual (pixel-based) segmentation, the third method in doc 08 and doc 06? — DC-21 says DOM bounds come "before any visual segmentation", so a visual method is expected somewhere; the model for it is not decided (doc 06) and a new image-analysis system has a maintenance cost for a solo founder (F-35 spirit). — **Suggested default:** not in V0; `visual` stays a reserved value of `section.detection_method`; weak results are flagged `segmentation_weak` and reviewed; the spike counts how often `dom` and `layout_block` fail gate check 12 and the decision is revisited if that rate is above the inbox budget (DC-17, ≤ 5% of units).
- **OPEN QUESTION OQ-2.3-11:** Values of the segmentation parameters (minimum width ratio, minimum height, minimum coverage, gap). — They decide where sections begin and end for every site. — **Suggested default** ([Estimate] placeholders, calibrated on the golden set and the 200 labelled sections of F-29): 0.8, 120 px, 0.8, 24 px (120 px and 80% equal gate check 12's starting values).
- **OPEN QUESTION OQ-2.3-12:** What does 2.3 do when a media element crosses a section edge (DC-21)? — Overlapping device mockups and hero images are common; if every one were a gate failure the inbox (DC-17) would fill. The rule "crop through media is a gate failure" fixes the verdict but not the remedy; the remedy must not invent pixel boundaries. — **Suggested default:** **merge** the two sections whose shared edge the media crosses (the merged box is still DOM-derived: top of the first, bottom of the second; `merged_from` and `flags: edge_merged` record it), provided the merged height is at most 2 × the viewport height [Estimate]; otherwise keep the DOM bounds, set `flags: media_straddle` and leave the verdict to the gate. Alternatives: extend one section to contain the media and allow a documented overlap; or move the edge to the media's edge (rejected as default because it makes bounds non-DOM).
- **OPEN QUESTION OQ-2.3-13:** Which candidate technique becomes the default for each hazard, and what the pinned browser actually does. — DC-16 lists candidates, "not guarantees". Unknowns to measure in the spike: whether the chosen full-page capture call renders viewport-fixed layers once, per viewport or not at all; whether it changes `innerHeight`; whether converting bottom-anchored fixed layers to absolute positions is safe; whether forcing reveal styles is ever acceptable. — The default must be proven on the fixtures, not argued. — **Suggested default:** use §5.2's first technique per row; do **not** adopt forced reveal styles or hiding of any element; adopt "convert bottom-anchored fixed layers to absolute for one shot" only if `hazard_sticky_fixed` shows it is needed and restores cleanly; record the measured behaviour of the pinned Chromium as a constant table next to `CAPTURE_SHOT_MAX_DEVICE_PX`.
- **OPEN QUESTION OQ-2.3-14:** Scroll-pass step rule for tall pages and the stop conditions. — 40 steps of 400 px cover only 16,000 CSS px, but the gate's maximum is 30,000 px, so lazy content on a 20,000 px page would stay unloaded. Stepping by a full viewport still brings every pixel into view but skips scroll-scrubbed animations. — **Suggested default:** 400 px while `ceil(height / 400) ≤ 40`; otherwise widen the step up to the viewport height; beyond that stop at 40 steps and set `truncated`; stop early when `scrollY` does not advance (E6) or the height keeps growing (hazard 10).
- **OPEN QUESTION OQ-2.3-15:** Frame selection: how many frames, spacing and the "settled" test. — The field rule is "4–6 frames about a second apart, keep the settled one" but pixels cannot be compared when a WebGL ribbon keeps moving. — **Suggested default:** `CAPTURE_FRAME_COUNT` 6 and `CAPTURE_FRAME_SPACING_MS` 1000; the test compares the **text** of the detected counter elements between frames, not pixels; applied only to viewports where hazard 8 or 7 was detected; the first unchanged pair wins.

(wave-3 review) Revised: 2.10 is the **only** writer of `section_artifact.is_selected`, through `applyGateToGraph` (called by 3.2 inside `recordScreenGraph`'s transaction, 1.2 §3.8); 3.2 does not write it. 2.3 still supplies only `pass_hint`.
- **OPEN QUESTION OQ-2.3-17:** Evidence for gate check 9 ("two captures about 1 s apart"). — The check needs two frames; computing the difference needs an image-diff routine. — **Suggested default:** 2.3 stores the second frame (`stability_frame`) and 2.10 computes the difference; 2.2's `StabilityProbe` stays for in-child waiting only. If 2.10 prefers a number from the child, 2.3 can add `stability_diff` using the same routine as the probe.

Chromium's DevTools protocol offers a DOM snapshot call that returns structure, boxes and a chosen subset of computed styles in one request; in-page JavaScript is the alternative. — **Suggested default:** the spike picks the cheaper of the two on the 20 sites; content as §3.4 and R21: allow-listed attributes (including `id`, `class`, `role`, `aria-*`, `href`, `src`, `srcset`, `alt`, `type`, `name`, `for`, `lang`, `data-*` names only), text nodes with boxes, no form-field values, main frame and open shadow roots, iframes as leaves, size capped by `dom_max_nodes` and the blob cap with a `truncated` flag.

- **OPEN QUESTION OQ-2.3-20:** Rendered HTML versus the server's response body, and secrets in raw HTML. — F-25's change signal and V1 technology detection (4.7) may want the unrendered body; inline scripts and hidden inputs on a public page can hold tokens; altering the serialization would alter raw evidence. — **Suggested default:** V0 stores the rendered HTML only (`HTML`, `role = rendered_html`), the response body only on S3 (2.2); form-field values are already omitted from the DOM snapshot but left as serialized in the rendered HTML; secret screening happens before indexing (3.3, F-19) and the raw blob stays private (1.3 R17); revisit when 4.7 is specified.

### Assumptions

- **[Assumption] A1:** 2.3 lives in the child process of 2.2, in Node/TypeScript with Playwright's `Page`; `page.evaluate` runs in the page's world (E25).
- **[Assumption] A2:** The page is at scroll 0 when bounds are read, so page coordinates equal viewport coordinates plus the scroll offsets; the document scrolls (E6 covers the exception).
- **[Assumption] A3:** The static state is the canonical measurement state (doc 08); re-measuring in the motion state is cheap (DOM reads only).
- **[Assumption] A4:** The viewport and `screen` stay fixed for the attempt (2.2 §5.6); the static pass does not need a different viewport.
- **[Assumption] A5:** Section crops are deterministic functions of shots and rectangles and can run in `worker-app` without a browser (OQ-2.3-1, -2).
- **[Assumption] A6:** Hazard techniques are candidates until the fixtures and the spike prove them (DC-16, doc 23); nothing in §5.2 is a guarantee.
- **[Assumption] A7:** Reduced motion plus a style tag that pauses animations and transitions (doc 08) is what `enterStatic()` does; it does not pause `<video>`, so 2.3 pauses videos itself.
- **[Assumption] A8:** One navigation, in-place switch between passes (OQ-2.2-14 suggested default); if 2.2 later uses two navigations, only the internals of `enterStatic()` change.
- **[Assumption] A9:** Raw screenshot encoding and compression follow 1.3's suggestions (OQ-1.3-9: PNG; gzip for text).
- **[Assumption] A10:** The document schemas live in `packages/schemas` (1.1) and the module in `services/page-capture` (OQ-2.3-6).
- **[Assumption] A11:** The Chromium full-page capture works up to a limit that the spike measures; above it tiling is used (OQ-2.3-7).
