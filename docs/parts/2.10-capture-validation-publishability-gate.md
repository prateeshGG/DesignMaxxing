## 1. Purpose & Scope

**Purpose.** A capture is only evidence that something was photographed. 2.10 decides whether what was photographed may ever be shown to a user (DC-06: **captured never means publishable**). For every captured attempt it runs the automated checks of doc 22 §8, turns the results into a `quality_score` (0–100) and a verdict, hands the verdict to 1.4 so the unit moves to `ACCEPTED`, `NEEDS_REVIEW`, a retry, `QUARANTINED`, `BLOCKED` or `SKIPPED`, and later sets `publish_status` on the screens and sections that pass. It also owns the **bad-page fingerprint library** (known-bad renders such as challenge pages, blank pages, 404 pages and consent walls) and the rule that decides when an accepted screen becomes visible (`eligible` → `published`), including the founder's 5% spot check of each batch (doc 22 §8).

The gate is the second half of the "never get stuck, never publish unusable data" promise (doc 22 §1, class B "silent bad data"). It must be **deterministic** (same evidence and same gate version give the same result), **bounded** (DC-01), **cheap** (it runs on stored evidence only, with no browser and no request to any site), and **calibratable** (every threshold is configuration, every result is stored with the numbers behind it, so the 20-site spike E2 can tune it, F-29).

**Phase:** `[V0]`. Later-phase hooks are marked **[hook]** and are compatibility notes only (F-40).

## 3. Data Model

**Conventions.** Table and column names follow 1.2's conventions C1–C14: snake_case singular, `id uuid` UUIDv7 generated by `newId()`, `text` + `CHECK` instead of native enums, `timestamptz` UTC, `ON DELETE RESTRICT`. Every name in this section marked **(P)** is proposed (OQ-2.10-40). **JSONB is not used** (1.2 C11 allows it only where a decision names it); numeric measurements get real columns. 2.10 writes its own migrations with 1.2's tool.

### 3.1 The single home of each gate value (answers OQ-1.2-19 and OQ-1.4-23)

Review-wave-1 §4 and review-wave-2 §4 asked for one clear home per value. The problem behind the question: the gate runs **before** normalization, so no `screen` or `section` row exists yet when the verdict is made (1.2 §3.3: 3.2 creates the rows from `ACCEPTED` units, 1.4 §4.5 routes `ev.normalize` to 3.2 on `ACCEPTED` only). A graph column therefore cannot be the first home of a gate value. The proposal below gives every value exactly one writer and one source of truth; graph columns are **write-once read copies** made at normalization, regenerable from the gate tables (derived data, Blueprint §6; 1.2 R10).

| Value | Single home (source of truth) | Written by | Copies and readers | Basis |
|---|---|---|---|---|
| Verdict of one attempt (`ACCEPTED`, `NEEDS_REVIEW`, `REJECTED`, `BLOCKED`, `SKIPPED`) | `capture_attempt.verdict` (1.4) | 2.10, only through `recordValidation` | 2.9 (probe), 4.4, 1.8 | 1.4 §3.6, OQ-1.4-23 |
| Unit outcome (`ACCEPTED`, `NEEDS_REVIEW`, `RETRY_WAIT`, `QUARANTINED`, `BLOCKED`, `SKIPPED`) | `capture_unit.state` (1.4) | 1.4 | everyone | 1.4 §3.8 |
| Why (reason code, small detail) | `capture_unit.reason_code`, `reason_detail`; `capture_attempt.reason_code`, `reason_detail` (1.4) | `recordValidation` | 4.4, 6.4 | 1.4 §3.5–3.6 |
| Unit `quality_score` of one attempt | `gate_result.quality_score` (P) | 2.10 | copy: `screen.quality_score` | DC-06, 1.2 §3.8 |
| Result of each check, with the number behind it | `gate_check_result` (P) | 2.10 | 4.4 (review screen), 6.4, calibration | doc 22 §8, F-29 |
| Section verdict, section `quality_score`, selected pass | `gate_section_result` (P) | 2.10 | copies: `section.quality_score`, `section_artifact.is_selected` | DC-06, DC-20, 1.2 §3.3 |
| `capture_status` ("did evidence get stored") | **Derived**, function `captureStatus(unitId)` (P); no column | — | 4.4, 6.4, 1.8 | DC-06, OQ-2.10-2 |
| `publish_status` | `screen.publish_status` and `section.publish_status` (1.2); **no unit-level `publish_status`** | 2.10 via `setPublishStatus` for `unpublished → eligible → published`; `withdrawn` by 1.5/6.4 | 5.1, 5.2, 6.x (only `published` is user-visible) | DC-06, 1.2 R7–R9 |
| Bad-page fingerprints | `bad_page_fingerprint` (P) | 2.10; 4.4 and 6.4 call its functions | the gate | doc 22 §8 check 3 |
| Publication batch and spot-check outcome | `publish_batch`, `publish_batch_item` (P) | 2.10 | 4.4 (screen), 6.4 | doc 22 §8 lifecycle |

Consequences: (1) between `ACCEPTED` and normalization a unit is publishable only in the sense that its unit state is `ACCEPTED`; no user-facing read can see it, because no `screen` row exists (1.2 R7). (2) `capture_attempt.verdict` stays null if `recordValidation` was a no-op (the unit left `VALIDATING`, for example `closeUnits`); `gate_result.computed_verdict` then records what the gate decided (a different fact: computed versus applied). (3) A rejected attempt keeps its `gate_result` forever, so the history of why the ladder climbed survives (OQ-2.10-39).

### 3.4 State machines

**Gate handling of one attempt** (not stored; logged with `step = validate`). The unit states are 1.4's.

```
capture_unit.captured delivered
  ├─ stale? (unit not CAPTURED for this attempt) ─────────────► drop (idempotent no-op)
  ├─ sibling in flight, first delivery, breaker closed ───────► WAIT: ack, unit stays CAPTURED (§5.6)
  └─ otherwise: beginValidation (T14: CAPTURED → VALIDATING)
        load evidence → run checks → store gate_result
        recordValidation:  ACCEPTED | NEEDS_REVIEW   (T15)
                           REJECTED → RETRY_WAIT | QUARANTINED   (T16 / T17)
                           BLOCKED  → RETRY_WAIT | BLOCKED       (T18)
                           SKIPPED                               (T19)
```

**`publish_status` transitions performed by 2.10** (1.2 R8; the demotions need OQ-2.10-26):

| Transition | Function | When |
|---|---|---|
| `unpublished → eligible` | `applyGateToGraph` | Unit is `ACCEPTED`, the section/screen verdict allows it, and `evaluateCollection('publish')` allows it now |
| `eligible → published` | `publishBatch`, or `applyGateToGraph` in mode `auto` | Spot check passed (or mode `auto`); policy re-checked at that moment (1.5 R-15) |
| `eligible → unpublished`, `published → unpublished` | `dropFromBatch`, `demoteScreen` | A spot check found a bad item, or a re-review demotes it (OQ-1.2-18). **Needs 1.2 to allow the transitions** |
| `any → withdrawn` | not 2.10 | 1.5 / 6.4 takedown (F-18) |

**`publish_batch`:** `open` (items collected) → `sampled` (5% chosen) → `ready` (all sampled items `ok`) → `published`; `held` (a sampled item is `bad`, or the founder holds it) → `ready` or `cancelled` by an explicit logged action; mode `auto` skips `sampled`/`ready`.

**`bad_page_fingerprint`:** `active` ↔ `retired` (retired entries are ignored by matching, kept for audit).

## 4. API Surface

**No HTTP endpoints** (F-24 forbids `/internal/*`; end users never reach the gate). Operators use 4.4 and 6.4 screens or the CLI. All contracts are TypeScript module functions in a 2.10 module (P name `services/publishability-gate`), with payload schemas in `packages/schemas`. **The gate opens no browser and sends no request to any site** (DC-08, F-10): it reads Postgres and stored evidence only.

**Common rules**

| Rule | Detail |
|---|---|
| Auth | In-process calls under the deployable's DB role (1.7). Calls that start from a person carry `actor`, recorded in the row they write |
| Errors | `LeaseLost` does not apply: the gate holds no lease (the lease was cleared at T7). `IllegalTransition` and `NotFound` from 1.4 are treated as "stale, drop" in the consumer. Infrastructure errors (DB, Redis, `BlobNotYetStored`) are thrown unchanged so `consume` retries with 1.4's backoff (F-32) |
| Idempotency | Stated per function. The gate keys everything on `capture_attempt_id`, so a redelivered event changes nothing (F-24, DC-02) |
| Transactions | Each function is one transaction, except the gate handler, which is deliberately two steps (store `gate_result`, then `recordValidation`) and safe to repeat (§5.1 R6) |
| Time | Every wait and loop is bounded and receives an `AbortSignal` (DC-01) |

### 4.1 Queue and consumer

| Item | Value | Basis |
|---|---|---|
| Consumer name / queue | `gate` on `ev.gate` | 1.4 §4.5 (queue reserved for 2.10) |
| Event consumed | `capture_unit.captured` (payload: `crawl_run_id, attempt_id, attempt_no, strategy, flags, canonical_url, device_profile_code, retry_round`) | 1.4 §4.6 |

### 4.2 The gate handler and the check engine

```ts
handleUnitCaptured(env: Envelope<'capture_unit.captured'>): Promise<void>
gateAttempt(input: { unitId: UUID; attemptId: UUID; mode: 'record' | 'dry_run' }): Promise<GateOutcome>
loadGateInput(attemptId: UUID): Promise<GateInput>          // reads Postgres + evidence; no network to sites
runChecks(input: GateInput, cfg: GateConfig): CheckSet       // PURE: images, DOM facts, signatures, fingerprints
resolveOutcome(checks: CheckSet, policy: PolicyDecision, cfg: GateConfig): GateOutcome   // PURE: score, caps, verdict

type GateOutcome = {
  verdict: 'ACCEPTED'|'NEEDS_REVIEW'|'REJECTED'|'BLOCKED'|'SKIPPED';
  reasonCode?: 'GATE_REVIEW'|'GATE_REJECTED'|'BLOCKED'|'CAPTCHA_REQUIRED'|'AUTH_REQUIRED'
             |'HTTP_NOT_FOUND'|'OFF_DOMAIN_REDIRECT'|'NON_HTML_RESPONSE'|'POLICY_DENIED'|'TAKEDOWN';   // 1.4 §3.11 + GATE_REVIEW (P)
  reasonDetail: { gate_version: string; score: number | null; failed_checks: string[];
                  review_reasons: string[]; deny_reason?: string; sibling_unit_id?: UUID; };  // codes and numbers only
  qualityScore: number | null; evaluatedWeightPct: number;
  checks: CheckResult[]; sections: SectionResult[];
  fingerprint?: string;                       // §5.8, only for REJECTED
  retryable?: false;                          // (wave-3 review) (P) set only with REJECTED when no retry can help (e.g. a soft 404); passed to recordValidation
  phash: { motion?: string; static?: string; algo?: string };
};
```

**`handleUnitCaptured` (contract-level pseudocode)**

```
unit = read capture_unit(env.entity_id)                       // handlers re-read state and drop stale events (1.4 §4.4)
if unit.state not in (CAPTURED, VALIDATING) or unit.result_attempt_id != env.payload.attempt_id: return
if unit.state == CAPTURED and mustWaitForSibling(unit): return          // §5.6: ack; unit stays CAPTURED, bounded by 1.4's validation deadline
beginValidation({ unitId, attemptId })                        // T14; no-op if already VALIDATING for this attempt
input   = loadGateInput(attemptId)                            // BlobNotYetStored / DB errors are thrown and retried
checks  = runChecks(input, cfg)                               // bounded by LIMIT_GATE_UNIT_MAX_S
policy  = evaluateCollection({ source_id, purpose: 'publish', now })   // check 15, evaluated last (1.5 R-15)
outcome = resolveOutcome(checks, policy, cfg)
upsert gate_result, gate_check_result, gate_section_result    // replace while capture_attempt.verdict is null
recordValidation({ unitId, attemptId, verdict: outcome.verdict, reasonCode, reasonDetail, fingerprint, retryable: outcome.retryable })   // T15–T19 (wave-3 review: retryable)
wakeSibling(unit)                                             // gate the other viewport if it was waiting (§5.6)
```

| Function | Behaviour | Errors / idempotency |
|---|---|---|
| `handleUnitCaptured` | As above. A drop leaves no trace except a log line | Repeating it for the same attempt recomputes the same result and `recordValidation` is a no-op (1.4 §4.2) |
| `gateAttempt` | The body of the handler for one attempt. `dry_run` writes nothing and never calls `beginValidation` or `recordValidation` (used by `replayGate`, 2.11, 4.6, the CLI) | — |
| `loadGateInput` | Assembles the roles of §3.6: `listRawArtifacts({captureAttemptId})`, the persisted attempt facts, the DOM snapshot, section data, the sibling's evidence, the page-type hint, the job purpose, the library snapshot | `GateInputMissing{role}` becomes `not_evaluable` for that check; a missing mandatory role (no screenshot at all for a non-`no_visual` attempt) is verdict `REJECTED`, detail `evidence_unreadable` (R9) |
| `runChecks` | Pure and deterministic: the same `GateInput`, config and library give the same `CheckSet` (R7). Never reads the clock or the network | — |
| `resolveOutcome` | Applies hard-fail priority, the score formula, caps, section rules and the 80/60 thresholds (§5.3) | — |

## 5. Business Rules & Edge Cases

### 5.1 Rules

| # | Rule | Basis |
|---|---|---|
| R1 | **Captured never means publishable.** `CAPTURED` leads only to `VALIDATING`; only the gate (or a human through 4.4) moves a unit to `ACCEPTED`; only `screen`/`section` rows with `publish_status = 'published'` are user-visible. No code path from `CAPTURED` to `published` skips the gate | DC-06, 1.4 R12, 1.2 R7 |
| R2 | **The gate uses stored evidence only.** It opens no browser and sends no request to any site, so it cannot cause or evade a block | DC-08, F-10 |
| R3 | **Every attempt that reaches `CAPTURED` is gated exactly once.** Redelivery recomputes the same result and changes nothing. Every `REJECTED` attempt keeps its `gate_result` | DC-02, F-24, doc 22 §8 |
| R4 | **Order of work.** Cheap before expensive: `G00`, `G01`, `G02` (facts and text), then `G03`, `G04` (pixels), then the scored checks, then check 15 last. A hard failure ends scoring: `quality_score` is `NULL` ("not scored"), never 0 | DC-01, doc 22 §8 ("check 1–3 and 4 are hard fails, not weighted") |
| R5 | **Verdict resolution** follows §5.3 exactly: hard-fail priority, then score, then caps. `quality_score ≥ 80` and no cap → `ACCEPTED`; `60–79` or a cap → `NEEDS_REVIEW`; `< 60` or a hard failure of kind "bad render" → `REJECTED`; a check that **proves** a block, a missing page or a policy denial → `BLOCKED` or `SKIPPED` (§5.5) | DC-06, doc 22 §8, OQ-1.4-8 |
| R6 | **Two-step write, safe to repeat.** The handler stores `gate_result` and its child rows, then calls `recordValidation`. A crash between the two leaves a `gate_result` without a verdict on the attempt; the redelivery replaces it with the same content and then records. After `capture_attempt.verdict` is set the rows are frozen | DC-14, 1.4 §4.2 |
| R7 | **Deterministic.** No randomness and no clock reads inside `runChecks`. The one "random" element, the DOM↔OCR sample, is a function of the attempt id (§5.2 G13). Same evidence + same `gate_version`, `config_version`, `library_version`, `signatures_version` → same result | DC-02, F-29 |
| R8 | **Missing evidence is not a pass.** A check whose evidence role is absent is `not_evaluable` and leaves the score formula (its weight is removed from both sides); the share of weight actually evaluated is stored and a low share caps the unit at `NEEDS_REVIEW` (`LOW_EVIDENCE`). Nothing is ever scored as passing because it could not be measured | DC-06, "never silently publish a broken capture" (IF§26) |
| R9 | **Unreadable evidence is a bad capture, not an outage.** A screenshot that does not decode, is missing from storage (`BlobMissing`), fails its hash (`IntegrityError`), or has pixel dimensions that disagree with its registered `meta`, gives `REJECTED` with detail `evidence_unreadable` (check `G00`), so the next rung recaptures. `BlobNotYetStored` (the blob is still in the spool on another machine) is not judged: it is thrown and retried | doc 22 §2 row 16, 1.3 §4.4 |
| R10 | **A dependency outage never blocks collection.** If 4.2 (OCR, DOM text) or 3.3 (screening) is unavailable, the affected check is `not_run`, a metric counts it, and the unit continues. Only checks that need no dependency can fail a unit | DC-10 |
| R11 | **Policy is evaluated late and again later.** Check 15 runs last in the handler; `applyGateToGraph` and `publishBatch` each evaluate `publish` again. A takedown or flag change therefore takes effect at the next step, never from a cache | 1.5 R-15, F-18 |
| R12 | **A block stays a block.** A gate `BLOCKED` follows 1.4's rule: one polite retry on the next rung, then `BLOCKED`. The gate never proposes a retry that changes identity, IP, headers or fingerprint, and never solves anything | DC-08, SC-03, 1.4 R10, DC-18 |
| R13 | **Sections are judged one by one.** A section with verdict `REJECTED` is withheld: it is never `eligible`, and a human approval of the unit does not change that in V0. Effects on the unit are in §5.4 | DC-06, DC-21, OQ-2.10-6 |
| R14 | **The gate chooses a pass, it never makes an image.** For each section it picks the motion or the static crop from the two the capture produced (DC-20); it never composites. A section crop that 2.3 reports as composed from more than one shot is withheld | DC-20 |
| R15 | **The fingerprint library cannot silently start rejecting good pages.** Adding an entry runs the self-check of §5.7; wrong entries are retired, never deleted | doc 22 §8 check 3, GAP§29 |
| R16 | **No silent exemptions.** Pages with little text, thin sections and similar legitimate cases are handled only by the mechanisms of OQ-2.10-9. Until the founder decides, such pages lose score or go to review; they are never skipped from a check unannounced | doc 22 §15 #2 |
| R17 | **The gate is calibrated, not hand-tuned.** Thresholds, weights, the signature file and the shipped fixtures are versioned; changing any of them is a gate change and must pass the torture suite and the golden-set canary. Library entries added by a person at run time are data, guarded by R15 [Assumption: DC-12 extends to the gate] | DC-12, F-29, doc 22 §13 |
| R18 | **Everything is bounded.** One gate run ≤ `LIMIT_GATE_UNIT_MAX_S`; the sibling wait ≤ 1.4's validation deadline (first delivery only); decode and hash work runs on at most `LIMIT_GATE_MAX_PIXELS` per image (downsampled for analysis only, evidence untouched); library and signature lists are size-capped | DC-01 |
| R19 | **Human decisions are labels.** Each approve or reject by 4.4 and each spot-check result is stored with the `gate_result` it concerns, so precision and recall of the gate can be tracked against the benchmark (4.4 and 4.6 store and compute; 2.10 keeps the result stable and versioned) | doc 22 §8 "Gate regression", F-29 |
| R20 | **`published` needs an explicit step.** In V0 the step is `publishBatch` after a 5% random spot check of the batch. `PUBLISH_MODE = auto` replaces it only after the founder decides E2 accuracy is stable | doc 22 §8 lifecycle |
| R21 | **Takedown wins.** A screen that is `withdrawn` can never be re-published by 2.10 (`StaleStatus`); batches skip it; `purgeSourceGateData` clears evidence links | F-18, 1.5 R-8 |
| R22 | **Seed previews are never published.** Captures made for the founder's contact sheet are gated (so the sheet shows whether the capture is usable) but their screens never become `eligible` while the source is not `approved` | DC-19, OQ-1.5-20 |
| R23 | **Results hold codes and numbers, never page text.** `reason_detail`, `detail_code` and `measured` carry ids, enums and measurements only | F-19 spirit, 1.4 §3.5 |
| R24 | **`no_visual` is never publishable as a visual.** An attempt with flag `no_visual` (the S3 non-browser fallback) is `REJECTED` after the facts-only checks, and the unit ends `QUARANTINED` with its evidence kept (1.4 T17) | doc 22 §7 |
| R25 | **One failure never touches another unit or domain.** A gate error on one attempt does not stop the consumer for others | DC-04, DC-09 |

### 5.3 Scoring and verdict resolution

**Score.** Each *evaluated* Score check gives a factor `f` of 1 (pass), 0.5 (partial: one of two sub-measures failed), or 0 (fail). `quality_score = round(100 × Σ(weight × f) ÷ Σ(weight))` over the evaluated Score checks only. `evaluated_weight_pct = 100 × Σ(weight of evaluated) ÷ Σ(weight of all Score checks)`. A section's score uses the same formula over its section-scope checks. All weights and the 0.5 rule are suggestions (OQ-2.10-7). Suggested weights (sum 100): G05 15 · G06 12 · G07 8 · G08 12 · G09 10 · G10 5 · G11 8 · G12 20 · G13 5 · G14 5.

**Hard-fail priority** (first row that applies decides; a verdict from a row above beats any row below):

| Priority | Condition | Verdict | `reasonCode` (1.4 §3.11) |
|---|---|---|---|
| 1 | G15 denied, except the seed-preview case (`not_approved` on a `candidate` source: no verdict effect (wave-3 review), the rows below decide) | `SKIPPED` | `TAKEDOWN` if the deny reason is `takedown`, else `POLICY_DENIED` (detail `deny_reason`) |
| 2 | G01: 404/410; other registrable domain; non-HTML | `SKIPPED` | `HTTP_NOT_FOUND`; `OFF_DOMAIN_REDIRECT`; `NON_HTML_RESPONSE` |
| 3 | G01 401, 403, 429 or login bounce; G02 challenge, CAPTCHA, access denied, login wall; G03 category `challenge` | `BLOCKED` | `CAPTCHA_REQUIRED` for CAPTCHA, `AUTH_REQUIRED` for login, else `BLOCKED` |
| 4 | G00 unreadable; G01 other non-2xx; G02 error text; G03 other categories; G04 blank; `no_visual`; score `< 60` | `REJECTED` | `GATE_REJECTED` (detail `failed_checks`, e.g. `evidence_unreadable`, `no_visual`) |
| 5 | Any Cap check failed, or the attempt flag `hazard_unresolved` is set (wave-3 review), or `60 ≤ score < 80`, or evaluated weight below the floor | `NEEDS_REVIEW` | `GATE_REVIEW` (P), detail `review_reasons` |
| 6 | Otherwise | `ACCEPTED` | none |

**Caps and their `review_reasons` names** (P; 4.4 maps them to inbox categories, doc 22 §10): `HAZARD_UNRESOLVED` (attempt flag `hazard_unresolved`, (wave-3 review)), `OVERLAY_UNRESOLVED` (G08; repeated on one site ⇒ `needs_recipe`), `TRUNCATED` (G10), `CROSS_VIEWPORT_MISMATCH` (G11), `PASS_DIFFERENCE_UNRESOLVED` and `OCR_DISAGREES` (a section the gate cannot settle, §5.4), `SECTION_WITHHELD_SHARE` (§5.4), `SECRET_FOUND` (G14), `DEGRADED_CAPTURE` (flag `degraded`), `LOW_EVIDENCE` (evaluated weight `< LIMIT_GATE_MIN_EVIDENCE_PCT`), `SCORE_BAND` (`60 ≤ score < 80`). Several may apply; all are listed.

**What the verdict does next (1.4's machine, unchanged):** `REJECTED` → next rung with backoff 30 s then 5 min, or `QUARANTINED` when the ladder is exhausted (T16/T17; doc 22 §7); `BLOCKED` → polite retry once, then `BLOCKED` (T18); `SKIPPED` → terminal (T19); `NEEDS_REVIEW` → terminal, 4.4's inbox (T15); `ACCEPTED` → 3.2 normalizes (T15, `ev.normalize`).

### 5.4 Sections and the choice of pass

**Section checks:** G04 (variance), G06, G09, G09b, G12 (box inside the page, height), G12b, G12c, G13. Section verdict: any section Hard failure (G04, box outside the page, G12b, G12c) → `REJECTED`; otherwise the section score `≥ 80` → `ACCEPTED`, `60–79` → `NEEDS_REVIEW`, `< 60` → `REJECTED`; a section the gate cannot settle (`PASS_DIFFERENCE_UNRESOLVED`, `OCR_DISAGREES`) → `NEEDS_REVIEW`.

**Effect on the unit (suggested default, OQ-2.10-6):**

| Section outcome | Section | Unit |
|---|---|---|
| `REJECTED` | Withheld: stays `unpublished` for good | Counts toward the withheld share; if withheld sections exceed `LIMIT_GATE_SECTION_WITHHELD_MAX_PCT` (25%) of the sections, cap `NEEDS_REVIEW` (`SECTION_WITHHELD_SHARE`). The unit is **not** rejected for retry |
| `NEEDS_REVIEW` for `PASS_DIFFERENCE_UNRESOLVED` or `OCR_DISAGREES` | Not eligible until a person approves the unit | Cap `NEEDS_REVIEW` (DC-16: unfixable hazards are `needs_review`, never auto-published) |
| `NEEDS_REVIEW` for the score band only | Not eligible (treated like withheld, counted in the share) | No cap of its own |
| `ACCEPTED` | `eligible` after normalization | — |

When a person approves a `NEEDS_REVIEW` unit (T22), its `NEEDS_REVIEW` sections become `eligible` with `selected_pass = static` (the default of the next table); `REJECTED` sections stay withheld (OQ-2.10-35).

**Pass selection (DC-20; the procedure is OQ-2.10-10).** Applies to each section for which both passes exist (S0). `similarity` = the lower of the global similarity of the two crops and the worst-cell similarity of an 8×8 grid, so that a small blank area (nav buttons) registers.

| Case | `selected_pass` | `pass_reason` |
|---|---|---|
| Only one pass exists (S1, S2 `static_only`) | that pass | `only_pass` |
| `similarity ≥ LIMIT_GATE_PASS_SIMILARITY_MIN` | `static` (the clean reference, DC-20 / doc 08) | `passes_similar` |
| Large difference; the static crop is blank or has clearly less content than the motion crop in the differing cells (variance), and the motion frames are stable | `motion` | `static_blank` |
| Large difference; the section holds a video (wave-3 review) (a `MediaManifest.items[]` entry with `asset_type = 'video'` whose `section.order_index` is this section, or whose `bounds` intersect it) and the static crop shows less content, motion stable | `motion` | `poster_in_static` |
| Large difference; motion frames unstable, static crop stable and not blank | `static` | `motion_unstable` |
| Large difference, none of the above (both look valid but different, e.g. a carousel on another slide) | none | `unresolved` → section `NEEDS_REVIEW` |

### 5.5 BLOCKED, SKIPPED and the 404 that reaches the gate (answers OQ-1.4-8 and review-wave-2 §4)

| Question | Rule (suggested default, OQ-2.10-3) |
|---|---|
| Can the gate return `BLOCKED`? | **Yes**, only when a check proves a block or a wall: G01 401/403/429 or login bounce; G02 challenge, CAPTCHA, access denied, login wall; G03 challenge entry. 1.4 T18 applies the polite-retry rule (`blocked_count`). Pages typed `login` or `signup` by 2.1 are legitimate login pages: the login-wall signature and the login-bounce rule do not apply to them |
| Can the gate return `SKIPPED`? | **Yes**, only for facts that no retry can change: policy denial (G15), 404/410, off-domain final URL, non-HTML. 1.4 T19 makes the unit terminal. `SKIPPED` units with reason `POLICY_DENIED`, `TAKEDOWN`, `HTTP_NOT_FOUND`, `OFF_DOMAIN_REDIRECT`, `NON_HTML_RESPONSE` are not manually retryable (1.4 T24 lists only `JOB_DEADLINE`, `JOB_CANCELLED`, `BUDGET`) |
| A real 404/410 reaches the gate | The suggested rule follows 1.4 T12, which the wave-2 review made accept `skipped HTTP_NOT_FOUND` (review-wave-2 §1): **2.2 reports it and no gate run happens**. (wave-3 review) 2.2 §5.4 now says the same (404 and 410 are `skipped HTTP_NOT_FOUND`); it had said "`captured`, the gate rejects", the difference review-wave-2 §4 carried to this Part (OQ-2.10-3). If a 404/410 unit reaches the gate anyway (older child build, a redirect landing on a 404), G01 maps it to the **same end state**: `SKIPPED HTTP_NOT_FOUND` via T19. Doc 22 §2 row 13 says "Reject; log fingerprint": `SKIPPED` satisfies "never published" and the gate still stores the perceptual hash in `gate_result`, so a person can promote it to a `not_found` library entry |
| A **soft 404** (HTTP 200 with a "not found" page) | G02 (`not_found_text`) or G03 (`not_found`) → `REJECTED`, as doc 22 row 13 says. It climbs the ladder because a different rung might render the real page (for example a consent wall that hid it), unless the gate can say no retry will help: (wave-3 review) `recordValidation` now takes `retryable: false` (1.4 §4.2, T17b, (P)), which the gate passes for outcomes no retry can fix, such as a soft 404 matched by a `not_found` library entry or signature on a page that no consent dismissal explains. Otherwise it costs up to 3 more attempts with 30 s and 5 min backoffs; OQ-2.10-3 keeps the question of when `retryable: false` applies open |
| A 5xx page served as content | `REJECTED` (a retry may succeed) |
| A cross-domain redirect that reached the gate | `SKIPPED OFF_DOMAIN_REDIRECT` (2.2 R8 normally ends it earlier; OQ-1.5-24 notion.so → notion.com) |

### 5.6 Cross-viewport pairing (check 11) and waiting for the sibling

The sibling of a unit is the other unit with the same `crawl_run_id` and `canonical_url` and the other `device_profile` (V0: exactly one; 2.1 creates the two adjacent, OQ-2.1-22).

| Situation when unit X is delivered | Behaviour |
|---|---|
| Sibling has no unit (not created) | G11 `not_evaluable` (`sibling:none`) |
| Sibling is in flight (`PENDING`, `LEASED`, `RUNNING`, `RETRY_WAIT`), this is the first delivery (`validation_redeliveries = 0`), and the domain's breaker is `closed` | **Wait**: acknowledge the event; X stays `CAPTURED`. The wait ends when the sibling's own `capture_unit.captured` event arrives (its handler gates X too, `wakeSibling`), or at 1.4's validation deadline, when T20 redelivers and X proceeds without waiting |
| Domain breaker is `half_open` or `open` | **Do not wait**: a half-open domain admits only one probe unit (1.4 §5.3), so the sibling cannot run until this unit's verdict arrives; waiting would only delay 2.9's probe resolution (2.9 §5.4). G11 `not_evaluable` (`sibling:breaker`) |
| Sibling is `CAPTURED`, `VALIDATING` or terminal with a captured attempt | Proceed; G11 compares the two units' `page_metadata` (`title`, `h1[]`) (wave-3 review) |
| Sibling is terminal with no captured attempt (`QUARANTINED`, `BLOCKED`, `SKIPPED`) | G11 `not_evaluable` (`sibling:uncaptured`) |
| Sibling's own hard checks (`G00`–`G04`) fail when evaluated in memory | G11 `not_evaluable` (`sibling:untrusted`): a challenge page on the other viewport must not make this unit look mismatched. The sibling's results are not written by X's run |
| Redelivery of X (T20) | X never waits again; G11 is evaluated against whatever evidence exists |

**Late sibling (accepted asymmetry, OQ-2.10-11).** If X was judged without its sibling and the sibling later disagrees, the sibling's unit gets `NEEDS_REVIEW` (`CROSS_VIEWPORT_MISMATCH`, detail `sibling_unit_id`); X stays `ACCEPTED` because 1.4 has no transition out of a terminal state. The 5% spot check is the backstop. The spike measures how often this happens.

### 5.7 The bad-page fingerprint library

| Rule | Detail |
|---|---|
| What is compared | The perceptual hash of the above-the-fold region (the first viewport, CSS 1440×900 or 390×844) of each pass's screenshot, because pages differ in total height and a challenge page is a short page. Hash function and region: OQ-2.10-14 |
| Match | Similarity ≥ 0.95 (doc 22 check 3, F-25). With a 64-bit hash, at most 3 differing bits |
| Seeding | Initial entries come from 2.11's fixtures (a challenge page, a blank render, a 404 page, a consent wall) and from the 20-site spike's labelled rejects (OQ-2.10-15) |
| Growth | "The library grows from review decisions" (doc 22 §8): when a reviewer in 4.4 rejects a capture and says it is a bad page (category), 4.4 calls `addBadPageFingerprint`. Default scope `source` (this site's own consent wall); the founder may promote one to `global` (OQ-2.10-15) |
| Safety | Before an entry is created, the self-check counts `ACCEPTED` units and `published` screens whose stored hash would match it. A non-zero count blocks the entry unless `force` is given with a reason (R15) |
| Wrong entries | `retireBadPageFingerprint`; matching ignores retired entries from the next run. Units already rejected by a wrong entry are not re-opened automatically (they can be retried manually, 1.4 T24) |
| Takedown | When a source is taken down, `purgeSourceGateData` clears `evidence_raw_artifact_id` of entries made from that source's captures; the hash stays (a 64-bit hash cannot reconstruct a page) [Assumption; counsel to confirm with E5] |
| Usefulness | `hit_count` and `last_hit_at` per entry; entries never hit are candidates for review |

### 5.8 Gate fingerprints for poison-site detection (OQ-2.9-30)

2.9 counts `QUARANTINED` units of one site that share a `fingerprint` (≥ 5) and then marks the site `needs_recipe_or_skip` (2.9 §5.6). The gate supplies the value through `recordValidation(…, fingerprint)` for every `REJECTED` verdict (suggested format, OQ-2.10-17):

`fingerprint = sha256('gate/v1' ‖ sorted ids of the failed hard checks ‖ matched fingerprint entry id or signature id (if any))`

and, for a rejection by score only, `sha256('gate/v1/score' ‖ sorted ids of the checks with factor 0)`. It deliberately excludes the strategy, URL and attempt, so "this site's pages are always blank" or "always match entry 17" gives equal values across units. It contains no page content.

### 5.11 Capture hazards (DC-16) as seen by the gate

2.3 owns the techniques; the gate detects what is left. Anything it cannot settle is `needs_review`, never auto-published (DC-16). (wave-3 review) 2.3 says so with the attempt flag `hazard_unresolved` (and a `hazards[]` entry in `page_capture_report`); the gate maps the flag to at most `NEEDS_REVIEW` (§5.2, §5.3).

| Sticky or fixed elements | A fixed element covering the first viewport | G08 | Cap `OVERLAY_UNRESOLVED`. Header repeated down a stitched tall image is **not** detected in V0 (OQ-2.10-36) |

The gate shares the founder's computer with the browser slots (F-45). It runs at low CPU priority and with concurrency 1 by default (OQ-2.10-21). If it falls behind, units wait in `CAPTURED`; 1.4's backlog hold counted only accepted-but-not-normalized units (OQ-1.4-17); (wave-3 review) 1.4 §5.4 step 7 now also counts units in `CAPTURED` and `VALIDATING` (OQ-2.10-21).

### Reliability

- The gate is idempotent per attempt and restartable at any point (R3, R6). Losing Redis loses no validation: `capture_unit` state and the event outbox are in Postgres (DC-14, 1.4 §5.4 steps 5–6).
- No unit can stay in `CAPTURED` or `VALIDATING` forever: 1.4's T20 redelivers after the validation deadline and quarantines after the bound (`VALIDATION_TIMEOUT`, which 2.9's breaker window ignores).
- A gate bug can mis-judge many units, so every threshold, weight, signature and library entry is recorded in `*_version` columns, replayable on stored evidence (`replayGate`), and guarded by the torture suite and canary (R17, DC-12).
- The gate never makes a state change except through 1.4's and 1.2's functions (R1, §3.3).

### Security and privacy

| Area | Note |
|---|---|
| Untrusted input | Page text, HTML structure and images come from third-party sites and are attacker-controlled. The gate never executes or renders them. Signature patterns use a linear-time matcher with bounded pattern length (no catastrophic backtracking). Image decoding uses Sharp with a pixel cap (`LIMIT_GATE_MAX_PIXELS`) against decompression bombs |
| No network | The gate makes no outbound request to any site (R2, DC-08) and holds no credentials beyond the worker's database role (1.1 secret matrix) |
| No page text stored | Results hold ids, enums and numbers (R23). OCR text and DOM text are processed in memory and discarded; only overlap ratios are stored |
| Third-party content | `bad_page_fingerprint` stores a perceptual hash, not an image; the optional evidence link is cleared on takedown (R21, §5.7) [Assumption: a 64-bit hash is not third-party content; counsel to confirm, E5] |
| Display policy | Nothing is `published` unless `evaluateCollection('publish')` allowed it at that moment (F-18, R11); screenshots only (F-18) |
| Human overrides | Every approve, reject, fingerprint change, hold and publish override is stored with `actor` and reason (GAP§29) |

### Cost recording

The gate calls no vendor and records no `CostEvent`. It runs on the crawler machine (F-45). The OCR sample uses open-source OCR on CPU (F-28); any `CostEvent` for it is 4.2's and 1.6's. Gate wall time per unit is in `gate_result.duration_ms` so 1.6 can attribute compute if it chooses.

### Testing requirements

| Test | Requirement |
|---|---|
| Per-check unit tests | Every row of §5.2 passes with its negative fixture and fails with its positive fixture; boundary values (0.94 / 0.96 hash similarity; 49 / 50 words; 9% / 11% broken images; 29% / 31% overlay; 29,999 / 30,001 px; 119 / 121 px section) behave as the limits say |
| Resolution tests | Property test over random `CheckSet`s: the verdict follows §5.3 priority exactly; `SKIPPED` and `BLOCKED` never come from a score; a hard failure never has a score; every unit gets exactly one verdict |
| Determinism | Running `runChecks` and `resolveOutcome` twice on the same input, and via `gate run` and via the handler, gives byte-identical results; the OCR sample for an attempt id never changes |
| Idempotency and crash | Kill the handler after storing the result and before `recordValidation`; redelivery ends in one verdict and one `gate_result`; double delivery; delivery after `closeUnits` |
| Sibling wait | Sibling in flight, sibling arrives, sibling never arrives (T20 ends the wait), breaker half-open (no wait), sibling is a challenge page (`untrusted`), late sibling mismatch |
| Library | Self-check refuses an entry that would match an accepted fixture; retire takes effect next run; takedown clears the evidence link and keeps the hash |
| Graph application with 3.2 | `ACCEPTED` unit → screen `eligible`, withheld sections stay `unpublished`; human-approved unit → `NEEDS_REVIEW` sections `eligible` with `selected_pass = static`; denied policy → nothing `eligible`; seed-preview unit → nothing `eligible`; re-applying changes nothing |
| Publication | Sample size is `ceil(5%)` and reproducible from the seed; a `bad` item holds the batch; `StaleStatus` item is skipped; `auto` mode skips the spot check; takedown between `eligible` and `published` publishes nothing |
| Replay | `replayGate` on the golden set with the recorded versions reproduces the stored `computed_verdict` and score; with a changed threshold it reports which checks change and writes nothing |
| **Fixtures required from 2.11** (DC-12, doc 22 §13) | Every fixture named in §5.2, plus the pipeline fixtures below. Each must end with the right verdict and a terminal unit state within its deadline |

**Pipeline fixtures requested from 2.11** (in addition to the per-check ones in §5.2):

| Fixture | Expected result |
|---|---|
| Gate process killed between `gate_result` write and `recordValidation` | One verdict after redelivery, no duplicate rows |
| Redis wiped while units are `CAPTURED` | Reconciler re-delivers (1.4 §5.4 step 6); units validated |
| Evidence only in the spool of a stopped machine (`BlobNotYetStored`) | Retries, then T20, never a wrong verdict |
| OCR engine down; screening function down | G13 / G14 `not_run`; units still get a verdict (DC-10) |
| Sibling never captured (permanent failure of the other viewport) | First unit validates after the deadline with G11 `not_evaluable` |
| Domain breaker half-open with the sibling in `PENDING` | No sibling wait |
| Takedown injected between gate and `applyGateToGraph`, and between `eligible` and `publishBatch` | Nothing becomes or stays `published` (1.5 fixture (d)) |
| Spot check with one `bad` item | Batch `held`; nothing published |
| Library entry that matches a good fixture | Self-check refusal; with `force`, the good fixture is rejected and the entry can be retired |
| Threshold change replayed over the golden set | `replayGate` lists changed checks; no unit changes state |
| Oversized screenshot (pixel count above the cap) | Analysed on a downsampled copy; verdict unchanged |
