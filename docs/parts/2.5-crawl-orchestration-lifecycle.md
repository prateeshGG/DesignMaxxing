## 1. Purpose & Scope

**Purpose.** 1.4 defines the tables, the unit state machine and the events. 2.1 plans pages and 2.9 runs the units. 2.5 is the part that decides **what work exists and when it starts, and makes sure every piece of it ends**. A founder command creates a `crawl_run` (a batch) holding one `capture_job` per site. 2.5 admits jobs one by one, tells 2.1 to start discovery, watches the job while units are captured, pauses it when a site is unhealthy, closes it when its time is up, and rolls the unit results up into one job status using the F-32 70% rule. It then closes the run. A job always reaches a terminal state (DC-04, DC-13). A site that fails never stops other sites (DC-09). The founder normally does one thing, press start (DC-17).

A "per-source crawl run" in the hierarchy text is a `capture_job` inside a `crawl_run`. A single-site crawl is a run of one job (the `POST /sources/:id/crawl` case of Blueprint §47).

**Phase:** `[V0]`. Later-phase hooks are marked **[hook]**.

**Conventions.** Table names are snake_case singular and enums follow 1.2. All ids are UUIDv7 (F-23). All times are `timestamptz`. **Every clock comparison in this Part uses the Postgres clock** (1.4 assumption; OQ-1.1-21). 2.5 **owns two new tables** (§3.4, §3.5). It **reads** other Parts' tables only as listed in §3.1.

### 3.6 Job lifecycle (transition table)

**Terminal statuses:** `COMPLETED`, `FAILED`, `CANCELLED`. A terminal job can be left only by J14 (re-open) and J15 (upgrade-only re-roll-up); `CANCELLED` is never re-opened (OQ-1.4-10).

**Notation.** `PAUSED(x)` = `status = PAUSED`, `status_reason = x` (tokens in §3.7). "Policy" = `evaluateCollection({source_id, purpose: job.purpose, now})` with the robots-based deny reasons `robots_disallow_all` and `robots_unavailable` **ignored** (R4, OQ-2.5-12). Every transition is one Postgres transaction that (a) updates `capture_job` with a **compare-and-set** on `(id, status, status_changed_at)`, (b) sets `status_changed_at`, (c) inserts the `capture_job_change` row, and (d) calls `emit` for any event inside that transaction (1.4 R14). A failed compare-and-set changes nothing and the caller re-reads once.

Starts the close grace (R13) |
| J11 | `PAUSED(closing:*)` | `COMPLETED` / `FAILED` | janitor | no non-terminal unit remains, **or** `now − status_changed_at ≥ LIMIT_JOB_CLOSE_GRACE_S`. In the second case `closeUnits(reasonCode = 'JOB_DEADLINE', includeInFlight = true)` runs first (wave-3 review) (1.4's default `closeUnits` now closes only `PENDING`, `RETRY_WAIT` and `LEASED` units; the flag, a (P) addition in 1.4 §4.2, is what also closes `RUNNING`, `CAPTURED` and `VALIDATING` units once the grace is over: OQ-2.5-8) | roll-up as J8/J9 with `closed_by = <cause>` |
| J12 | `RUNNING` | `FAILED` | janitor (stuck rule, §5.3), or the `capture_job.units_planned` handler | `units_planned_at` is null and the stuck rule fires (`DISCOVERY_FAILED`); or the plan has `unit_count = 0` (`EMPTY_PLAN`) | `error = { code, detail }`; emit finished; defensive `closeUnits(JOB_CANCELLED)` if any unit exists |
| J13 | `RUNNING`, `PAUSED(any)` | `CANCELLED` | `cancelJob` / `cancelRun`; takedown handler; policy watch with a permanent deny | — | **Status first, then** `closeUnits(reasonCode)` where reason ∈ `JOB_CANCELLED`, `TAKEDOWN`, `POLICY_DENIED`; emit finished. A crash between the two is repaired by J16 |
| J14 | `COMPLETED`, `FAILED` | `RUNNING` | janitor **re-open sweep**, or `retryUnits` (immediately) | The job has at least one non-terminal unit (after `manualRetry`, or after a human rejects a `NEEDS_REVIEW` unit, 1.4 T23) | `attempts + 1`, `deadline_at = now + max_runtime_s` (a new active-time budget), `completed_at = null`. **No `capture_job.started`** (discovery is not re-run). The run stays `FINISHED`. Policy watch runs at once, so a denied source is paused or its units closed |
| J15 | `COMPLETED`, `FAILED` | same job, better outcome | `capture_unit.finalized` handler | a unit finalized from `NEEDS_REVIEW` to `ACCEPTED`; no non-terminal unit; recomputed roll-up is strictly better | `FAILED → COMPLETED(partial)` or `partial true → false` only; **never worse**; change row; no event (the finished `dedup_key` is taken) |
| J16 | `CANCELLED` | `CANCELLED` | janitor **cancel sweep** | non-terminal units exist | `closeUnits` again with the code stored in `status_reason` |
| [hook V2] | `RUNNING` | `WAITING_FOR_AUTH` | 7.1 | — | Not built in V0 (F-40) |

## 4. API Surface

**No new BullMQ job name, no new queue, no new event.** 2.5 adds one consumer on 1.4's queue `ev.orchestrator`, two timer loops in `worker-app`, and module functions. **HTTP:** only the admin operator endpoints that Blueprint §47 and 1.5 §4.4 already assign to 2.5, plus (P) siblings; no `/internal/*` (F-24). Everything is a TypeScript module **`services/crawl-orchestrator`** (name from 1.1 §3.1). Names are (P).

**Common rules.**

| Rule | Detail |
|---|---|
| Auth | Commands: `admin` role (F-34) through `web`, or the `cli` role. Loops and event handlers run as `system:2.5-*`. Every command takes an `actor`, written to `capture_job_change.actor` |
| Errors | `NotFound`, `ForbiddenActor`, `InvalidSelection`, `SelectionTooLarge`, `IllegalJobTransition{from,to}`, `NotPlannedYet` (pause before a plan exists), `JobClosing`, `JobCancelled` (retry of a cancelled job), `PolicyDenied{reason}`. Infrastructure errors are thrown unchanged; callers retry |
| Transactions | Each command is one transaction; events are written inside it by `emit`, BullMQ enqueue happens after commit (1.4 §4.4) |
| Idempotency | Stated per function. Every status change is a compare-and-set, so repeating a command or a handler changes nothing the second time |

### 4.1 Types

```ts
type Selection =
  | { kind: 'sources'; sourceIds: UUID[] }
  | { kind: 'filter';  seedStatus: 'candidate' | 'approved';
      neverPreviewed?: boolean;   // no seed_preview job in any status
      neverCrawled?: boolean;     // no crawl/recrawl job in status COMPLETED
      category?: string; limit?: number }   // stable order: domain A to Z

  DenyReason | 'NOT_FOUND' | 'UNSUPPORTED_SOURCE_TYPE' | 'NOT_A_CANDIDATE'

type StartResult = { run: CrawlRun | null;        // null when every source was refused
                     jobs: Array<{ jobId: UUID; sourceId: UUID; purpose: Purpose }>;

```

### 4.2 Commands (callers: 6.4, 4.4, CLI)

```ts
startSeedPreview(input: { selection: Selection; actor: string; label?: string; priority?: number }): Promise<StartResult>
startCrawl      (input: { selection: Selection; actor: string; label?: string; priority?: number }): Promise<StartResult>
cancelJob  (input: { jobId: UUID; actor: string; reason?: string }): Promise<{ status: JobStatus }>
cancelRun  (input: { runId: UUID; actor: string; reason?: string }): Promise<{ cancelledJobs: number }>
pauseJob   (input: { jobId: UUID; actor: string; reason: string }): Promise<{ status: JobStatus }>
resumeJob  (input: { jobId: UUID; actor: string }): Promise<{ status: JobStatus }>
retryUnits (input: { jobId: UUID; unitIds?: UUID[]; startStrategy?: CaptureStrategy; actor: string }):
            Promise<{ retried: UUID[]; refused: Array<{ unitId: UUID; reason: string }>; reopened: boolean }>
```

| Function | Behaviour | Idempotency / errors |
|---|---|---|
| `startSeedPreview` | For each source: pre-checks (R3) with purpose `seed_preview`; the source must be `candidate` (else refusal `NOT_A_CANDIDATE`). Creates one run and one `QUEUED` job per accepted source (J1). Nothing runs until admission | A source with an active job is refused `ACTIVE_JOB_EXISTS`, so a double click creates nothing new. `SelectionTooLarge` above `LIMIT_RUN_MAX_JOBS` |
| `startCrawl` | Same, with the purpose of R3 (`crawl` or `recrawl`, per source). Sources must pass the policy for that purpose (so `candidate`, `dropped`, takedown, competitor are refused with their `DenyReason`) | As above. This is also the re-crawl command (F-10: manual in V0) |
| `cancelJob` | J3 or J13. Status first, then `closeUnits`. Terminal units keep their state | No-op on a terminal job. `JobClosing` is not raised: cancel wins over closing |
| `cancelRun` | RN3: cancels every non-terminal job of the run | Repeat cancels nothing new |
| `pauseJob` / `resumeJob` | J6 / J7. Pause is refused before a plan exists (`NotPlannedYet`); resume re-checks the policy | `IllegalJobTransition` otherwise |
| `retryUnits` | The preferred entry for "re-run failed units" (F-32). Refuses `CANCELLED` jobs (`JobCancelled`) and closing jobs (`JobClosing`); checks the policy for the job's purpose (`PolicyDenied`); calls 1.4's `manualRetry` (which refuses `BLOCKED` and policy-skipped units, R14); if at least one unit was retried and the job is terminal, applies J14 at once. `unitIds` omitted = every retryable unit of the job | If `manualRetry` retries nothing, the job is not re-opened. A direct `manualRetry` call by another Part is still repaired by the janitor's re-open sweep within a minute (J14) |

`reconcileJobPolicy(job)` (pure decision, shared by handlers and the janitor):

```
d = policy(job)                                     // robots reasons ignored
if allowed:                  PAUSED(domain_unhealthy|snoozed|needs_recipe) -> RUNNING   (J5)    // manual pauses stay
elif d.reason == takedown:   cancel(TAKEDOWN)                                          (J3/J13)
elif d.reason in {breaker_open, access_snoozed, needs_recipe_or_skip}:
                             RUNNING -> PAUSED(token)   only if units_planned_at set   (J4)
else:                        cancel(POLICY_DENIED:<d.reason>)                          (J3/J13)
```

All handlers re-read current state and drop stale events; ordering is not guaranteed (1.4 §4.4). The janitor repeats every decision, so a lost event costs at most one janitor interval (DC-14).

## 5. Business Rules & Edge Cases

### 5.1 Rules

| # | Rule | Basis |
|---|---|---|
| R1 | **Work starts only from a person's command in V0.** No automatic first crawl after approval, no automatic re-crawl, no automatic preview after a seed import. A scheduled run is a V1 hook that uses the same creation core | F-10, F-46, DC-19, F-40 |
| R2 | **One active job per source** (unique index, §3.3). A second command for the same source is refused with `ACTIVE_JOB_EXISTS`. A source is never crawled twice in parallel | DC-09, F-10 |
| R3 | **Pre-checks and purpose.** For each source in order: it exists; its type has an adapter (`getAdapter`, entry stage `web_discovery`); no active job (R2). Purpose: `startSeedPreview` → `seed_preview` (source must be `candidate`); `startCrawl` → `recrawl` if the source has a job with purpose `crawl` or `recrawl` in status `COMPLETED`, else `crawl` (a previous `FAILED` crawl is not a completed crawl). Then the policy for that purpose must allow it, robots reasons ignored (R4). A refused source gets a `Refusal`, never a job | 1.5 R-17, R-15, DC-19, F-46 |
| R4 | **Policy is checked, never cached, at four moments:** run creation, admission, re-open, and every janitor tick (policy watch). The two robots-based deny reasons (`robots_disallow_all`, `robots_unavailable`) are **ignored in 2.5's checks**, because a stored robots status can be stale and 2.1 refetches robots.txt at the start of every discovery and plans `SKIPPED` units if it is still disallowed. Permanent denies cancel the job; temporary denies pause or hold it (§4.3). (wave-3 review) 1.5's `evaluateCollection` now takes `phase: 'job_start'` for `crawl` and `recrawl`, which does not deny on a stored robots status; 2.5 passes it at J1, J2 and J14 and keeps ignoring the two robots reasons at janitor ticks (OQ-2.5-12b) | 1.5 R-1, R-15, R-17; 2.1 R-4, R-5; OQ-2.5-12 |
| R5 | **Admission rules.** A `QUEUED` job is admitted only when (a) no intake hold of any reason is open, (b) the crawler is present (§3.5), (c) `running < cap` where `running` counts `RUNNING` jobs only (a `PAUSED` job uses no slot) and `cap = LIMIT_JOBS_RUNNING_MAX`, halved (floor, minimum 1) while the budget state is `throttle`, (d) the policy allows. Order: `priority` descending, then `created_at`, then `id`. Resuming a paused job is never blocked by the cap | doc 22 §6, §9, F-07, F-45 |
| R6 | **2.5 starts discovery only by emitting `capture_job.started` with `purpose`, and never discovers or creates units.** It then waits for `capture_job.units_planned`. Re-opening a job (J14) does not start discovery again | review-wave-2 (OQ-2.1-17), 1.4 §4.6 |
| R7 | **A job never waits without a bound.** (a) Before a plan exists (`units_planned_at` null) a job can only end through the stuck rule (J12), a cancel, or a failed admission: it is never paused or closed with grace, because 1.4's `createUnits` refuses a job that is not `QUEUED` or `RUNNING` and 2.1 would abandon its plan (OQ-2.5-10). (b) After the plan, the active-time deadline (R8), the pause cap, the wall-clock age cap and the discovery stall rule bound every state. `QUEUED` is bounded only by the finite queue, visible in `admissionStatus` (OQ-2.5-9) | DC-01, DC-04, DC-13 |
| R8 | **The 30-minute deadline counts active time** (suggested default of OQ-1.4-24, OQ-1.4-26, OQ-2.9-38): the minutes in which the job was `RUNNING`, the crawler was present and no intake hold was open (§5.5). Stopping the crawl session, closing the lid, a sleeping computer, a power cut, a disk or budget hold and a breaker pause do not use up the clock (which holds count: OQ-2.5-14). The limit is `max_runtime_s` from the effective policy (≤ 1800) | DC-13, F-45, OQ-1.4-26 |
| R9 | **Roll-up only after the plan.** It runs on `capture_unit.finalized` when the job has no non-terminal unit left, and from the janitor as a backstop. ### 5.2 Roll-up (F-32 partial rule) and the denominator

**Inputs.** All units of the job in their current state, grouped by `canonical_url` (read with SQL, OQ-2.5-4a). Rows for earlier manual-retry rounds are not special: only the current unit state counts.

**Classify each unit.**

| Class | Units |
|---|---|
| `good` | `ACCEPTED` (and `NEEDS_REVIEW` when the purpose is `seed_preview`) |
| `review` | `NEEDS_REVIEW` for `crawl` / `recrawl` |
| `excluded` | `SKIPPED` with reason `HTTP_NOT_FOUND`, `NON_HTML_RESPONSE`, `OFF_DOMAIN_REDIRECT`, `ROBOTS_DISALLOWED`, `POLICY_DENIED` or `TAKEDOWN` (the page cannot or must not be captured; 1.4 T12, 2.1 R-5, R-10) |
| `miss` | everything else: `QUARANTINED`, `BLOCKED`, `SKIPPED` with `JOB_DEADLINE`, `JOB_CANCELLED` or `BUDGET`, and any non-terminal unit still present (a bug; logged) |

**Classify each page.** `excluded_page` = all its units excluded. `missed_page` = at least one `miss` unit. `review_page` = no miss, at least one `review` unit. `good_page` = no miss, no review, at least one `good` unit (excluded units are ignored).

**Decide.**

```
target = pages − excluded_pages
if target = 0:        COMPLETED, partial=false, outcome 'nothing_to_capture', status_reason 'ALL_SKIPPED:<top excluded reason>'
                      (an empty plan, unit_count = 0, is FAILED 'EMPTY_PLAN' instead, via J12)
elif good*100 >= LIMIT_PARTIAL_THRESHOLD_PCT * target:
                      COMPLETED, partial = (good < target)
else:                 FAILED, partial=false, status_reason = most frequent reason among missed pages
```

`status_reason` for misses = the unit `reason_code` with the highest count among the units of missed pages (ties: alphabetical). `review_pages` are reported but never counted as good.

**Worked cases (all `crawl` purpose, 25 planned pages unless stated).**

| Case | good | target | Result |
|---|---|---|---|
| All 25 pages accepted on both viewports | 25 | 25 | `COMPLETED`, `partial = false` |
| 18 good, 7 missed | 18 | 25 | 72%: `COMPLETED`, `partial = true` |
| 17 good, 8 missed | 17 | 25 | 68%: `FAILED` (18 is the first passing value: 18×100 ≥ 70×25) |
| 3 pages are 404 (excluded), 16 good, 6 missed | 16 | 22 | 72.7%: `COMPLETED`, `partial = true` |
| Page: desktop accepted, mobile quarantined | | | a `missed_page` |
| Page: desktop accepted, mobile `NEEDS_REVIEW` | | | a `review_page`: not good |
| Site disallows robots (all units `SKIPPED ROBOTS_DISALLOWED`) | 0 | 0 | `COMPLETED`, `partial = false`, `ALL_SKIPPED:ROBOTS_DISALLOWED`, outcome `nothing_to_capture` (on the attention list) |
| Every unit `BLOCKED` | 0 | 25 | `FAILED`, `BLOCKED` (the breaker has also opened, DC-18) |
| 10 pages planned, 6 good, deadline closes 4 | 6 | 10 | 60%: `FAILED`, `JOB_DEADLINE` |
| Seed preview: homepage `NEEDS_REVIEW` | 1 | 1 | `COMPLETED` |
| Seed preview: homepage `BLOCKED` | 0 | 1 | `FAILED`, `BLOCKED` (recorded with the source's `category`, DC-18) |

**Upgrade-only re-roll-up (J15, P).** When a person approves a `NEEDS_REVIEW` unit later (1.4 T22), the job is recomputed. It may move from `FAILED` to `COMPLETED(partial)` or from `partial = true` to `false`. It never gets worse, and no new event is emitted. A rejection (1.4 T23) leaves the terminal set and re-opens the job through J14.

### 5.3 The janitor tick (every 60 s)

Each step is idempotent and independent (R22). Steps 1–9 run per job in a bounded batch, oldest first.

| Step | Action | Basis |
|---|---|---|
| 1 | **Roll-up backstop.** `RUNNING` and `PAUSED(closing:*)` jobs with `units_planned_at` set and no non-terminal unit → J8 / J9 / J11 | R9 |
| 2 | **Clock.** For each `RUNNING` job with a plan: `activeMs ≥ limit` → J10 (`deadline`). Refresh `deadline_at` as `now + remaining` for jobs that stay `RUNNING` | R8, §5.5 |
| 3 | **Caps.** Wall-clock age since `started_at` ≥ `LIMIT_JOB_MAX_AGE_H` → J10 (`max_age`); `PAUSED(≠ closing)` older than `LIMIT_JOB_PAUSE_MAX_H` → J10 (`pause_max`) | DC-01 |
| 4 | **Closing.** `PAUSED(closing:*)` jobs whose grace is over, or with nothing left to wait for → J11 | R11 |
| 5 | **Stuck before planning.** `RUNNING` jobs with `units_planned_at` null: fail with `DISCOVERY_FAILED` (J12) when (a) the `capture_job.started` delivery to consumer `discovery` is `dead` in `event_delivery`; or (b) `getDiscoveryRun` is null and the job's active age ≥ `LIMIT_DISCOVERY_STALL_MIN`; or (c) the discovery run is `RUNNING` or `PLAN_COMMITTED` and no update for `LIMIT_DISCOVERY_STALL_MIN` active minutes; or (d) the discovery run is `ABANDONED` | OQ-2.1-16(b), E-33 of 2.1 |
| 6 | **Policy watch.** For each `RUNNING` or `PAUSED(domain_unhealthy \| snoozed \| needs_recipe)` job: `reconcileJobPolicy` (J4, J5, J13). This also resumes a breaker-paused job when the breaker becomes half-open. (wave-3 review) 2.9's DB2 now emits `source.breaker_half_open`, so this step is the backstop for a lost event, not the only trigger | OQ-2.5-11 |
| 7 | **Re-open sweep.** `COMPLETED` / `FAILED` jobs with non-terminal units → J14. **Cancel sweep:** `CANCELLED` jobs with non-terminal units → J16 | R16, R17 |
| 8 | **Run roll-up.** `OPEN` runs whose jobs are all terminal → RN2 | S9 |
| 9 | **Admission tick** (also runs on its own timer) | R5 |
| 10 | Record counts and the tick time (metrics, §7) | DC-11 |

Active age for rule 5 uses the same active-time function as the deadline (§5.5), measured from `started_at`, or from the discovery run's last update.

### 5.4 Admission (pseudocode)

```
admissionTick():                                    // advisory lock 'orch.admission'
  if isIntakeHeld().held:         return            // any reason (R5a)
  if not isCrawlerPresent():      return            // R5b
  running = count(jobs where status = RUNNING)
  cap     = LIMIT_JOBS_RUNNING_MAX; if budgetState() == 'throttle': cap = max(1, floor(cap / 2))
  for job in QUEUED order by priority desc, created_at, id:
      if running >= cap: break
      d = policy(job)                               // robots reasons ignored
      if d.denied:
          if d.reason in {breaker_open, access_snoozed, needs_recipe_or_skip}: continue     // stays QUEUED
          cancel(job, 'POLICY_DENIED:' + d.reason); continue                                 // J3
      J2(job)                                       // RUNNING + capture_job.started in one transaction
      running += 1
```

Fan-out sequence (what a founder command sets in motion):

```
startCrawl ─► crawl_run + QUEUED jobs (J1) ─► admission (J2) ─► capture_job.started{purpose} ─► 2.1 discovery
   ─► createUnits(final=true) ─► capture_job.units_planned ─► 2.9 leases units (job RUNNING) ─► units end
   ─► capture_unit.finalized ─► roll-up (J8/J9) ─► capture_job.finished ─► run check (RN2) ─► crawl_run.finished
```

### 5.5 The active-time clock

For a job whose current budget started at `b` (the last `capture_job_change` row with reason `admitted` or `reopened`):

```
activeMs(job, at) = measure{ t in [b, at] :
      job.status(t) = RUNNING                      // from capture_job_change intervals
  and crawler_present(t)                           // from crawler_presence intervals (§3.5)
  and no intake_hold open at t }                   // from intake_hold held_at / released_at, any reason
limit  = max_runtime_s * 1000                      // getEffectivePolicy, ≤ 1.8 million ms (30 min)
deadline reached  <=>  activeMs(job, now) >= limit
```

It is a pure function of three interval lists, computed from history at each tick, not accumulated. A janitor that was off for hours, a laptop that slept, or a missed tick cannot make it drift. Accuracy is one janitor interval (up to 60 s late, never early). Reasons a job can be `RUNNING` and still not accumulate time: crawl session stopped (the founder-stop hold or no presence), a disk, backlog or budget hold, the machine asleep or off. `activeTime(jobId)` returns the numbers and the reason the clock is stopped, for 6.4.

| Time that does not count | Why |
|---|---|
| `PAUSED` (any reason), `QUEUED` | not `RUNNING` |
| Crawler absent | nothing can be leased or discovered (F-45) |
| Any intake hold | no new lease can be issued (1.4 R17); the clock would measure nothing about the site |

Doc 22 says a job can never stay `RUNNING` past its deadline. That holds on this clock: a `RUNNING` job always has `activeMs < limit` until J10. The unbounded cases (hold or stop that never ends) are bounded by `LIMIT_JOB_MAX_AGE_H`.

## 7. Non-Functional Notes

### Capacity [Estimate]

| Quantity | Value | Basis |
|---|---|---|
| Jobs per full V0 run | ≈ 500 (one per site) | F-07, `LIMIT_RUN_MAX_JOBS` |
| Units per job | ≤ 50 (25 pages × 2 profiles) | F-10, F-12, doc 22 DC-13 |
| One site end to end | ≈ 17 min on 2 concurrent units (≈ 33 slot-minutes at ≈ 40 s per unit) | DC-13, doc 22 §14 |
| Full V0 batch on 2 slots, one job at a time | ≈ 500 × 17 min ≈ 142 h, so several founder sessions | derived from the line above; the 20-site spike measures it (F-40, E2) |
| Why the running-job cap is about half the slots | A site uses at most 2 slots (F-10). With k jobs on S slots each gets min(2, S ÷ k): S = 2, k = 1 → 17 min; S = 2, k = 2 → ≈ 33 min (over 30); S = 3, k = 2 → ≈ 22 min | OQ-2.5-9 |

| `capture_job_change` rows | ≈ 4 per job, ≈ 2,000 per full run | |

No scaling work is needed. A second crawler machine would be a deployment action (the loops use advisory locks and compare-and-set, 1.1 hook).

### Reliability

- Every state is in Postgres; Redis loss is covered by 1.4's reconciler plus the janitor's repeat of every decision (DC-14).
- Every transition is a compare-and-set in one transaction with its change row and event (1.4 R14). A crash leaves either the old or the new state, never half.
- Cancel and close write status first and units second; sweeps repair a crash between the two (R16).
- Every loop is advisory-locked, idempotent and bounded (R22). Deadlines on every state: active-time clock, discovery stall, pause cap, age cap (R7, R8).
- All loops and handlers run in `worker-app`; before launch that is the founder's own computer, so when nothing runs nothing ticks. The history-based clock (§5.5) makes the first tick after a long gap correct.

### Security & privacy

| Concern | Rule |
|---|---|
| Authorization | Commands require the `admin` role (F-34). Loops use `system:2.5-*` actors. No `/internal/*` (F-24) |
| Credentials | None held or passed. 2.5 needs `DATABASE_URL` and `REDIS_URL` only (1.1 §3.5) |
| Payloads | IDs, counts and short tokens only: no page content, no URLs of discovered pages in events or `error` (F-19 spirit) |

| Boundary | `web` may import this module but not the capture runtime (1.1 R4); 2.5 imports no browser code (R25) |
